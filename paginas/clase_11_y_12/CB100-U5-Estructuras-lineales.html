Casi todas comparten el mismo contrato, el TDA Lista:

public interface Lista<T> {
    void agregar(T x);            // agrega al final
    void insertar(int i, T x);    // inserta en la posición i
    T    obtener(int i);          // devuelve el elemento en i

5.1El TDA Vector (arreglo dinámico)

La primera implementación usa un arreglo por dentro. La gran ventaja del arreglo es el acceso directo: llegar a datos[i] es O(1), instantáneo. El problema es que un arreglo tiene tamaño fijo, y nosotros queremos una estructura que crezca. La solución es el vector dinámico: guardar dos cosas, el tamaño (cuántos elementos hay) y la capacidad (cuántas celdas tiene el arreglo), y agrandar el arreglo cuando se llena.

5.1.1Agregar al final y crecer

Agregar al final es poner el elemento en la primera celda libre. Pero si el arreglo está lleno, primero hay que agrandarlo: se crea uno nuevo del doble de capacidad y se copian los elementos.

public void agregar(T x) {
    if (tamanio == datos.length) {
        redimensionar(datos.length * 2);
    }
    datos[tamanio++] = x;
}

private void redimensionar(int nuevaCapacidad) {
    datos = Arrays.copyOf(datos, nuevaCapacidad);
}

Copiar cuesta O(n)… pero pasa muy de vez en cuando. Este es el famoso análisis amortizado: aunque una operación puntual sea cara, si se reparte su costo entre muchas operaciones baratas, el promedio es bajo.

Idea clave

¿Por qué agregar al final es O(1) amortizado? Al duplicar, las copias a lo largo de n inserciones suman 1 + 2 + 4 + ⋯ + n ≈ 2n = O(n) en total; repartido entre las n inserciones, da O(1) por inserción en promedio. Duplicar (en vez de agrandar de a uno, que costaría O(n) por inserción) es lo que lo hace eficiente.

5.1.2Insertar, eliminar, buscar

Insertar en el medio obliga a correr a la derecha todos los elementos posteriores; eliminar, a correr a la izquierda. Ambas son O(n). Buscar también recorre (O(n)). Pero obtener por índice es O(1).

Como el vector tiene acceso directo, se puede ordenar eficientemente (O(n log n)) con un algoritmo como Mergesort o Quicksort (Unidad 4):

public void ordenar(Comparator<? super T> comparador) {
    T[] vista = (T[]) Arrays.copyOf(datos, tamanio);
    Arrays.sort(vista, comparador);
    System.arraycopy(vista, 0, datos, 0, tamanio);
}

5.1.6Código de uso: todas las operaciones

VectorDinamico<String> v = new VectorDinamico<>();
v.agregar("a");                   // [a]
v.agregar("b");                   // [a, b]
v.insertar(1, "x");               // [a, x, b]
System.out.println(v.obtener(2));          // b     (acceso directo O(1))
System.out.println(v.indiceDe("x"));       // 1
System.out.println(v.contiene("b"));       // true
v.eliminar(0);                    // [x, b]
v.ordenar(Comparator.naturalOrder());      // [b, x]    (orden alfabético)


VectorDinamico<String> otro = new VectorDinamico<>();
otro.agregar("c"); otro.agregar("d");
v.agregarTodos(otro);             // [b, x, c, d]
System.out.println(v.tamanio() + " " + v.capacidad());

(Un detalle fino: el orden de String compara por el valor Unicode de cada carácter; con todo en minúsculas coincide con el alfabético, pero ojo que las mayúsculas ordenan antes: "Z" < "a".)

5.1.7Casos de uso y características

Idea clave

Cuándo conviene un vector. Cuando hacés mucho acceso por índice (leer/escribir v[i]), cuando agregás sobre todo al final, o cuando necesitás ordenar o recorrer rápido. Ejemplos: una tabla de puntajes, los píxeles de una fila, un buffer de lecturas. Es la estructura por defecto para una secuencia.

Error común

Limitaciones del vector. (1) Insertar o borrar al principio o en el medio es O(n) (hay que correr todo). (2) Deja espacio sin usar: la capacidad suele ser mayor que el tamaño, así que hay celdas reservadas y “desperdiciadas”. (3) La redimensión, aunque amortizada, implica una copia costosa puntual. Admite valores duplicados y mantiene el orden de inserción.

5.1.8En la API de Java

Java trae dos clases con esta idea: ArrayList (la recomendada) y Vector (más antigua, sincronizada; hoy se prefiere ArrayList). Ambas implementan la interfaz List.

List<String> lista = new ArrayList<>();     // como nuestro VectorDinamico
lista.add("a"); lista.add(1, "X"); lista.get(0); lista.contains("a");
lista.remove(0); Collections.sort(lista);

5.2El TDA Conjunto (Set)

Un Conjunto es una colección sin duplicados y sin posición: sólo importa si un elemento está o no está. Su operación distintiva es que agregar ignora lo que ya está.

5.2.1Implementación manual y operaciones de conjuntos

Podemos implementarlo apoyándonos en una lista (ConjuntoLista): antes de agregar, chequea si el elemento ya está. Además de agregar/quitar/contiene, un conjunto ofrece las operaciones clásicas: unión, intersección y diferencia.

public Conjunto<T> interseccion(Conjunto<T> otro) {
    ConjuntoLista<T> r = new ConjuntoLista<>();
    for (Object o : aArreglo()) {
        if (otro.contiene((T) o)) {
            r.agregar((T) o);    // sólo los que están en ambos
        }
    }
    return r;
}

(aArreglo() es un método auxiliar del conjunto que devuelve sus elementos en un Object[] para poder recorrerlos; como los arreglos de Java no pueden ser genéricos, al leer cada elemento hace falta el cast (T) o — está completo en el repo, en ConjuntoLista.)

5.2.2Código de uso

ConjuntoLista<String> a = new ConjuntoLista<>();
a.agregar("a"); a.agregar("b"); a.agregar("a");         // el segundo "a" se ignora
System.out.println(a.contiene("a"));                    // true
a.eliminar("b");                                        // {a}


ConjuntoLista<String> otro = new ConjuntoLista<>();
otro.agregar("a"); otro.agregar("c");
System.out.println(a.union(otro));              // {a, c}
System.out.println(a.interseccion(otro));       // {a}
System.out.println(a.diferencia(otro));         // {}

5.2.3Casos de uso y características

Idea clave

Cuándo conviene un conjunto. Cuando necesitás pertenencia sin duplicados: “¿ya vimos este usuario?”, “palabras únicas de un texto”, “etiquetas de un elemento”. También para operaciones de conjuntos (unión de dos grupos, intersección de intereses, etc.).

Error común

Limitaciones del conjunto. (1) No admite duplicados (si necesitás contar repetidos, no es la estructura). (2) No tiene posición ni orden (no existe “el elemento i”). (3) En nuestra implementación sobre lista, agregar/contiene son O(n); con una tabla de hash (próxima unidad) serán O(1) promedio.

5.2.4En la API de Java

HashSet (sin orden, O(1) promedio), LinkedHashSet (mantiene el orden de inserción) y TreeSet (mantiene los elementos ordenados, O(log n)). Todos implementan Set.

Set<String> s = new HashSet<>();
s.add("a"); s.add("a");              // el segundo se ignora
s.retainAll(otro);                   // intersección
s.addAll(otro);                      // unión
s.removeAll(otro);                   // diferencia

5.3Listas enlazadas

Las listas enlazadas no usan un arreglo, sino nodos encadenados por referencias (Unidad 2). Su gran ventaja frente al vector: insertar y borrar en los extremos es O(1) y no desperdician espacio (usan exactamente los nodos que necesitan). Su desventaja: no tienen acceso directo (llegar a la posición i es O(n)).

5.3.1Lista simplemente enlazada

Cada nodo guarda su valor y una referencia al siguiente. La lista conoce el primero (y, para agregar al final rápido, el ultimo); el último apunta a null.

Insertar no requiere correr nada, sólo re-enganchar referencias:

public void insertar(int i, T x) {
    if (i < 0 || i > tamanio) {
        throw new IndexOutOfBoundsException("índice " + i);
    }
    if (i == tamanio) { agregar(x); return; }
    Nodo<T> n = new Nodo<>(x);
    if (i == 0) { n.siguiente = primero; primero = n; }
    else {
        Nodo<T> anterior = nodoEn(i - 1);
        n.siguiente = anterior.siguiente;
        anterior.siguiente = n;
    }
    tamanio++;
}

Eliminar es “saltear” el nodo; el eliminado queda inalcanzable y lo libera el GC (Unidad 2). Buscar recorre comparando con equals.

Código de uso:

ListaSimplementeEnlazada<String> l = new ListaSimplementeEnlazada<>();
l.agregar("a"); l.agregar("b"); l.agregar("c");
l.insertar(0, "X");             // [X -> a -> b -> c]
l.obtener(2);                   // b      (¡esto recorre, es O(n)!)
l.indiceDe("c");                // 3
l.eliminar(1);                  // saca "a"
Idea clave

Cuándo conviene una lista enlazada. Cuando hacés muchas inserciones y borrados al principio (o en posiciones que ya tenés ubicadas), o cuando no sabés cuántos elementos vas a tener y no querés desperdiciar espacio. Es la base de pilas, colas y muchas otras estructuras.

Error común

Limitaciones de la lista simple. (1) No hay acceso directo: obtener(i) es O(n). (2) Cada nodo gasta memoria extra en la referencia al siguiente. (3) Sólo se recorre hacia adelante. Admite duplicados y mantiene el orden.

5.3.2Lista doblemente enlazada

Si cada nodo guarda también una referencia al anterior, tenemos una lista doblemente enlazada. Permite recorrer en los dos sentidos y eliminar un nodo dado en O(1) (no hace falta buscar al anterior).

Insertar y eliminar re-enganchan referencias en ambos sentidos. Insertar X entre a y b requiere exactamente cuatro asignaciones de referencias, y el orden en que las hagas importa:

Seguí los números: (1) X.siguiente = b y (2) X.anterior = a conectan el nodo nuevo mirando a sus futuros vecinos — esto no rompe nada, porque todavía nadie apunta a X. Recién entonces (3) a.siguiente = X y (4) b.anterior = X insertan a X en la cadena. Si hicieras (3) antes que (1), a dejaría de apuntar a b… y como X todavía no lo apunta, perdés la referencia al resto de la lista: es el error clásico de “la lista se corta”.

Eliminar es más simple: sólo dos re-enganches, porque el nodo que se va no necesita que lo desconecten “de su lado”:

ListaDoblementeEnlazada<Integer> l = new ListaDoblementeEnlazada<>();
l.agregar(1); l.agregar(2); l.agregar(3);
l.insertar(1, 99);              // [1 <-> 99 <-> 2 <-> 3]
l.eliminar(0);                  // [99 <-> 2 <-> 3]
Idea clave

Ventaja clave. Además de recorrer en dos sentidos, para llegar a la posición i se puede empezar por el extremo más cercano (a lo sumo n/2 pasos). Es la que usa LinkedList de Java.

Error común

Costo extra. Cada nodo guarda dos referencias (anterior y siguiente) en vez de una: más memoria por elemento. Sigue sin tener acceso directo O(1) — n/2 es la mitad de n, y la mitad de lineal sigue siendo lineal.

5.3.3Lista circular

En una lista circular, el siguiente del último nodo vuelve a apuntar al primero, cerrando un anillo. Es ideal para recorrer en ronda.

ListaCircular<String> c = new ListaCircular<>();
c.agregar("lun"); c.agregar("mar"); c.agregar("mie");
c.insertar(1, "feriado");       // (lun -> feriado -> mar -> mie -> lun…)
c.eliminar(2);                  // saca "mar"; el anillo se re-cierra
c.obtener(0);                   // lun
c.contiene("mie");              // true
Idea clave

Cuándo conviene. Para procesos que se repiten en ronda: turnos rotativos (round-robin), un reproductor en modo “repetir”, el problema de Josephus, un buffer circular.

Error común

Cuidado al recorrerla. Nunca se llega a null: si recorrés esperando el final, das vueltas para siempre. Hay que contar los elementos.

5.3.4Lista circular doblemente enlazada

Combina las dos ideas: cada nodo conoce a su anterior y a su siguiente, y el anillo se cierra en los dos sentidos (ultimo.siguiente == primero y primero.anterior == ultimo). Permite avanzar y retroceder en ronda, y agregar/quitar en cualquiera de los dos extremos en O(1).

Sus operaciones combinan lo que ya sabés de la doble y de la circular: al insertar o eliminar se re-enganchan los punteros en ambos sentidos, y además hay que mantener cerrados los dos cierres del anillo (la flecha naranja, anterior del primero al último; y la violeta, siguiente del último al primero):

ListaCircularDoble<String> c = new ListaCircularDoble<>();
c.agregar("a"); c.agregar("b"); c.agregar("c");
c.insertar(0, "X");             // (X <-> a <-> b <-> c <->…)
c.eliminar(2);                  // saca "b": vecinos re-enganchados en ambos sentidos
Error común

Limitaciones de la circular doble. Es la lista más “cara” de mantener: (1) cada nodo guarda dos referencias (más memoria por elemento); (2) cada inserción/borrado debe actualizar punteros en ambos sentidos y preservar los dos invariantes del anillo — más punteros que mantener consistentes, más lugares donde equivocarse; (3) igual que la circular simple, nunca hay null: recorrer esperando el final da vueltas infinitas (hay que contar); y (4) sigue sin acceso directo: obtener(i) es O(n) (aunque puede arrancar por el extremo más cercano). Usala sólo cuando de verdad necesites ronda + ambos sentidos.

Idea clave

Cuándo conviene. Cuando necesitás recorrer una ronda en los dos sentidos (adelante y atrás) con inserción/borrado eficiente en los extremos: listas de reproducción con “anterior/siguiente” cíclico, la lista de ventanas abiertas (Alt+Tab), historiales circulares.

5.4Pila (LIFO)

Una Pila (stack) es una estructura lineal donde sólo se toca un extremo, el tope. Sigue la regla LIFO (Last In, First Out): el último que entra es el primero que sale, como una pila de platos. Sus operaciones son apilar (poner en el tope), desapilar (sacar del tope) y tope (mirar sin sacar).

La construimos sobre un vector: apilar y desapilar operan al final del arreglo, así que son O(1) (amortizado). Es un buen ejemplo de armar una estructura sobre otra.

public class Pila<T> {
    private final VectorDinamico<T> datos = new VectorDinamico<>();
    public void apilar(T x)  { datos.agregar(x); }
    public T desapilar()     { return datos.eliminar(datos.tamanio() - 1); }
    public T tope()          { return datos.obtener(datos.tamanio() - 1); }
}

Código de uso:

Pila<String> p = new Pila<>();
p.apilar("a"); p.apilar("b"); p.apilar("c");        // tope = c
p.tope();               // c   (mira sin sacar)
p.desapilar();          // c   (LIFO: sale el último que entró)
p.desapilar();          // b
Idea clave

Casos de uso. Deshacer/rehacer (undo), el botón “atrás” del navegador, evaluar expresiones y balancear paréntesis, la pila de llamadas de la recursión (Unidad 4), y el recorrido DFS de un grafo (más adelante).

Error común

Limitaciones. Sólo se accede al tope: no hay acceso por índice ni recorrido arbitrario. Si necesitás mirar el elemento del medio, la pila no es la estructura.

En la API de Java: se recomienda ArrayDeque (con push/pop/peek); existe también java.util.Stack, pero es una clase antigua que conviene evitar.

5.5Cola (FIFO)

Una Cola (queue) agrega por un extremo (el fondo) y saca por el otro (el frente). Sigue la regla FIFO (First In, First Out): el primero que entra es el primero que sale, como la fila del banco. Operaciones: encolar, desencolar y frente.

La construimos con nodos enlazados y punteros al frente y al fondo, para que encolar y desencolar sean O(1).

public void encolar(T x) {
    Nodo<T> n = new Nodo<>(x);
    if (fondo == null) {
        frente = fondo = n;
    } else { fondo.siguiente = n; fondo = n; }
    tamanio++;
}

public T desencolar() {
    T valor = frente.valor;
    frente = frente.siguiente;
    if (frente == null) {
        fondo = null;
    }
    tamanio--;
    return valor;
}

Código de uso:

Cola<String> c = new Cola<>();
c.encolar("a"); c.encolar("b"); c.encolar("c");       // frente = a
c.frente();           // a
c.desencolar();       // a    (FIFO: sale el primero que entró)
c.desencolar();       // b
Idea clave

Casos de uso. Atención por orden de llegada (una impresora, pedidos de un servidor), buffers de mensajes o streaming, el recorrido BFS de un grafo (más adelante), y la planificación round-robin de tareas.

Error común

Limitaciones. Sólo se ven el frente y el fondo: sin acceso por índice. Una variante, la cola doble (deque), permite agregar y quitar por ambos extremos.

En la API de Java: las interfaces son Queue y Deque; la implementación recomendada es ArrayDeque (también sirve LinkedList).

5.8Ejemplo integrador: un sistema de turnos

Cerremos la unidad con un ejemplo que junta las cuatro estructuras —y, fiel a la regla de la materia, usando la API nativa de Java. Una mesa de ayuda atiende clientes: la fila de espera es una Cola (se atiende en orden de llegada, FIFO); los DNI registrados son un Conjunto (nadie saca dos turnos); el historial de atendidos es un Vector (orden de atención, acceso por índice); y las atenciones se pueden deshacer con una Pila (se deshace la última, LIFO).

private final Deque<Integer> filaDeEspera = new ArrayDeque<>();   // Cola     (FIFO)
private final Set<Integer>   registrados  = new HashSet<>();      // Conjunto
private final List<Integer>  atendidos    = new ArrayList<>();    // Vector
private final Deque<Integer> deshacer     = new ArrayDeque<>();   // Pila     (LIFO)


public boolean sacarTurno(int dni) {
    if (!registrados.add(dni)) {
        return false;     // el Conjunto rechaza duplicados
    }
    filaDeEspera.addLast(dni);                      // encolar: al FONDO de la fila
    return true;
}


public int atender() {
    int dni = filaDeEspera.pollFirst();             // desencolar: del FRENTE (FIFO)
    atendidos.add(dni);                             // historial en orden
    deshacer.push(dni);                             // apilar para poder deshacer
    return dni;
}


public int deshacerUltimaAtencion() {
    int dni = deshacer.pop();                       // el ÚLTIMO atendido (LIFO)
    atendidos.remove(atendidos.size() - 1);
    filaDeEspera.addFirst(dni);                     // vuelve AL FRENTE de la fila
    return dni;
}

Tracemos una sesión y verifiquemos cada estructura en su papel:

mesa.sacarTurno(111);                 // true
mesa.sacarTurno(222);                 // true
mesa.sacarTurno(111);                 // false: ya tenía turno (Conjunto)
mesa.sacarTurno(333);                 // true
mesa.atender();                       // 111    (FIFO: el primero que llegó)
mesa.atender();                       // 222
mesa.historial();                     // [111, 222]
mesa.deshacerUltimaAtencion();        // 222    (LIFO: el último atendido)
mesa.atender();                       // 222    (volvió al frente de la fila)
mesa.atender();                       // 333
mesa.historial();                     // [111, 222, 333]

Fijate el juego entre las dos disciplinas: la Cola decide a quién atender (el que más espera), la Pila decide qué deshacer (lo más reciente). El código completo, ejecutable, está en el repo: material.i05_lineales, clase SistemaDeTurnos.

5.9Errores comunes

Error común
  • Confundir tamaño con capacidad en el vector: hay celdas libres que no son elementos.
  • Olvidar poner en null la celda liberada al eliminar del vector (fuga de memoria, Unidad 2).
  • Perder una referencia al re-enganchar una lista enlazada: la lista se “corta”.
  • Recorrer una lista circular esperando un null: hay que contar los elementos.
  • Creer que la lista enlazada tiene acceso por índice O(1): llegar a la posición i es O(n).
  • Usar un conjunto cuando necesitás contar duplicados, o una lista cuando necesitás pertenencia rápida.
  • Usar nuestras implementaciones en los parciales/TP en vez de las de la API de Java.

5.11Preguntas teóricas

1¿Qué diferencia hay entre el tamaño y la capacidad de un vector dinámico?

Son dos números distintos que el vector guarda por separado:

  • Tamaño (tamanio): cuántos elementos hay realmente. Es lo que devuelve size() y lo único que le importa a quien usa la estructura.
  • Capacidad: cuántas celdas tiene el arreglo interno. Es un detalle de implementación.

Siempre vale tamaño ≤ capacidad. La diferencia, capacidad − tamaño, son celdas reservadas y vacías: memoria pedida que todavía no se usa.

¿Para qué existe esa diferencia? Para que agregar sea barato. Si el arreglo tuviera exactamente el tamaño justo, cada inserción obligaría a crear uno nuevo y copiar todo: O(n) siempre. Teniendo lugar de sobra, agregar es simplemente escribir en la próxima celda libre: O(1).

La característica negativa es el espacio desperdiciado: justo después de duplicar, la mitad del arreglo está vacía. Es el precio del O(1) amortizado.

El error de confundirlos es concreto: si el bucle de recorrido usara datos.length (capacidad) en vez de tamanio, recorrerías celdas en null que no son elementos.
2¿Por qué agregar al final de un vector es O(1) amortizado? ¿Y si agrandáramos de a uno?

Con duplicación. Casi todas las inserciones cuestan 1 (escribir en la celda libre). Sólo las que caen justo cuando el arreglo se llena pagan la copia. Las capacidades van 1, 2, 4, 8, 16…, así que las copias suman:

1 + 2 + 4 + ⋯ + n/2 + n < 2n

Es una suma geométrica: cada término es el doble del anterior, y el total es menos que el doble del último. Sumando las n escrituras, el costo total de n inserciones es menos de 3n, o sea menos de 3 por inserción: O(1) amortizado.

Agrandando de a uno. Ahí cada inserción redimensiona, y la inserción i copia i − 1 elementos:

1 + 2 + 3 + ⋯ + (n − 1) = n(n − 1)/2 = Θ(n²)

Es una suma aritmética. Repartido entre n operaciones queda Θ(n) amortizado: para n = 1000, mil veces más lento.

La regla general: cualquier factor multiplicativo (×2, ×1.5) da amortizado constante, porque genera una serie geométrica; cualquier incremento aditivo (+1, +10) da amortizado lineal, porque genera una serie aritmética. El tamaño del salto sólo cambia la constante.

(Dato: el ArrayList de Java usa ×1.5.)

3¿Por qué insertar en el medio de un vector es O(n) y en una lista enlazada (ubicado el lugar) es O(1)?

Porque el vector guarda los elementos contiguos y la lista enlazada no.

En el vector, la posición i de cada elemento es su lugar físico en memoria. Para meter uno nuevo en la posición i, todos los que están de i en adelante tienen que correrse físicamente una celda a la derecha. Son n − i movimientos: O(n), y en el peor caso (insertar al principio) se mueve todo.

En la lista enlazada, el orden no lo da la posición física sino las referencias. Los nodos pueden estar desparramados por la memoria. Insertar es sólo re-enganchar punteros: dos asignaciones en la simple, cuatro en la doble. Ningún dato se mueve, y el costo no depende de n: O(1).

La letra chica

Fijate que el enunciado aclara “ubicado el lugar”, y eso es esencial. Llegar a la posición i de una lista enlazada cuesta O(n), porque hay que saltar de nodo en nodo. Así que insertar(i, x) completo es O(n) en las dos estructuras.

La lista sólo gana de verdad cuando ya tenés el nodo en la mano (recorriendo, o con un iterador) o cuando insertás en los extremos, que es donde los punteros primero y ultimo te ahorran la búsqueda.

4¿Por qué acceder por índice es O(1) en el vector y O(n) en la lista enlazada?

En el vector, las celdas son contiguas y del mismo tamaño, así que la dirección del elemento i se calcula con una cuenta:

direccion(i) = inicio + i × (tamaño de celda)

Una multiplicación y una suma, sin importar si i es 0 o un millón: O(1). Es acceso directo o aleatorio.

En la lista enlazada no hay ninguna cuenta posible: cada nodo está en una dirección arbitraria, y la única forma de conocerla es preguntándosela al nodo anterior. Para llegar al elemento i hay que arrancar en primero y saltar i veces: O(n). Es acceso secuencial.

La doblemente enlazada mejora la constante —puede arrancar por el extremo más cercano, a lo sumo n/2 saltos— pero no el orden: la mitad de lineal sigue siendo lineal.

Consecuencia práctica: un bucle for (i=0; i<n; i++) lista.get(i) es O(n) sobre un ArrayList y O(n²) sobre una LinkedList. Para recorrer una lista enlazada se usa el for-each o un iterador, que avanzan de a un nodo y vuelven a ser O(n).
5¿Qué ventaja aporta una lista doblemente enlazada frente a la simple?

Que cada nodo conoce también a su anterior. Eso habilita cuatro cosas:

  1. Recorrer en los dos sentidos. La simple sólo va hacia adelante.
  2. Eliminar un nodo dado en O(1). Es la ventaja más concreta: para sacar un nodo hace falta modificar a su antecesor, y la doble lo tiene a mano (nodo.anterior). En la simple hay que recorrer desde el principio para encontrarlo: O(n).
  3. Eliminar el último en O(1). Caso particular del anterior, pero muy visible: aunque la lista simple guarde el puntero ultimo, para borrarlo necesita al anteúltimo, y tiene que recorrer toda la lista para llegar. La doble lo obtiene con ultimo.anterior.
  4. Llegar a la posición i por el extremo más cercano (≤ n/2 saltos). Mejora la constante, no el orden.

El costo: una referencia más por nodo (más memoria por elemento) y el doble de punteros que mantener consistentes en cada operación — cuatro re-enganches al insertar en vez de dos, y más lugares donde equivocarse.

Es la que usa LinkedList de Java, y por eso implementa Deque: agregar y quitar por los dos extremos en O(1).

6¿Para qué sirve una lista circular y qué cuidado hay que tener al recorrerla?

Para qué sirve: para procesos que se repiten en ronda, donde después del último elemento viene naturalmente el primero. Casos típicos:

  • Turnos rotativos (round-robin): repartir tiempo de CPU o atención entre varios, dando la vuelta.
  • Reproductor en modo “repetir”: al terminar la última canción arranca la primera.
  • Problema de Josephus: eliminar cada k-ésimo en ronda hasta que quede uno (ejercicio 4 del nivel difícil).
  • Buffer circular: un área de memoria que se sobreescribe dando la vuelta.

La ventaja estructural es que desaparece el caso especial: no hace falta preguntar “¿llegué al final? entonces volvé al principio”, porque el siguiente del último es el primero.

El cuidado, y es serio: nunca se llega a null. Este bucle, que es correcto en cualquier lista normal, acá no termina jamás:

while (actual != null) {        // ¡vueltas infinitas!
    hacerAlgo(actual);
    actual = actual.siguiente;
}

Hay dos formas correctas: contar, o comparar contra el nodo de arranque.

// (a) contando
Nodo<T> actual = primero;
for (int i = 0; i < tamanio; i++) {
    hacerAlgo(actual);
    actual = actual.siguiente;
}

// (b) hasta volver al principio (ojo con la lista vacía)
if (primero != null) {
    Nodo<T> actual = primero;
    do {
        hacerAlgo(actual);
        actual = actual.siguiente;
    } while (actual != primero);
}

Fijate que en (b) va do-while y no while: con while, la condición actual != primero sería falsa de entrada y no procesaría ningún nodo.

7¿Qué caracteriza al TDA Conjunto? ¿Por qué agregar es O(n) en una implementación sobre lista?

Lo que lo caracteriza:

  1. No admite duplicados. agregar de algo que ya está no hace nada (y no es un error: se ignora en silencio).
  2. No tiene posición ni orden. No existe “el elemento i”: no hay obtener(i) ni indiceDe. Sólo importa si está o no está.
  3. Ofrece las operaciones de conjuntos: unión, intersección y diferencia.

Por qué agregar es O(n) sobre lista: porque antes de agregar hay que verificar que no esté, y la única forma de verificarlo en una lista es recorrerla entera comparando con equals. Ese chequeo es una búsqueda lineal:

public void agregar(T x) {
    if (!contiene(x)) {      // <- O(n): recorre toda la lista
        datos.agregar(x);    //    O(1) amortizado
    }
}

El costo no está en insertar (eso es barato), sino en garantizar el invariante “sin duplicados”. Lo mismo vale para contiene y eliminar. Y las operaciones de conjuntos quedan en O(n · m), porque por cada elemento de uno se busca en el otro.

Cómo se arregla: con una tabla de hash (próxima unidad), que ubica cada elemento en una posición calculada a partir de su hashCode. Ahí verificar la pertenencia deja de ser un recorrido y pasa a ser una cuenta: O(1) promedio. Por eso HashSet es la implementación estrella, y por eso el contrato equals/hashCode de la Unidad 3 importa tanto.

La respuesta honesta

En la práctica, casi siempre ArrayList. Y si sólo tocás los extremos, ArrayDeque le gana a LinkedList incluso ahí.

El motivo son las constantes y la caché: el ArrayList guarda los elementos contiguos en memoria, así que recorrerlo trae bloques enteros de una vez. La LinkedList salta a direcciones arbitrarias, cada salto puede fallar la caché, y además cada nodo es un objeto más que el recolector tiene que administrar. Para n moderados, un ArrayList puede ganarle a una LinkedList incluso insertando al principio, aunque su complejidad sea peor.

Es un buen recordatorio de la Unidad 4: la notación asintótica dice cómo escala, no cuál es más rápido para tu n.

Los tres implementan Set —sin duplicados— y se diferencian en el orden que garantizan y en el costo:

Set<String> h = new HashSet<>(List.of("pera", "manzana", "uva"));
// [uva, pera, manzana] — orden arbitrario, puede cambiar entre corridas

Set<String> l = new LinkedHashSet<>(List.of("pera", "manzana", "uva"));
// [pera, manzana, uva] — como las metiste

Set<String> t = new TreeSet<>(List.of("pera", "manzana", "uva"));
// [manzana, pera, uva] — alfabético

Cuál usar:

  • HashSet por defecto, si el orden no importa. Es el más rápido.
  • LinkedHashSet cuando necesitás únicos pero en orden de aparición — el caso clásico es “palabras únicas de un texto”, donde un HashSet te las daría desordenadas.
  • TreeSet cuando necesitás recorrerlos ordenados, o consultas de rango (first, last, headSet, subSet). Pagás O(log n) por eso.
Dos trampas

(1) Con HashSet y LinkedHashSet, si tu clase redefine equals sin hashCode, los objetos se pierden adentro del conjunto: metés uno y contains te dice que no está. Es exactamente el contrato de la Unidad 3.

(2) Con TreeSet, el que decide si dos elementos son “el mismo” es el compareTo, no el equals. Si compareTo devuelve 0 para dos objetos distintos, el TreeSet los trata como duplicados y descarta uno.

Invertir

List<Integer> invertir(List<Integer> l) que devuelva una nueva lista invertida. Test.

PistaEl enunciado dice nueva: no uses Collections.reverse sobre el argumento, que lo modifica in situ. Copiá primero.
/** O(n). Devuelve una lista NUEVA: no toca el argumento. */
public static List<Integer> invertir(List<Integer> l) {
    List<Integer> r = new ArrayList<>(l);   // copia O(n)
    Collections.reverse(r);                  // in situ sobre LA COPIA
    return r;
}

Versión a mano, recorriendo de atrás para adelante:

public static List<Integer> invertirManual(List<Integer> l) {
    List<Integer> r = new ArrayList<>(l.size());
    for (int i = l.size() - 1; i >= 0; i--) {
        r.add(l.get(i));
    }
    return r;
}

El punto del ejercicio es la decisión in situ vs. nueva. Collections.reverse(l) modifica la lista que le pasás — si lo aplicaras directo al argumento, quien te llamó se encontraría con su lista dada vuelta sin haberlo pedido. Es el aliasing de la Unidad 2.

Ojo con la versión manual sobre LinkedList

l.get(i) es O(1) en ArrayList pero O(n) en LinkedList: el bucle pasaría a ser O(n²). Si el parámetro es un List genérico, no sabés cuál te van a pasar. La versión con Collections.reverse no tiene ese problema porque usa un ListIterator cuando conviene.

Sin duplicados

List<Integer> sinDuplicados(List<Integer> l) preservando el orden (usá LinkedHashSet). Test.

PistaEl enunciado te da la estructura justa. Preguntate por qué no sirve un HashSet común acá.
/** O(n): el LinkedHashSet descarta duplicados en O(1) promedio
 *  y conserva el orden de inserción. */
public static List<Integer> sinDuplicados(List<Integer> l) {
    return new ArrayList<>(new LinkedHashSet<>(l));
}

Una sola línea que hace dos cosas: el LinkedHashSet tira los repetidos y recuerda el orden; el ArrayList lo vuelve a convertir en lista.

Por qué LinkedHashSet y no HashSet: el HashSet también saca los duplicados, pero te los devuelve en orden arbitrario —un orden que ni siquiera está garantizado entre corridas—. El enunciado pide preservar el orden, así que ahí se rompería.

Y por qué no a mano con una lista:

// funciona, pero es O(n²)
List<Integer> r = new ArrayList<>();
for (int x : l) {
    if (!r.contains(x)) r.add(x);   // contains recorre: O(n)
}

Ese contains sobre lista es O(n) y se ejecuta n veces: O(n²). Es exactamente el problema del conjunto sobre lista de 5.2.3, y la razón de que exista el hashing.

@Test void quitaDuplicadosPreservandoOrden() {
    assertEquals(List.of(3, 1, 2), sinDuplicados(List.of(3, 1, 3, 2, 1)));
    assertEquals(List.of(5), sinDuplicados(List.of(5, 5, 5)));
    assertEquals(List.of(1, 2, 3), sinDuplicados(List.of(1, 2, 3)));
    assertEquals(List.of(), sinDuplicados(List.of()));
}

@Test void conservaLaPrimeraAparicion() {
    // si el orden fuera el de la última aparición, daría [1, 3, 2]
    assertEquals(List.of(3, 1, 2), sinDuplicados(List.of(3, 1, 2, 3, 1)));
}
El último test es el que distingue “primera aparición” de “última”, y el que falla si usaras un HashSet.

Unión de dos listas sin duplicados. Test.

PistaUn Set hace el trabajo solo: metés las dos listas y los repetidos se descartan.
/** O(n + m) con LinkedHashSet: cada add es O(1) promedio. */
public static List<Integer> union(List<Integer> a, List<Integer> b) {
    Set<Integer> r = new LinkedHashSet<>(a);
    r.addAll(b);                   // los repetidos se ignoran solos
    return new ArrayList<>(r);
}

addAll es la unión de la API: agrega todos los de b, y el Set descarta los que ya estaban. Usé LinkedHashSet para que el resultado sea predecible (primero los de a en su orden, después los nuevos de b), lo que hace los tests mucho más fáciles de escribir.

Las tres operaciones de conjuntos de la API, todas sobre una copia para no destruir el original:

Set<Integer> copia = new HashSet<>(a);
copia.addAll(b);       // UNIÓN          A ∪ B
copia.retainAll(b);    // INTERSECCIÓN   A ∩ B   (quedarse sólo con los de b)
copia.removeAll(b);    // DIFERENCIA     A − B
El error que hay que evitar

a.addAll(b) directamente sobre el parámetro modifica la lista de quien te llamó. Un método que se llama union y además muta su argumento es una sorpresa desagradable. Copiá siempre primero.

Palíndromo

boolean esPalindromo(List<Character> l). Test.

PistaDos índices caminando desde los extremos hacia el centro: alcanza con n/2 comparaciones. No hace falta invertir nada.
/** O(n) tiempo, O(1) espacio: dos índices hacia el centro. */
public static boolean esPalindromo(List<Character> l) {
    int i = 0, j = l.size() - 1;
    while (i < j) {
        if (!l.get(i).equals(l.get(j))) {   // ¡equals, no ==!
            return false;                    // corta apenas encuentra diferencia
        }
        i++;
        j--;
    }
    return true;
}

n/2 comparaciones y nada de memoria extra. La alternativa —invertir y comparar— también es O(n) en tiempo pero gasta O(n) de espacio en la copia.

La trampa del ==

La lista es de Character (el objeto), no de char (el primitivo). Con == compararías referencias, y funcionaría sólo por accidente: Java cachea los Character del rango ASCII, así que 'a' == 'a' daría true… pero con caracteres fuera de ese rango fallaría. Siempre equals con objetos — es lo mismo que pasa con Integer y el cache de −128 a 127 (Unidad 2).

    assertTrue(esPalindromo(List.of()));                    // el vacío lo es
    assertFalse(esPalindromo(List.of('a', 'b')));
    assertFalse(esPalindromo(List.of('a', 'b', 'c', 'a')));
}

Rotar

Rotá una List k posiciones a la derecha (devolvé nueva). Test.

PistaExiste Collections.rotate, pero es in situ. Y pensá qué pasa si k es mayor que el tamaño, o negativo.
/** O(n). Devuelve una lista NUEVA rotada k posiciones a la derecha. */
public static <T> List<T> rotar(List<T> l, int k) {
    List<T> r = new ArrayList<>(l);
    if (r.size() > 1) {
        Collections.rotate(r, k);    // maneja k > n y k negativo solo
    }
    return r;
}

Versión a mano, que deja ver la aritmética:

public static <T> List<T> rotarManual(List<T> l, int k) {
    int n = l.size();
    if (n == 0) return new ArrayList<>();
    int d = ((k % n) + n) % n;       // normaliza: k grande y k negativo
    List<T> r = new ArrayList<>(n);
    for (int i = 0; i < n; i++) {
        r.add(l.get((i - d + n) % n));
    }
    return r;
}

Los dos bordes que decide el ((k % n) + n) % n:

  • k mayor que n: rotar 7 posiciones una lista de 3 es lo mismo que rotar 1. El % n lo resuelve.
  • k negativo: acá está la trampa. En Java -1 % 3 da -1, no 2, y un índice negativo revienta. Sumar n y volver a tomar módulo lo normaliza al rango correcto.

Rotar es, conceptualmente, recorrer una lista circular: el % n es lo que hace que después del último venga el primero.

PistaCollections.max ya lanza si está vacía — pero lanza NoSuchElementException. Decidí cuál querés vos.
/** O(n). Lanza IllegalArgumentException si la lista está vacía. */

        throw new IllegalArgumentException("no hay máximo de una lista vacía");

A mano, si querés mostrar el recorrido:

int max = l.get(0);                 // arranca con un elemento REAL
for (int x : l) {                   // for-each: O(n) en cualquier List

Intersección de dos Set<Integer> (usá retainAll sobre una copia). Test.

PistaEl enunciado subraya “sobre una copia” por algo: retainAll modifica el conjunto sobre el que lo llamás.
/** O(n) con HashSet: cada contains del retainAll es O(1) promedio. */
public static Set<Integer> interseccion(Set<Integer> a, Set<Integer> b) {
    Set<Integer> r = new HashSet<>(a);   // LA COPIA
    r.retainAll(b);                       // se queda sólo con los que están en b
    return r;
}

retainAll es “retené sólo estos”: elimina de r todo lo que no esté en b. Eso es exactamente A ∩ B.

El costo: con HashSet es O(n), porque cada consulta a b es O(1) promedio. Sobre listas sería O(n · m) — el mismo salto de 5.2.3.

¿Contiene todos?

boolean contieneTodos(List<Integer> l, List<Integer> req). Test.

Pistal.containsAll(req) lo hace en una línea, pero fijate qué complejidad tiene. ¿Se puede mejorar?
/** O(n + m): pasar l a HashSet hace que cada consulta sea O(1) promedio. */
public static boolean contieneTodos(List<Integer> l, List<Integer> req) {
    Set<Integer> presentes = new HashSet<>(l);   // O(n)
    return presentes.containsAll(req);            // m consultas O(1)
}

La versión de una línea también es correcta:

return l.containsAll(req);    // pero es O(n · m)

La diferencia es el costo. containsAll sobre una List hace, por cada elemento de req, un contains que recorre l entera: O(n · m). Volcando l a un HashSet primero, cada consulta pasa a O(1) promedio y el total es O(n + m).

Con n = m = 10 000: cien millones de comparaciones contra veinte mil. Cambiar la estructura de datos cambió el orden del algoritmo — que es el mensaje central de esta unidad junto con la 4.

Pila sobre ArrayList

Pila<T> (apilar/desapilar/tope) usando ArrayList por dentro; test LIFO.

PistaEl tope tiene que ser el final del ArrayList, no el principio: ahí las operaciones son O(1).
/** Pila LIFO sobre ArrayList. El tope es el FINAL de la lista:
 *  apilar y desapilar son O(1) amortizado. */
public class Pila<T> {
    private final List<T> datos = new ArrayList<>();

    public void apilar(T x) {
        datos.add(x);                       // al final: O(1) amortizado
    }

    public T desapilar() {
        if (estaVacia()) {
            throw new NoSuchElementException("la pila está vacía");
        }
        return datos.remove(datos.size() - 1);   // del final: O(1)
    }

    public T tope() {
        if (estaVacia()) {
            throw new NoSuchElementException("la pila está vacía");
        }
        return datos.get(datos.size() - 1);      // mira sin sacar
    }

    public boolean estaVacia() { return datos.isEmpty(); }
    public int tamanio()       { return datos.size(); }
}
La decisión que define el ejercicio

El tope va al final, no al principio. Si usaras datos.add(0, x) y datos.remove(0), la pila seguiría siendo LIFO y los tests pasarían… pero cada operación sería O(n), porque habría que correr todos los elementos. Al final, en cambio, no se mueve nada.

Esto es exactamente la diferencia entre las figuras 5.2 y 5.3. La estructura que elegís por dentro determina el costo del TDA de afuera, aunque el contrato sea idéntico.

Por qué lanzar y no devolver null: desapilar una pila vacía es un error de uso, no un resultado válido. Devolver null sería ambiguo (¿estaba vacía, o apilaste un null?) y el problema aparecería lejos de la causa. Es la regla de excepciones de la Unidad 1B.

@Test void comportamientoLIFO() {
    Pila<String> p = new Pila<>();
    p.apilar("a"); p.apilar("b"); p.apilar("c");
    assertEquals("c", p.tope());          // mira sin sacar
    assertEquals(3, p.tamanio());          // tope NO consumió
    assertEquals("c", p.desapilar());      // sale el ÚLTIMO
    assertEquals("b", p.desapilar());
    assertEquals("a", p.desapilar());
    assertTrue(p.estaVacia());
}

@Test void vaciaLanza() {
    Pila<Integer> p = new Pila<>();
    assertTrue(p.estaVacia());
    assertThrows(NoSuchElementException.class, p::desapilar);
    assertThrows(NoSuchElementException.class, p::tope);
}

@Test void inverteElOrden() {
    Pila<Integer> p = new Pila<>();
    for (int i = 1; i <= 5; i++) p.apilar(i);

    assertEquals(List.of(5, 4, 3, 2, 1), salida);   // dada vuelta
}

Cola sobre LinkedList

PistaAcá sí conviene la LinkedList: sacar del principio es O(1) porque no hay que correr nada. Con ArrayList sería O(n).
/** Cola FIFO sobre LinkedList: se encola al final y se desencola del frente.
 *  Las dos son O(1) porque la LinkedList es doblemente enlazada. */
public class Cola<T> {
    private final LinkedList<T> datos = new LinkedList<>();

    public void encolar(T x) {
        datos.addLast(x);                   // al FONDO: O(1)
    }

    public T desencolar() {
        if (estaVacia()) {
            throw new NoSuchElementException("la cola está vacía");
        }
        return datos.removeFirst();         // del FRENTE: O(1)
    }

    public T frente() {
        if (estaVacia()) {
            throw new NoSuchElementException("la cola está vacía");
        }
        return datos.getFirst();
    }

    public boolean estaVacia() { return datos.isEmpty(); }
    public int tamanio()       { return datos.size(); }
}

Acá la elección de estructura importa de verdad, y es el contraste con el ejercicio anterior:

Estructura internaencolar (al final)desencolar (del frente)
ArrayListO(1) amort.O(n) — corre todo
LinkedListO(1)O(1)

La pila puede vivir sobre un ArrayList porque toca un solo extremo, el final — el barato. La cola toca los dos, y uno de ellos es el principio, que en un arreglo es caro. Por eso va sobre nodos enlazados.

(En producción usarías ArrayDeque para las dos: es un arreglo circular que hace los dos extremos O(1) sin el costo de memoria de los nodos.)

Mezclar ordenadas

Fusioná dos List ordenadas en una nueva ordenada. Test.

PistaEs la fusión de Mergesort (Unidad 4). Dos índices avanzando en paralelo: en cada paso tomás el menor de los dos frentes.
/** O(n + m): un solo recorrido en paralelo. NO hay que ordenar de nuevo. */
public static List<Integer> mezclar(List<Integer> a, List<Integer> b) {
    List<Integer> r = new ArrayList<>(a.size() + b.size());
    int i = 0, j = 0;

    while (i < a.size() && j < b.size()) {      // mientras queden en las DOS
        if (a.get(i) <= b.get(j)) {             // <= mantiene la estabilidad
            r.add(a.get(i++));
        } else {
            r.add(b.get(j++));
        }
    }
    while (i < a.size()) r.add(a.get(i++));     // lo que sobró de a
    while (j < b.size()) r.add(b.get(j++));     // ...o de b
    return r;
}

Por qué no juntar y ordenar. La solución fácil sería:

List<Integer> r = new ArrayList<>(a);
r.addAll(b);
Collections.sort(r);          // O((n+m) log(n+m))

Funciona, pero desperdicia la información que ya tenías: las listas ya venían ordenadas. Aprovecharlo baja de O(N log N) a O(N). Es una idea que aparece todo el tiempo: los datos ordenados valen, no los desordenes por comodidad.

Los dos while del final son imprescindibles. Cuando una lista se agota, la otra puede tener elementos sin copiar. Olvidarlos es el bug más común acá, y sólo se ve con listas de largos distintos — por eso el test los cubre.

El <= del medio hace la fusión estable: ante un empate toma el de la izquierda, así que los elementos iguales conservan su orden relativo original. Con < estricto se perdería.

}

Eliminar según condición

Quitá de una List los múltiplos de 3 (removeIf). Test.

PistaProbá primero borrar dentro de un for-each y mirá qué excepción salta. Ese es el punto del ejercicio.
/** O(n). Modifica la lista IN SITU. */
public static void quitarMultiplosDe3(List<Integer> l) {
    l.removeIf(x -> x % 3 == 0);
}
Por qué existe removeIf: las dos formas que NO funcionan

(1) Borrar dentro de un for-each tira ConcurrentModificationException:

for (Integer x : l) {
    if (x % 3 == 0) l.remove(x);      // ✗ ConcurrentModificationException
}

El iterador lleva un contador de modificaciones; si la lista cambia por fuera, detecta la inconsistencia y aborta. Es una protección, no un capricho: sin ella recorrerías basura.

(2) Un for con índice hacia adelante compila, corre… y saltea elementos:

for (int i = 0; i < l.size(); i++) {
    if (l.get(i) % 3 == 0) l.remove(i);   // ✗ saltea
}

Al borrar la posición i, todo se corre una a la izquierda: el que era i+1 pasa a ser i, pero el bucle igual incrementa y lo salta. Con [3, 6, 1] el 6 sobrevive. Es un bug silencioso, que es lo peor.

Las dos formas correctas, si no pudieras usar removeIf:

// (a) con el iterador explícito — el remove del ITERADOR sí es válido
Iterator<Integer> it = l.iterator();
while (it.hasNext()) {
    if (it.next() % 3 == 0) it.remove();
}

// (b) recorriendo HACIA ATRÁS: borrar en i no afecta a los índices menores
for (int i = l.size() - 1; i >= 0; i--) {
    if (l.get(i) % 3 == 0) l.remove(i);
}
Y una trampa más, con List<Integer>

l.remove(2) borra la posición 2; l.remove(Integer.valueOf(2)) borra el valor 2. Son dos sobrecargas distintas (remove(int) y remove(Object)) y Java elige la de int sin avisarte.

Insertar ordenado

Insertá un valor en una List ordenada manteniéndola ordenada. Test.

PistaComo ya está ordenada, podés encontrar la posición con búsqueda binaria en O(log n). Mirá qué devuelve Collections.binarySearch cuando no encuentra el valor.
/** Busca la posición en O(log n), pero insertar sigue siendo O(n). */
public static void insertarOrdenado(List<Integer> l, int x) {
    int pos = Collections.binarySearch(l, x);
    if (pos < 0) {
        pos = -pos - 1;          // el "punto de inserción" codificado
    }
    l.add(pos, x);
}
El truco de binarySearch

Cuando encuentra el valor, devuelve su índice (≥ 0). Cuando no, no devuelve simplemente −1: devuelve -(punto de inserción) - 1, que siempre es negativo y codifica dónde habría que meterlo. Deshacer esa cuenta es -pos - 1.

¿Por qué esa codificación tan rara? Porque el punto de inserción puede ser 0, y -0 es 0: no se distinguiría de “lo encontré en la posición 0”. El -1 extra desplaza todo al rango negativo sin ambigüedad.

La versión lineal, equivalente y más legible:

int i = 0;
while (i < l.size() && l.get(i) < x) i++;
l.add(i, x);
La búsqueda binaria acá no cambia el orden total

Encontrar la posición pasa de O(n) a O(log n), pero add(pos, x) sigue siendo O(n) porque hay que correr todos los posteriores (figura 5.3). El total es O(n) igual.

Para que la búsqueda binaria realmente rindiera haría falta una estructura donde insertar en el medio sea barato — y ninguna lista lineal lo es. Eso llega con los árboles balanceados (y es lo que hace TreeSet por dentro, en O(log n) todo).

Y en una LinkedList es peor: binarySearch necesita get(i), que ahí es O(n), así que la "búsqueda binaria" termina costando O(n log n) — peor que recorrer.

¿Permutación?

boolean esPermutacion(List<Integer> a, List<Integer> b). Test.

Pista¡Ojo con usar conjuntos acá! [1,1,2] y [1,2,2] tienen el mismo conjunto y no son permutación. Las repeticiones cuentan.
/** O(n log n): ordenar las dos copias y comparar. */
public static boolean esPermutacion(List<Integer> a, List<Integer> b) {
    if (a.size() != b.size()) {
        return false;                     // atajo O(1)
    }
    List<Integer> x = new ArrayList<>(a);
    List<Integer> y = new ArrayList<>(b);
    Collections.sort(x);
    Collections.sort(y);
    return x.equals(y);
}

Versión O(n) con un mapa de frecuencias:

public static boolean esPermutacionRapida(List<Integer> a, List<Integer> b) {
    if (a.size() != b.size()) return false;
    Map<Integer, Integer> cuenta = new HashMap<>();
    for (int x : a) cuenta.merge(x, 1, Integer::sum);    // +1
    for (int x : b) {
        Integer c = cuenta.get(x);
        if (c == null || c == 0) return false;           // sobra en b
        cuenta.put(x, c - 1);                            // -1
    }
    return true;   // los tamaños coinciden, así que no puede sobrar en a
}
Por qué un Set NO sirve

Sería tentador escribir new HashSet<>(a).equals(new HashSet<>(b)). Pero el conjunto descarta las repeticiones, que es justo la información que define una permutación:

a = [1, 1, 2]     →  conjunto {1, 2}
b = [1, 2, 2]     →  conjunto {1, 2}     ¡iguales!

Y no son permutación una de otra. Es exactamente el error de 5.9: usar un conjunto cuando necesitás contar duplicados.

El chequeo de tamaño tampoco lo salva: en el ejemplo, las dos listas miden 3.

Diferencia de conjuntos

A − B con removeAll sobre una copia. Test.

PistaTesteá explícitamente que A − B ≠ B − A: es la propiedad que distingue a la diferencia de las otras dos operaciones.
/** A − B: los de A que NO están en B. O(n) con HashSet. */
public static Set<Integer> diferencia(Set<Integer> a, Set<Integer> b) {
    Set<Integer> r = new HashSet<>(a);   // LA COPIA
    r.removeAll(b);
    return r;
}

Las tres operaciones juntas, para tenerlas de una:

Set<Integer> copia = new HashSet<>(a);
copia.addAll(b);       // UNIÓN          A ∪ B    (conmutativa)
copia.retainAll(b);    // INTERSECCIÓN   A ∩ B    (conmutativa)
copia.removeAll(b);    // DIFERENCIA     A − B    ← NO conmutativa

La diferencia no es simétrica, y es lo único que hay que retener de este ejercicio. Con A = {1,2,3} y B = {3,4}:

A − B = {1, 2}        los de A que no están en B
B − A = {4}           los de B que no están en A

Pensalo así: A − B siempre es un subconjunto de A, nunca puede aparecer algo de B. Por eso el resultado depende de cuál va primero.

(Si necesitaras “lo que está en uno pero no en el otro”, sin importar cuál, eso es la diferencia simétrica: (A − B) ∪ (B − A).)

    assertEquals(Set.of(1, 2), diferencia(Set.of(1, 2), Set.of()));
    assertEquals(Set.of(), diferencia(Set.of(), Set.of(1)));
}

¿Subconjunto?

boolean esSubconjunto(Set<Integer> a, Set<Integer> b). Test.

PistaDefiní primero en qué dirección: ¿a ⊆ b o b ⊆ a? Documentalo, porque es la mitad del ejercicio. Y pensá qué pasa con el conjunto vacío.
/** ¿a ⊆ b? True si TODOS los elementos de a están en b. O(n) con HashSet. */
public static boolean esSubconjunto(Set<Integer> a, Set<Integer> b) {
    return b.containsAll(a);
}

Una línea, pero la dirección hay que dejarla clarísima en el javadoc: b.containsAll(a) pregunta si a ⊆ b, no al revés. Invertirlo es el error de este ejercicio, y los tests tienen que fijarlo.

Equivalente con diferencia, que a veces se ve más claro:

// a ⊆ b  ⟺  no queda nada de a al sacarle todo lo de b
return diferencia(a, b).isEmpty();
Los dos casos que confunden

El conjunto vacío es subconjunto de todos, incluido de sí mismo. No es un capricho de la definición: “todos los elementos de ∅ están en B” es verdadero por vacuidad, porque no hay ningún elemento que pueda fallar la condición. containsAll sobre un conjunto vacío devuelve true, que es lo correcto.

Todo conjunto es subconjunto de sí mismo (A ⊆ A). Si quisieras el subconjunto propio —contenido pero distinto— habría que pedir además !a.equals(b).

El costo: O(n) con HashSet, porque cada contains es O(1) promedio. Si b fuera una List, sería O(n · m).

Mover el máximo al final

Reordená una List dejando el máximo último. Test.

PistaDecidí antes de escribir: ¿intercambiás el máximo con el último (rápido), o lo sacás y lo agregás al final (conserva el orden del resto)? No dan lo mismo.
/** O(n). Saca el máximo de donde esté y lo agrega al final.
 *  Conserva el orden relativo del resto. */
public static void maximoAlFinal(List<Integer> l) {
    if (l.size() <= 1) {
        return;                              // ya está
    }
    int pos = l.indexOf(Collections.max(l));  // primera aparición del máximo
    l.add(l.remove(pos));                     // sacar y volver a agregar al final
}

La otra interpretación, con intercambio:

public static void maximoAlFinalSwap(List<Integer> l) {
    if (l.size() <= 1) return;
    int pos = l.indexOf(Collections.max(l));
    int ultimo = l.size() - 1;
    Collections.swap(l, pos, ultimo);
}
Las dos no dan lo mismo

Con [1, 9, 2, 3]:

sacar y agregar  →  [1, 2, 3, 9]      el resto conserva su orden
intercambiar     →  [1, 3, 2, 9]      el 3 quedó en el lugar del 9

Las dos cumplen “el máximo queda último”, así que el enunciado está incompleto y hay que elegir. Lo importante es documentar cuál elegiste y que el test lo fije — si no, el primer cambio de implementación rompe a quien te usaba.

El intercambio es O(1) (una vez ubicado); sacar-y-agregar es O(n) porque remove(pos) corre todo. Los dos son O(n) en total por la búsqueda del máximo.

El intercambio, por cierto, es exactamente lo que hace cada pasada del selection sort: llevar el extremo a su lugar definitivo.

Frecuencia de un elemento

int veces(List<Integer> l, int x) (con Collections.frequency o a mano). Test.

PistaEs el ejercicio que muestra por qué una lista sí sirve para algo que un conjunto no puede hacer.
/** O(n): un recorrido comparando con equals. */
public static int veces(List<Integer> l, int x) {
    return Collections.frequency(l, x);
}

A mano:

public static int vecesManual(List<Integer> l, int x) {
    int cuenta = 0;
    for (Integer v : l) {
        if (v != null && v == x) {   // v == x desempaqueta: comparación numérica
            cuenta++;
        }
    }
    return cuenta;
}

Este ejercicio cierra el nivel por una razón: es lo que un conjunto no puede hacer. Un Set te dice si algo está, nunca cuántas veces — descarta los duplicados por definición. Para contar hacen falta una lista (recorriendo, O(n) por consulta) o un mapa de frecuencias (O(1) por consulta, que llega con hashing).

Si vas a consultar muchas veces sobre la misma lista, conviene precalcular el mapa una sola vez:

Map<Integer, Integer> frecuencias = new HashMap<>();
for (int v : l) {
    frecuencias.merge(v, 1, Integer::sum);       // O(n) UNA vez
}
frecuencias.getOrDefault(x, 0);                  // O(1) cada consulta

Con k consultas: O(n · k) recorriendo, contra O(n + k) con el mapa.

En v == x, como x es un int primitivo, Java desempaqueta el Integer y compara números: está bien. Pero si los dos fueran Integer, compararías referencias, y funcionaría sólo entre −128 y 127 por el cache de Integer (Unidad 2). Con 1000 daría false aunque los valores sean iguales.

Collections.frequency usa equals, así que no tiene ese problema.

Vector dinámico

VectorDinamico<T> sobre arreglo con redimensión (agregar/obtener/insertar/eliminar/tamanio); test que crece más allá de la capacidad inicial.

PistaJava no deja hacer new T[n]. La forma estándar es (T[]) new Object[n] con @SuppressWarnings. Y no te olvides del null al eliminar.
public class VectorDinamico<T> {
    private T[] datos;
    private int tamanio;

    @SuppressWarnings("unchecked")
    public VectorDinamico() {
        datos = (T[]) new Object[4];     // no se puede new T[]: genéricos + arreglos
        tamanio = 0;
    }

    /** O(1) amortizado. */
    public void agregar(T x) {
        if (tamanio == datos.length) {
            redimensionar(datos.length * 2);
        }
        datos[tamanio++] = x;
    }

    /** O(1): acceso directo. */
    public T obtener(int i) {
        verificarRango(i, tamanio - 1);
        return datos[i];
    }

    /** O(n): hay que correr los posteriores a la derecha. */
    public void insertar(int i, T x) {
        verificarRango(i, tamanio);       // acá i == tamanio SÍ vale
        if (tamanio == datos.length) {
            redimensionar(datos.length * 2);
        }
        for (int k = tamanio; k > i; k--) {
            datos[k] = datos[k - 1];
        }
        datos[i] = x;
        tamanio++;
    }

    /** O(n): hay que correr los posteriores a la izquierda. */
    public T eliminar(int i) {
        verificarRango(i, tamanio - 1);
        T quitado = datos[i];
        for (int k = i; k < tamanio - 1; k++) {
            datos[k] = datos[k + 1];
        }
        tamanio--;
        datos[tamanio] = null;            // ← IMPRESCINDIBLE: evita la fuga
        return quitado;
    }

    public int tamanio()    { return tamanio; }
    public int capacidad()  { return datos.length; }

    private void redimensionar(int nuevaCapacidad) {
        datos = Arrays.copyOf(datos, nuevaCapacidad);
    }

    private void verificarRango(int i, int max) {
        if (i < 0 || i > max) {
            throw new IndexOutOfBoundsException("índice " + i + ", tamaño " + tamanio);
        }
    }
}
Las tres cosas que se cobran

(1) El datos[tamanio] = null al eliminar. Sin esa línea todo pasa los tests funcionales, pero el arreglo sigue apuntando al objeto que "sacaste": el recolector no lo puede levantar. Es la fuga de memoria de la Unidad 2, y es silenciosa.

(2) El rango de insertar es distinto. Para obtener y eliminar, el índice válido llega hasta tamanio - 1. Para insertar llega hasta tamanio, porque insertar al final es legítimo.

(3) El bucle de insertar va hacia atrás. Si corrieras de izquierda a derecha, cada escritura pisaría el valor que todavía no copiaste y terminarías replicando un solo elemento.

Sobre el (T[]) new Object[n]: los arreglos de Java son covariantes y reificados (saben su tipo en ejecución) pero los genéricos se borran en compilación, así que new T[n] no compila. Crear un Object[] y castearlo es el idioma estándar; el warning es seguro mientras el arreglo quede privado y nunca lo devuelvas como T[].

public class ListaSimplementeEnlazada<T> {

    private static class Nodo<T> {
        T valor;
        Nodo<T> siguiente;
        Nodo(T valor) { this.valor = valor; }
    }

    private Nodo<T> primero;
    private Nodo<T> ultimo;      // para que agregar al final sea O(1)
    private int tamanio;

    /** O(1) gracias al puntero «ultimo». */
    public void agregar(T x) {
        Nodo<T> n = new Nodo<>(x);
        if (primero == null) {
            primero = ultimo = n;           // la lista estaba vacía
        } else {
            ultimo.siguiente = n;
            ultimo = n;
        }
        tamanio++;
    }

    /** O(1) al principio; O(n) en el medio por la búsqueda. */
    public void insertar(int i, T x) {
        if (i < 0 || i > tamanio) {
            throw new IndexOutOfBoundsException("índice " + i);
        }
        if (i == tamanio) { agregar(x); return; }     // reusa el caso del final

        Nodo<T> n = new Nodo<>(x);
        if (i == 0) {
            n.siguiente = primero;          // (1) el nuevo mira al viejo primero
            primero = n;                    // (2) recién ahora se re-apunta
        } else {
            Nodo<T> anterior = nodoEn(i - 1);
            n.siguiente = anterior.siguiente;   // (1) leer ANTES de sobrescribir
            anterior.siguiente = n;             // (2)
        }
        tamanio++;
    }

    /** O(n): hay que llegar al ANTERIOR del que se elimina. */
    public T eliminar(int i) {
        verificar(i);
        Nodo<T> quitado;
        if (i == 0) {
            quitado = primero;
            primero = primero.siguiente;
            if (primero == null) ultimo = null;      // quedó vacía
        } else {
            Nodo<T> anterior = nodoEn(i - 1);
            quitado = anterior.siguiente;
            anterior.siguiente = quitado.siguiente;  // saltea
            if (quitado == ultimo) ultimo = anterior;
        }
        quitado.siguiente = null;           // no dejar al nodo apuntando a la lista
        tamanio--;
        return quitado.valor;
    }

    /** O(n): no hay acceso directo. */
    public T obtener(int i) {
        verificar(i);
        return nodoEn(i).valor;
    }

    /** O(n): primera posición de x, o -1. */
    public int indiceDe(T x) {
        Nodo<T> actual = primero;
        for (int i = 0; actual != null; i++, actual = actual.siguiente) {
            if (Objects.equals(actual.valor, x)) {   // tolera nulls
                return i;
            }
        }
        return -1;
    }

    public int tamanio() { return tamanio; }

    private Nodo<T> nodoEn(int i) {
        Nodo<T> actual = primero;
        for (int k = 0; k < i; k++) actual = actual.siguiente;
        return actual;
    }

    private void verificar(int i) {
        if (i < 0 || i >= tamanio) {
            throw new IndexOutOfBoundsException("índice " + i);
        }
    }

Los tres detalles que separan una implementación correcta de una que "casi anda"

(1) Mantener ultimo consistente. Cada operación tiene que actualizarlo: al eliminar el último nodo, ultimo pasa al anterior; al vaciar la lista, a null. Si te olvidás, el próximo agregar engancha el nodo a un fantasma y la lista se corrompe en silencio.

(2) Leer antes de sobrescribir. En n.siguiente = anterior.siguiente seguido de anterior.siguiente = n, el orden es obligatorio: al revés, n se apuntaría a sí mismo y perderías el resto (laboratorio 3).

(3) Objects.equals y no valor.equals(x). Si el valor guardado es null, la segunda forma tira NullPointerException.

Por qué eliminar el último es O(n) aunque tengas ultimo: necesitás al anteúltimo para que apunte a null, y la lista simple no tiene forma de ir hacia atrás. Es precisamente lo que resuelve la doble.

public class ListaDoblementeEnlazada<T> {

    private static class Nodo<T> {
        T valor;
        Nodo<T> anterior, siguiente;
        Nodo(T valor) { this.valor = valor; }
    }

    private Nodo<T> primero, ultimo;
    private int tamanio;

    public void agregar(T x) {
        Nodo<T> n = new Nodo<>(x);
        if (ultimo == null) {
            primero = ultimo = n;
        } else {
            n.anterior = ultimo;
            ultimo.siguiente = n;
            ultimo = n;
        }
        tamanio++;
    }

    public void insertar(int i, T x) {
        if (i < 0 || i > tamanio) throw new IndexOutOfBoundsException("índice " + i);
        if (i == tamanio) { agregar(x); return; }

        Nodo<T> b = nodoEn(i);              // el que va a quedar DESPUÉS
        Nodo<T> a = b.anterior;             // el que va a quedar ANTES (puede ser null)
        Nodo<T> n = new Nodo<>(x);

        n.siguiente = b;                    // (1) el NUEVO mira adelante
        n.anterior  = a;                    // (2) el NUEVO mira atrás
        if (a == null) primero = n;         // (3) re-apuntar los VIEJOS
        else           a.siguiente = n;
        b.anterior = n;                     // (4)
        tamanio++;
    }

    /** Con el nodo ya ubicado, el desenganche es O(1): sólo 2 asignaciones. */
    public T eliminar(int i) {
        verificar(i);
        Nodo<T> n = nodoEn(i);
        desenganchar(n);
        tamanio--;
        return n.valor;
    }

    private void desenganchar(Nodo<T> n) {
        if (n.anterior == null) primero = n.siguiente;      // era el primero
        else                    n.anterior.siguiente = n.siguiente;

        if (n.siguiente == null) ultimo = n.anterior;       // era el último
        else                     n.siguiente.anterior = n.anterior;

        n.anterior = n.siguiente = null;    // que el nodo suelto no retenga la lista
    }

    public T obtener(int i) { verificar(i); return nodoEn(i).valor; }
    public int tamanio()    { return tamanio; }

    /** Arranca por el extremo MÁS CERCANO: a lo sumo n/2 saltos. */
    private Nodo<T> nodoEn(int i) {
        if (i < tamanio / 2) {
            Nodo<T> actual = primero;
            for (int k = 0; k < i; k++) actual = actual.siguiente;
            return actual;
        }
        Nodo<T> actual = ultimo;
        for (int k = tamanio - 1; k > i; k--) actual = actual.anterior;
        return actual;
    }

    private void verificar(int i) {
        if (i < 0 || i >= tamanio) throw new IndexOutOfBoundsException("índice " + i);
    }

PistaEs el caso de uso de la lista circular: la ronda no termina nunca hasta que vos la cortás. Cuidado con el conteo — si k = 1 se elimina a cada paso.
/** Problema de Josephus: n personas en ronda, se elimina cada k-ésima
 *  hasta que queda una. O(n · k) con lista circular. */
public static <T> T sobreviviente(ListaCircular<T> ronda, int k) {
    if (ronda.tamanio() == 0) {
        throw new IllegalArgumentException("la ronda está vacía");
    }
    if (k < 1) {
        throw new IllegalArgumentException("k debe ser >= 1");
    }

    int pos = 0;
    while (ronda.tamanio() > 1) {
        pos = (pos + k - 1) % ronda.tamanio();   // avanzar k−1 desde el actual
        ronda.eliminar(pos);
        // al eliminar, el siguiente ocupa la misma posición:
        // pos ya apunta al próximo, pero puede haberse pasado del final
        if (pos == ronda.tamanio()) pos = 0;
    }
    return ronda.obtener(0);
}

La versión sobre nodos, que deja ver por qué la lista circular es la estructura natural:

public static <T> T sobrevivienteConNodos(Nodo<T> cualquiera, int n, int k) {

    while (n > 1) {
        for (int i = 0; i < k - 2; i++) {    // parar en el ANTERIOR al que se va
            actual = actual.siguiente;
        }
        actual.siguiente = actual.siguiente.siguiente;   // saltear: eliminar
        actual = actual.siguiente;
        n--;
    }
    return actual.valor;

Por qué acá la lista circular gana de verdad

Con una lista común, cada vez que llegás al final tendrías que preguntar "¿me pasé? entonces volvé al principio". Con la circular ese caso especial no existe: el siguiente del último es el primero, y el bucle es uniforme.

/** Conjunto sobre una lista. INVARIANTE: nunca hay dos elementos equals. */
public class ConjuntoLista<T> {

    private final ListaSimplementeEnlazada<T> datos = new ListaSimplementeEnlazada<>();

    /** O(n): el costo está en verificar que no esté. */
    public boolean agregar(T x) {
        if (contiene(x)) {
            return false;            // ya estaba: se ignora (y avisa)
        }
        datos.agregar(x);
        return true;
    }

    /** O(n): búsqueda lineal. */
    public boolean contiene(T x) {
        return datos.indiceDe(x) != -1;
    }

    /** O(n). */
    public boolean eliminar(T x) {
        int i = datos.indiceDe(x);
        if (i == -1) return false;
        datos.eliminar(i);
        return true;
    }

    /** O(n · m): por cada elemento del otro, un agregar que es O(n). */
    public ConjuntoLista<T> union(ConjuntoLista<T> otro) {
        ConjuntoLista<T> r = new ConjuntoLista<>();
        for (int i = 0; i < this.tamanio(); i++) r.agregar(this.obtener(i));
        for (int i = 0; i < otro.tamanio(); i++) r.agregar(otro.obtener(i));
        return r;                    // los repetidos los filtra agregar
    }

    public ConjuntoLista<T> interseccion(ConjuntoLista<T> otro) {
        ConjuntoLista<T> r = new ConjuntoLista<>();
        for (int i = 0; i < this.tamanio(); i++) {
            T x = this.obtener(i);
            if (otro.contiene(x)) r.agregar(x);
        }
        return r;
    }

    public ConjuntoLista<T> diferencia(ConjuntoLista<T> otro) {
        ConjuntoLista<T> r = new ConjuntoLista<>();
        for (int i = 0; i < this.tamanio(); i++) {
            T x = this.obtener(i);
            if (!otro.contiene(x)) r.agregar(x);
        }
        return r;
    }

    public int tamanio()      { return datos.tamanio(); }
    public boolean estaVacio() { return tamanio() == 0; }
    T obtener(int i)          { return datos.obtener(i); }   // paquete: uso interno
}

obtener(i) NO es público. Un conjunto no tiene posiciones: exponer un índice rompería el TDA y dejaría al usuario creyendo que hay un orden garantizado. Pila<T> sobre nodos (Nodo con siguiente); test LIFO.

PistaEl tope tiene que ser el primer nodo, no el último: apilar y desapilar al principio de una lista enlazada son O(1) sin recorrer nada.
/** Pila LIFO sobre nodos. El tope es el PRIMER nodo: todo O(1) real,
 *  ni siquiera amortizado (no hay redimensión). */
public class Pila<T> {

    private static class Nodo<T> {
        final T valor;
        final Nodo<T> siguiente;
        Nodo(T valor, Nodo<T> siguiente) {
            this.valor = valor;
            this.siguiente = siguiente;
        }
    }

    private Nodo<T> tope;
    private int tamanio;

    /** O(1): el nodo nuevo pasa a ser el tope y apunta al viejo. */
    public void apilar(T x) {
        tope = new Nodo<>(x, tope);       // funciona igual si tope era null
        tamanio++;
    }

    /** O(1). */
    public T desapilar() {
        if (estaVacia()) {
            throw new NoSuchElementException("la pila está vacía");
        }
        T valor = tope.valor;
        tope = tope.siguiente;            // el viejo tope queda inalcanzable -> GC
        tamanio--;
        return valor;
    }

    /** O(1): mira sin sacar. */
    public T tope() {
        if (estaVacia()) {
            throw new NoSuchElementException("la pila está vacía");
        }
        return tope.valor;
    }

    public boolean estaVacia() { return tope == null; }
    public int tamanio()       { return tamanio; }
}
Por qué esta versión es más elegante que la del nivel medio

El constructor new Nodo<>(x, tope) hace todo el trabajo en una línea y sin ningún caso especial: si la pila estaba vacía, tope era null y el nodo nuevo queda apuntando a null, que es justo lo correcto. No hace falta el if (primero == null) que sí necesitaba la lista enlazada del ejercicio 2.

Comparación con la pila sobre vector (ejercicio 1 del nivel medio):

  • Sobre nodos: O(1) estricto — nunca hay una operación cara. A cambio, una referencia extra por elemento y un objeto más para el recolector.
  • Sobre vector: O(1) amortizado — casi siempre instantáneo, con picos de O(n) al redimensionar. A cambio, elementos contiguos (mejor caché) y menos memoria por elemento.

Si te importa que ninguna operación individual sea lenta (sistemas de tiempo real), va la enlazada. Si te importa el rendimiento promedio, gana el vector.

Los campos van final porque un nodo de pila nunca cambia una vez creado: apilar crea uno nuevo, desapilar descarta el de arriba. Nadie modifica los del medio.

Cola enlazada

Cola<T> sobre nodos con punteros a frente y fondo; test FIFO.

PistaEl borde crítico: cuando la cola se vacía, fondo tiene que volver a null. Si te olvidás, el próximo encolar engancha a un nodo fantasma.
/** Cola FIFO sobre nodos. Se encola por el fondo y se desencola por el
 *  frente: los dos punteros hacen que ambas sean O(1). */
public class Cola<T> {

    private static class Nodo<T> {
        final T valor;
        Nodo<T> siguiente;
        Nodo(T valor) { this.valor = valor; }
    }

    private Nodo<T> frente, fondo;
    private int tamanio;

    /** O(1). */
    public void encolar(T x) {
        Nodo<T> n = new Nodo<>(x);
        if (fondo == null) {
            frente = fondo = n;           // estaba vacía: es el único nodo
        } else {
            fondo.siguiente = n;          // engancha al final
            fondo = n;                    // y pasa a ser el nuevo fondo
        }
        tamanio++;
    }

    /** O(1). */
    public T desencolar() {
        if (estaVacia()) {
            throw new NoSuchElementException("la cola está vacía");
        }
        T valor = frente.valor;
        frente = frente.siguiente;
        if (frente == null) {
            fondo = null;                 // ← EL BORDE: quedó vacía
        }
        tamanio--;
        return valor;
    }

    public T frente() {
        if (estaVacia()) {
            throw new NoSuchElementException("la cola está vacía");
        }
        return frente.valor;
    }

    public boolean estaVacia() { return frente == null; }
    public int tamanio()       { return tamanio; }
}
El bug de este ejercicio, y es siempre el mismo

Si en desencolar te olvidás del if (frente == null) fondo = null;, pasa esto:

encolar(1)     frente → [1] ← fondo
desencolar()   frente = null,  pero fondo SIGUE apuntando al nodo del 1
encolar(2)     como fondo != null, hace fondo.siguiente = nodo(2)
               ...engancha el 2 a un nodo que ya no está en la cola,
               y frente sigue en null
desencolar()   ✗ dice que está vacía, pero tamanio == 1

La cola queda internamente inconsistente: tamanio dice una cosa y los punteros otra. Y sólo se manifiesta después de vaciarla y volver a usarla, que es un caso que muchos tests no cubren.

Por qué acá los nodos sí necesitan siguiente mutable (a diferencia de la pila): al encolar hay que modificar el nodo que ya estaba en el fondo para que apunte al nuevo. En la pila nunca se toca un nodo existente.

Invertir enlazada

Invertí una lista simplemente enlazada in place (re-enganchando); test.

PistaNecesitás tres punteros a la vez: anterior, actual y siguiente. Antes de dar vuelta una flecha, guardá adónde apuntaba — si no, perdés el resto.
/** Invierte in place re-enganchando las referencias.
 *  O(n) tiempo, O(1) espacio: no se crea ningún nodo. */
public void invertir() {
    Nodo<T> anterior = null;
    Nodo<T> actual = primero;

    while (actual != null) {
        Nodo<T> siguiente = actual.siguiente;   // (1) GUARDAR antes de romper
        actual.siguiente = anterior;            // (2) dar vuelta la flecha
        anterior = actual;                      // (3) avanzar
        actual = siguiente;                     // (4)
    }

    Nodo<T> viejoPrimero = primero;
    primero = anterior;                         // anterior quedó en el último nodo
    ultimo = viejoPrimero;                      // ¡actualizar los DOS punteros!
}

Seguí el estado con [a → b → c]:

inicio    anterior=null   actual=a        null   a → b → c
vuelta 1  siguiente=b, a.siguiente=null   null ← a   b → c
          anterior=a, actual=b
vuelta 2  siguiente=c, b.siguiente=a      null ← a ← b   c → null
          anterior=b, actual=c
vuelta 3  siguiente=null, c.siguiente=b   null ← a ← b ← c
          anterior=c, actual=null
fin       primero = c,  ultimo = a        [c → b → a]
Por qué hacen falta exactamente tres punteros

La línea actual.siguiente = anterior destruye la única referencia que tenías hacia adelante. Si no guardaste siguiente antes, en la próxima vuelta no hay forma de llegar al resto de la lista: queda inalcanzable y el GC se la lleva.

Es la misma regla del laboratorio 3 y del ejercicio 2: leé lo que necesitás antes de sobrescribirlo. Acá se ve en su forma más pura.

No te olvides de ultimo. Es el error que sobrevive a los tests fáciles: la lista se recorre bien, obtener anda, pero el próximo agregar engancha el nodo en el lugar equivocado.

La versión recursiva, para comparar:

// T(n) = T(n−1) + O(1)  ->  O(n) tiempo, pero O(n) de STACK
private Nodo<T> invertirDesde(Nodo<T> n) {
    if (n == null || n.siguiente == null) return n;
    Nodo<T> nuevoPrimero = invertirDesde(n.siguiente);
    n.siguiente.siguiente = n;        // el siguiente ahora apunta para atrás
    n.siguiente = null;
    return nuevoPrimero;
}

Misma complejidad temporal, pero usa O(n) de pila de llamadas: con un millón de nodos tira StackOverflowError. La iterativa usa O(1).

Nodo del medio

Encontrá el nodo del medio con la técnica de los dos punteros (lento/rápido); test.

PistaUn puntero avanza de a 1 y el otro de a 2. Cuando el rápido llega al final, el lento está justo en el medio. Decidí qué devolver con largo par.
/** Técnica de la liebre y la tortuga. O(n) tiempo, O(1) espacio,
 *  y en UNA sola pasada (sin conocer el tamaño de antemano).
 *  Con largo par devuelve el SEGUNDO del medio. */
public T nodoDelMedio() {
    if (primero == null) {
        throw new NoSuchElementException("la lista está vacía");
    }
    Nodo<T> lento = primero;
    Nodo<T> rapido = primero;

    while (rapido != null && rapido.siguiente != null) {
        lento = lento.siguiente;            // avanza 1
        rapido = rapido.siguiente.siguiente; // avanza 2
    }
    return lento.valor;
}

Con [a, b, c, d, e]:

inicio    lento=a   rapido=a
vuelta 1  lento=b   rapido=c
vuelta 2  lento=c   rapido=e      (e.siguiente == null → corta)
resultado lento=c   ✓ el del medio
Por qué no recorrer dos veces

La solución obvia sería: contar los nodos (una pasada) y después avanzar n/2 (otra pasada). Es O(n) igual, y perfectamente válida.

La técnica de los dos punteros lo hace en una sola pasada, sin necesidad de conocer el tamaño. Eso importa cuando no podés recorrer dos veces: un stream que llega de a poco, un archivo enorme, o una estructura que no expone su tamaño.

La misma idea resuelve otros dos problemas clásicos:

  • Detectar un ciclo (algoritmo de Floyd): si hay ciclo, el rápido alcanza al lento; si no, llega a null.
  • El k-ésimo desde el final: adelantás el rápido k posiciones y después los movés juntos.
La condición del while, en ese orden

rapido != null && rapido.siguiente != null. Si las invirtieras, evaluarías rapido.siguiente con rapido en null y tendrías un NullPointerException. El && es cortocircuito: si la primera es falsa, no evalúa la segunda. Por eso el orden no es opcional.

Con largo par hay dos candidatos a "medio". Esta versión devuelve el segundo (con [a,b,c,d] da c). Para el primero, la condición sería rapido.siguiente != null && rapido.siguiente.siguiente != null. Las dos son válidas: hay que elegir una, documentarla y testearla.

Un TDA, dos implementaciones

Interfaz Lista<T> con VectorDinamico y ListaEnlazada; un mismo test verifica que ambas se comportan igual.

PistaEl test tiene que estar escrito una sola vez contra la interfaz. Con JUnit 5, @ParameterizedTest con @MethodSource te lo corre con las dos implementaciones.

Este ejercicio cierra la unidad y cierra también la Unidad 3: el TDA es el contrato, y quien lo usa no debe notar la diferencia.

public interface Lista<T> {
    void agregar(T x);
    void insertar(int i, T x);
    T    obtener(int i);
    T    eliminar(int i);
    int  indiceDe(T x);
    int  tamanio();

Las dos implementaciones son las de los ejercicios 1 y 2, declarando implements Lista<T>. Y el test, escrito una sola vez:

class ListaContratoTest {

    /** Las implementaciones a probar. Agregar una nueva es agregar una línea. */
    static Stream<Arguments> implementaciones() {
        return Stream.of(
            Arguments.of(named("VectorDinamico", (Supplier<Lista<Integer>>) VectorDinamico::new)),
            Arguments.of(named("ListaEnlazada",  (Supplier<Lista<Integer>>) ListaEnlazada::new))
        );
    }

    @ParameterizedTest @MethodSource("implementaciones")
    void agregarYObtener(Supplier<Lista<Integer>> fabrica) {
        Lista<Integer> l = fabrica.get();
        l.agregar(1); l.agregar(2); l.agregar(3);
        assertEquals(3, l.tamanio());
        assertEquals(1, l.obtener(0));
        assertEquals(3, l.obtener(2));
    }

    @ParameterizedTest @MethodSource("implementaciones")
    void insertarEnTodasLasPosiciones(Supplier<Lista<Integer>> fabrica) {
        for (int pos = 0; pos <= 3; pos++) {
            Lista<Integer> l = fabrica.get();
            for (int i = 1; i <= 3; i++) l.agregar(i);
            l.insertar(pos, 99);
            assertEquals(99, l.obtener(pos), "falla insertando en " + pos);
            assertEquals(4, l.tamanio());
        }
    }

    @ParameterizedTest @MethodSource("implementaciones")
    void eliminarDevuelveYAchica(Supplier<Lista<Integer>> fabrica) {
        Lista<Integer> l = fabrica.get();
        for (int i = 1; i <= 3; i++) l.agregar(i);
        assertEquals(2, l.eliminar(1));
        assertEquals(2, l.tamanio());
        assertEquals(3, l.obtener(1));      // el 3 se corrió a la posición 1
    }

    @ParameterizedTest @MethodSource("implementaciones")
    void indicesInvalidosLanzan(Supplier<Lista<Integer>> fabrica) {
        Lista<Integer> l = fabrica.get();
        l.agregar(1);
        assertThrows(IndexOutOfBoundsException.class, () -> l.obtener(1));
        assertThrows(IndexOutOfBoundsException.class, () -> l.obtener(-1));
        assertThrows(IndexOutOfBoundsException.class, () -> l.eliminar(5));
        assertThrows(IndexOutOfBoundsException.class, () -> l.insertar(9, 1));
    }

    @ParameterizedTest @MethodSource("implementaciones")
    void seComportanIgualQueUnArrayList(Supplier<Lista<Integer>> fabrica) {
        Lista<Integer> mia = fabrica.get();
        List<Integer> oraculo = new ArrayList<>();
        Random r = new Random(42);          // semilla fija: reproducible

        for (int op = 0; op < 1000; op++) {
            if (oraculo.isEmpty() || r.nextInt(3) > 0) {
                int i = r.nextInt(oraculo.size() + 1), v = r.nextInt(50);
                mia.insertar(i, v); oraculo.add(i, v);
            } else {
                int i = r.nextInt(oraculo.size());
                assertEquals(oraculo.remove(i), mia.eliminar(i));
            }
            assertEquals(oraculo.size(), mia.tamanio());
            for (int i = 0; i < oraculo.size(); i++) {
                assertEquals(oraculo.get(i), mia.obtener(i),
                             "difieren en " + i + " tras la operación " + op);
            }
        }
    }
}
Lo que este ejercicio demuestra

El test no menciona arreglos ni nodos. Habla sólo de agregar, obtener, eliminar — el contrato. Por eso puede correrse contra cualquier implementación presente o futura: agregar una tercera (una lista circular, por ejemplo) es agregar una línea a implementaciones() y heredás todos los tests.

Eso es exactamente lo que promete un TDA. Si un test tuviera que cambiar según la implementación, sería la señal de que el contrato está mal definido o de que se filtró un detalle interno.

Lo que el test NO puede verificar es la complejidad. Las dos pasan todo, pero obtener(i) es O(1) en una y O(n) en la otra. El contrato garantiza qué hace cada operación, no cuánto cuesta — y por eso la tabla de complejidades de 5.6 es información que el usuario necesita además de la interfaz para elegir bien.
