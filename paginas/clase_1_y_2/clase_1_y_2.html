1B.1Un poco de historia: por qué Java

Para entender Java conviene saber de dónde viene. A principios de los años 90, un equipo de Sun Microsystems liderado por James Gosling trabajaba en un lenguaje para electrodomésticos inteligentes (el “Green Project”). Ese lenguaje se llamó primero Oak. En 1995 se presentó públicamente como Java, y su gran promesa cambió las reglas: “Write Once, Run Anywhere” (escribí una vez, ejecutá en cualquier lado). En una época en la que cada programa había que recompilarlo para cada sistema, poder escribir un programa y correrlo igual en Windows, Mac o Unix fue una pequeña revolución. Los applets de Java, que corrían dentro del navegador, popularizaron el lenguaje casi de inmediato.

Con los años Java maduró: en 2004 (Java 5) llegaron los genéricos y los enum; en 2014 (Java 8), las lambdas y los streams, otro antes y después. En 2010 Oracle compró Sun, y desde 2017 hay una versión nueva cada seis meses, con versiones LTS (Long-Term Support, soporte de largo plazo) cada dos años. Nosotros usamos Java 25, la LTS publicada en septiembre de 2025.

¿Y hoy? Java sigue siendo uno de los lenguajes más elegidos del mundo. En el índice TIOBE, que mide la popularidad de los lenguajes, Java se mantiene entre los primeros puestos, con alrededor del 8–9 % de participación, peleando el podio con Python, C, C++ y C#. Está en el corazón de miles de sistemas bancarios, de gobierno y de empresas, y es la base histórica del desarrollo Android.

Al pie (del apunte)

Según el índice TIOBE, que mide la popularidad de los lenguajes, Java se mantiene entre los primeros puestos: en la edición de agosto de 2026 está 4.º con 8,25 %, a sólo 0,37 puntos de C++ — peleando el podio con Python, C y C++. Está en el corazón de miles de sistemas bancarios, de gobierno y de empresas, y es la base histórica del desarrollo Android. El “lenguaje del año 2025” fue C#.

El índice mide popularidad —búsquedas, cursos, avisos laborales—, no calidad; sirve como termómetro de qué se usa en la industria. Cuando leas esto el número exacto habrá cambiado; lo que no cambia hace 25 años es que Java está en los primeros puestos.

Idea clave

Java combina tres cosas que explican su longevidad: es portable (corre en cualquier máquina con una JVM), es robusto y tipado (muchos errores se detectan al compilar, no en producción) y tiene un ecosistema gigante de librerías y herramientas. Por eso sigue vigente 30 años después.

1B.2¿Cómo se ejecuta un programa Java?

Java es un lenguaje compilado a un formato intermedio que luego ejecuta una máquina virtual. Esto lo diferencia de lenguajes como C, que compilan directamente a instrucciones del procesador.

Cuando escribís un archivo Hola.java y lo compilás con javac, no obtenés un ejecutable para tu procesador, sino bytecode: un archivo Hola.class con instrucciones para una computadora “imaginaria” llamada JVM (Java Virtual Machine). Al correr el programa, la JVM lee ese bytecode y lo traduce a instrucciones reales de tu CPU, optimizando sobre la marcha con el compilador JIT (Just-In-Time).

Acá está la clave de “Write Once, Run Anywhere”: el mismo .class corre igual en cualquier sistema, porque lo que cambia de una máquina a otra es la JVM, no tu programa.

Para escribir un .java alcanza con un editor de texto, pero para compilarlo y ejecutarlo necesitás el JDK (Java Development Kit): incluye el compilador javac, herramientas varias y, adentro, el entorno de ejecución (JRE) con la JVM y las bibliotecas estándar. Cuando instales el JDK 25, verificá la versión en una terminal:

java -version       // muestra la versión de la JVM
javac -version      // muestra la versión del compilador

1B.4Tu primer programa

public class HolaCB100 {

    // El método main es SIEMPRE el punto de arranque del programa.
    public static void main(String[] args) {

Con precisión: un char es una unidad UTF-16 de 16 bits. Para los caracteres habituales (letras, dígitos, símbolos comunes) equivale a “un carácter”; algunos símbolos fuera de ese rango (emojis, escrituras históricas) ocupan dos char. Para esta materia, la idea “un char = un carácter” alcanza.

var pi = 3.14;                // ... infiere double
Idea clave

var no convierte a Java en un lenguaje dinámico: el tipo se fija al compilar y no cambia. Sólo te ahorra repetirlo cuando es evidente por el valor asignado.

1B.6.1La palabra var: inferencia de tipos (con criterio)

Desde Java 10 existe var: le deja al compilador el trabajo de inferir el tipo a partir del valor de la derecha, sin dejar de ser tipado:

var mensaje = "Hola";            // el compilador infiere String
var pi = 3.14;                   // ... infiere double
var texto = new StringBuilder(); // ... infiere StringBuilder
Idea clave

var no convierte a Java en un lenguaje dinámico: el tipo se fija al compilar y no cambia nunca — var mensaje = "Hola"; mensaje = 42; no compila. Es exactamente lo mismo que escribir el tipo, ahorrándote repetirlo cuando ya es evidente.

Buenas prácticas con var (las mismas que vas a encontrar en la industria):

  • Usalo cuando el tipo se ve a simple vista del lado derecho: var texto = new StringBuilder(), var archivo = Path.of("datos.txt"). Ahí repetir el tipo es puro ruido.
  • Evitalo cuando el tipo NO se ve: en var resultado = procesar(datos); el lector no sabe qué es resultado sin ir a mirar la firma de procesar. Con double resultado = procesar(datos); el renglón se explica solo.
  • Sólo funciona en variables locales (adentro de un método): no existe para atributos, parámetros ni tipos de retorno — ahí el tipo explícito es obligatorio, porque es parte del contrato.
  • Mientras aprendés, preferí el tipo explícito: escribir String, int o double[] te obliga a saber qué tenés entre manos. En este apunte vas a ver tipos explícitos en los ejemplos que enseñan un concepto, y var sólo donde el tipo es obvio y repetirlo distrae (p. ej. try (var sc = new Scanner(...))).
  • La regla de oro: var está para quitar ruido, nunca para ocultar información. Si al leer el renglón dudás del tipo, escribilo.

1B.7Rangos, conversiones y wrappers

Cada tipo primitivo tiene un rango de valores. Si te pasás del máximo, el valor “da la vuelta” (overflow): no da error, pero el resultado es incorrecto. Las clases envoltorio exponen esos límites (Integer.MAX_VALUE, etc.).

System.out.println(Integer.MIN_VALUE + " .. " + Integer.MAX_VALUE);
int max = Integer.MAX_VALUE;
System.out.println(max + 1);   // desborda a -2147483648 (¡negativo!)

Conversiones (casting). Pasar de un tipo más chico a uno más grande es automático (widening); al revés hay que pedirlo explícitamente (narrowing) y puede perder información:

double d = 9.99;
int truncado = (int) d;       // 9   (se pierde el decimal)
long l = truncado;            // automático (int cabe en long)

Wrappers y autoboxing. Cada primitivo tiene una clase envoltorio: int → Integer, double → Double, boolean → Boolean, etc. Java convierte entre ambos automáticamente (autoboxing / unboxing). Los wrappers también sirven para convertir desde y hacia texto.

Integer boxed = 42;                    // autoboxing: int -> Integer
int back = boxed;                      // unboxing:   Integer -> int

int n = Integer.parseInt("123");       // texto -> número
double x = Double.parseDouble("3.14");
String s = Integer.toString(255);      // número -> texto

Cuando necesitás números muy grandes o cálculos con decimales exactos (por ejemplo, dinero), están BigInteger y BigDecimal, que no tienen los límites ni los errores de redondeo de los primitivos:

BigInteger factorial = BigInteger.ONE;

Error común

1B.11.1Condicionales: if y switch

El if / else if / else funciona como esperás:

int nota = 7;
if (nota >= 8) {
    System.out.println("distinguido");
} else if (nota >= 4) {
    System.out.println("aprobado");
} else {
    System.out.println("insuficiente");
}

Cuando hay que elegir entre muchos valores, el switch expression (moderno) es más claro: devuelve un valor, usa flechas ->, no necesita break y el compilador te obliga a cubrir todos los casos.

String dia = "L";
String tipo = switch (dia) {
    case "L", "M", "X", "J", "V" -> "día hábil";
    case "S", "D" -> "fin de semana";
    default -> "desconocido";
};
Idea clave

Regla de estilo de la cátedra: las llaves van SIEMPRE, aunque el cuerpo sea una sola línea. if (nota >= 4) { aprobado = true; } y nunca if (nota >= 4) aprobado = true;. Las llaves marcan sin ambigüedad dónde empieza y dónde termina cada bloque, y evitan el clásico error de “agregué una segunda línea al if y quedó afuera”. Todo el código del apunte y del repositorio sigue esta regla — y se espera en TPs, parciales y finales.

1B.11.2Ciclos: for, while, do-while

El for clásico tiene tres partes: inicialización, condición y actualización.

int suma = 0;
for (int i = 1; i <= 5; i++) {
    suma += i;               // 1 + 2 + 3 + 4 + 5 = 15
}

El while repite mientras la condición sea verdadera:

int cuenta = 3;
while (cuenta > 0) {
    System.out.print(cuenta + " ");   // imprime: 3 2 1
    cuenta--;
}

El do-while es su hermano menos usado pero con una diferencia importante: ejecuta el cuerpo al menos una vez, porque chequea la condición después. Es la elección natural cuando algo debe ocurrir sí o sí la primera vez, como mostrar un menú y pedir una opción:

int opcion;
do {
    System.out.println("1) Jugar   2) Puntajes   3) Salir");
    opcion = scanner.nextInt();       // se pide AL MENOS una vez
} while (opcion != 3);                // repite hasta que elija salir

Dentro de cualquier ciclo hay dos “controles de salto”: break corta el ciclo por completo, y continue abandona la vuelta actual y pasa a la siguiente:

int[] datos = {7, -3, 12, 0, 5};
for (int d : datos) {
    if (d == 0) break;        // un 0 corta la búsqueda: no mira el 5
    if (d < 0)  continue;     // saltea los negativos: no imprime el -3
    System.out.print(d + " ");// imprime: 7 12
}

Usalos con moderación: un break claro (encontré lo que buscaba, corto) mejora el código; muchos saltos enredados lo vuelven ilegible.

1B.11.3Arreglos y for-each

Un arreglo guarda muchos valores del mismo tipo en celdas contiguas y numeradas. Es la estructura más básica de todas —y la base de varias que vamos a construir—, así que vale la pena mirarla de cerca:

Tres reglas para no tropezar nunca: (1) los índices arrancan en 0, así que la primera celda es numeros[0] y la última numeros[length - 1]; (2) el tamaño es fijo: se decide al crear el arreglo y no cambia (para “crecer” hay que crear otro y copiar — exactamente lo que hará el vector dinámico de la Unidad 5); y (3) acceder fuera del rango (numeros[6] en un arreglo de 6) lanza ArrayIndexOutOfBoundsException al ejecutar.

int[] numeros = {4, 8, 15, 16, 23, 42};
numeros[0];                    // 4      (la primera celda)
numeros[numeros.length - 1];   // 42     (la última)
numeros[3] = 99;               // también se puede escribir

int[] ceros = new int[5];      // {0,0,0,0,0}: se inicializa con "ceros"

Para recorrerlo sin manejar índices, se usa el for-each, que visita cada celda en orden:

int total = 0;
for (int n : numeros) {        // "para cada n en numeros"
    total += n;
}
System.out.println(total + " (largo " + numeros.length + ")");

Un arreglo también puede contener arreglos: es la forma de representar una matriz (tabla de filas y columnas). Se accede con dos índices, primero la fila y después la columna:

int[][] tablero = { {1, 2}, {3, 4} };     // 2 filas x 2 columnas
tablero[1][0];                            // 3   (fila 1, columna 0)

for (int f = 0; f < tablero.length; f++)              // recorrer una matriz:
    for (int c = 0; c < tablero[f].length; c++)       // un for por dimensión
        System.out.print(tablero[f][c] + " ");        // 1 2 3 4

1B.12Métodos

Un método (función) agrupa un cálculo bajo un nombre. Se declara con un tipo de retorno, un nombre y sus parámetros. Java permite sobrecarga (mismo nombre, distintos parámetros) y varargs (cantidad variable de argumentos).

static int cuadrado(int x) {        // recibe un int, devuelve un int
    return x * x;
}

static double area(double lado) { return lado * lado; }                 // sobrecarga
static double area(double base, double altura) { return base * altura; }

static int sumar(int... valores) {  // varargs: sumar(1,2,3,4)
    int acumulado = 0;
    for (int v : valores) acumulado += v;
    return acumulado;
}

1B.13Una clase propia (mínima)

Hasta acá usamos clases con métodos static. Pero la idea central de Java es crear objetos: unidades que combinan estado (datos, en campos) y comportamiento (métodos). Veamos la sintaxis mínima de una clase con estado. Para no adelantarnos, la dejamos con todo público y sin constructor; en la Unidad 3 vamos a ver por qué eso no es lo ideal y cómo se modela bien.

public class Rectangulo {

    public double base;        // estado: los datos del objeto
    public double altura;

    public double area() {              // comportamiento: qué sabe hacer
        return base * altura;
    }

    public double perimetro() {
        return 2 * (base + altura);
    }
}

Se usa creando un objeto con new y accediendo a sus campos y métodos con el punto:

Rectangulo r = new Rectangulo();   // se crea el objeto
r.base = 3;                        // se asignan sus campos
r.altura = 4;
System.out.println(r.area());      // 12.0

1B.14Enumerados: enum

Un enum define un tipo con un conjunto fijo y conocido de valores. Es más seguro que usar enteros o cadenas “mágicas”, porque el compilador conoce todos los casos posibles.

public enum DiaDeSemana {
    LUNES, MARTES, MIERCOLES, JUEVES, VIERNES, SABADO, DOMINGO;

    public boolean esFinDeSemana() {
        return this == SABADO || this == DOMINGO;
    }
}

Y así se usa: los valores se nombran como constantes, se pueden comparar con == (son únicos), recorrer con values() y usar en un switch que el compilador verifica completo:

DiaDeSemana hoy = DiaDeSemana.SABADO;
System.out.println(hoy);                   // SABADO
System.out.println(hoy.esFinDeSemana());   // true

for (DiaDeSemana d : DiaDeSemana.values()) {      // todos los valores, en orden
    System.out.print(d + ":" + (d.esFinDeSemana() ? "finde " : "hábil "));
}

String plan = switch (hoy) {               // switch sobre enum: cubre los casos
    case SABADO, DOMINGO -> "descansar";
    default              -> "cursar CB100";
};

1B.15Modelar datos con record

Muchas veces necesitás un objeto que sólo agrupa datos y no cambia una vez creado (inmutable). Hoy se hace con un record: en una línea, Java genera el constructor, los accesores y los métodos equals, hashCode y toString.

public record Temperatura(double celsius) {

    public Temperatura {                       // constructor compacto: valida
        if (celsius < -273.15) {
            throw new IllegalArgumentException("Bajo el cero absoluto: " + celsius);
        }
    }

    public String clasificar() {
        return switch (franja()) {
            case 0 -> "helado";   case 1 -> "frío";     case 2 -> "templado";
            case 3 -> "cálido";   default -> "caluroso";
        };
    }

    private int franja() {
        if (celsius < 0)  return 0;    if (celsius < 12) return 1;
        if (celsius < 22) return 2;    if (celsius < 30) return 3;
        return 4;
    }
}

1B.15.1Varios atributos y sus accesores

Un record puede tener todos los componentes que necesites, y por cada uno Java genera un accesor: un método sin parámetros con el mismo nombre del componente. Mirá FichaDeAlumno (del repo), con tres atributos:

public record FichaDeAlumno(String nombre, int padron, double promedio) {


    public FichaDeAlumno {                          // constructor compacto: valida TODO
        if (nombre == null || nombre.isBlank()) {
            throw new IllegalArgumentException("el nombre no puede estar vacío");
        }
        if (padron <= 0) {
            throw new IllegalArgumentException("el padrón debe ser positivo: " + padron);
        }
        if (promedio < 0 || promedio > 10) {
            throw new IllegalArgumentException("el promedio va de 0 a 10: " + promedio);
        }
    }


    public boolean promociona() {                   // los métodos combinan los atributos
        return promedio >= 7.0;
    }
}

Y así se leen los atributos — creando fichas y llamando a los accesores:

FichaDeAlumno ana = new FichaDeAlumno("Ana Gómez", 111234, 8.5);
FichaDeAlumno beto = new FichaDeAlumno("Beto Díaz", 109876, 6.1);


System.out.println(ana.nombre());          // Ana Gómez
System.out.println(ana.padron());          // 111234
System.out.println(ana.promedio());        // 8.5


// los accesores se usan como cualquier expresión:
System.out.println(ana.nombre() + " (" + ana.padron() + ")");     // Ana Gómez (111234)
double diferencia = ana.promedio() - beto.promedio();             // 2.4000000000000004


// toString, equals y hashCode vienen gratis:
System.out.println(beto);           // FichaDeAlumno[nombre=Beto Díaz, padron=109876, promedio=6.1]
FichaDeAlumno copia = new FichaDeAlumno("Ana Gómez", 111234, 8.5);
System.out.println(ana.equals(copia));     // true: igualdad por CONTENIDO, no por referencia
Idea clave

Tres cosas para fijar de los record: (1) el accesor se llama igual que el componente — promedio(), sin el prefijo get de las clases tradicionales; (2) equals compara por contenido: dos fichas con los mismos datos son iguales aunque sean objetos distintos; (3) no hay setters — un record es inmutable, y “modificarlo” significa crear otro (ana.conPromedio(9.0) devuelve una ficha nueva; ana queda intacta). Corré el main de FichaDeAlumno y verificá las tres.

1B.16Expresiones lambda

Una lambda es una función anónima y breve. Sirve para pasar “un comportamiento” como si fuera un dato. Una lambda implementa una interfaz funcional (una interfaz con un solo método). La flecha -> separa los parámetros del cuerpo.

interface Operacion { int aplicar(int a, int b); }

Operacion suma = (a, b) -> a + b;
Operacion producto = (a, b) -> a * b;
System.out.println(suma.aplicar(3, 4));    // 7

// La biblioteca trae interfaces funcionales listas para usar:
Predicate<Integer> esPar = n -> n % 2 == 0;
Function<String, Integer> largo = s -> s.length();
Idea clave

Por ahora nos quedamos con la idea: una lambda es una función corta que podemos guardar y pasar. Su uso más potente, junto con los streams, lo vamos a ver en detalle en la unidad de estructuras lineales.

1B.17Manejo de excepciones

Un programa robusto reacciona ante situaciones excepcionales: un archivo que no existe, una división por cero, un dato inválido. Java modela esto con excepciones: cuando algo excepcional ocurre, se lanza (throw) un objeto que describe el problema; en algún lugar del programa, alguien lo captura (try/catch) y decide qué hacer. Lo interesante —y lo que vamos a mirar con lupa— es lo que pasa en el medio: entre el throw y el catch hay un viaje.

1B.17.1El viaje de una excepción por la pila de llamadas

Cada vez que un método llama a otro, la JVM apila un marco con sus datos; cuando el método termina, su marco se desapila y la ejecución vuelve a donde estaba. Ahora mirá esta cadena de tres métodos —main llama a procesarPedido, que llama a validarCantidad, que valida y lanza— con println numerados para espiar qué se ejecuta:

public class ViajeDeUnaExcepcion {

    public static void main(String[] args) {
        System.out.println("(1) main: por llamar a procesarPedido(-3)");
        try {
            procesarPedido(-3);
            System.out.println("(X) main: NO se ejecuta (la llamada terminó en excepción)");
        } catch (IllegalArgumentException e) {
            System.out.println("(5) main: ¡capturada! mensaje = " + e.getMessage());
        }
        System.out.println("(6) main: el programa SIGUE con normalidad");
    }

    static void procesarPedido(int cantidad) {
        System.out.println("(2) procesarPedido: por llamar a validarCantidad");
        validarCantidad(cantidad);
        System.out.println("(X) procesarPedido: NO se ejecuta (la excepción pasó de largo)");
    }

    static void validarCantidad(int cantidad) {
        System.out.println("(3) validarCantidad: verificando " + cantidad);
        if (cantidad <= 0) {
            System.out.println("(4) validarCantidad: cantidad inválida, LANZO");
            throw new IllegalArgumentException("la cantidad debe ser positiva y es " + cantidad);
        }
        System.out.println("(X) validarCantidad: NO se ejecuta (está después del throw)");
    }
}

La salida real (corré ViajeDeUnaExcepcion en el repo):

(1) main: por llamar a procesarPedido(-3)
(2) procesarPedido: por llamar a validarCantidad
(3) validarCantidad: verificando -3
(4) validarCantidad: cantidad inválida, LANZO
(5) main: ¡capturada! mensaje = la cantidad debe ser positiva y es -3
(6) main: el programa SIGUE con normalidad

Fijate qué no está en la salida: ninguna de las tres líneas marcadas (X). El throw interrumpe validarCantidad en el acto (lo que está después del throw no corre), la excepción vuelve a procesarPedido —que tampoco termina: la línea que seguía a la llamada se saltea— y sigue bajando hasta que encuentra el catch de main. Ahí el viaje termina y el programa continúa.

Idea clave

Una excepción desapila la pila de llamadas buscando el primer catch compatible. En ese viaje no se ejecuta: (a) lo que está después del throw en el método que lanzó, y (b) lo que está después de la llamada en cada método intermedio que no la captura. Por eso una validación que lanza al principio de un método garantiza que el resto del método sólo corre con datos sanos — es el patrón que usamos en todos los TDA del curso.

1B.17.3try, varios catch, finally

La forma completa de la estructura tiene tres piezas: el try (el bloque vigilado), uno o más catch (qué hacer con cada tipo de problema) y un finally opcional (lo que debe pasar siempre, haya o no excepción: cerrar, devolver, limpiar).

Error común

Cuando encadenás varios catch, ordenálos del más específico al más general. Si ponés catch (Exception e) primero, captura todo y los catch siguientes se vuelven inalcanzables: el código no compila. Una excepción hija siempre va antes que su clase padre — en el integrador de abajo, NumberFormatException (hija) va antes que IllegalArgumentException (padre).

Las que descienden de Exception (pero no de RuntimeException) son chequeadas: si un método puede lanzarlas, debe declararlo con throws en su firma, y quien lo llame está obligado por el compilador a capturarla o a declararla a su vez. Es un contrato visible: “llamarme implica hacerse cargo de esto”.

Y podés definir excepciones propias de tu dominio: una clase que extiende RuntimeException (no chequeada) o Exception (chequeada), con un buen mensaje y, como cualquier objeto, los datos que le quieras cargar:

/** Propia y CHEQUEADA: quien llame a extraer debe hacerse cargo. */
public class SaldoInsuficienteException extends Exception {

    private final int faltante;

    public SaldoInsuficienteException(int montoPedido, int saldoDisponible) {
        super("pediste $" + montoPedido + " pero el saldo es $" + saldoDisponible);
        this.faltante = montoPedido - saldoDisponible;
    }

    public int faltante() {
        return faltante;
    }
}

Definir una excepción propia hace los errores más claros:

public class DivisionPorCeroException extends RuntimeException {
    public DivisionPorCeroException(int dividendo) {
        super("intento de dividir " + dividendo + " por cero");
    }
}

1B.17.5Ejemplo integrador: el cajero automático

Todos los casos juntos, en CajeroAutomatico (corrélo del repo): dos try anidados, excepciones del sistema y una propia chequeada, un throw dentro del try, varios catch bien ordenados y un finally inquebrantable.

/** Puede fallar de dos maneras: monto absurdo o saldo que no alcanza. */
public void extraer(int monto) throws SaldoInsuficienteException {
    System.out.println("   extraer: piden $" + monto + " (saldo $" + saldo + ")");
    if (monto <= 0) {
        throw new IllegalArgumentException("el monto debe ser positivo y es " + monto);
    }
    if (monto > saldo) {
        throw new SaldoInsuficienteException(monto, saldo);
    }
    saldo -= monto;
    System.out.println("   extraer: entregado, saldo restante $" + saldo);
}


/** Una operación completa del cajero. */
public void atender(String textoDelMonto) {
    System.out.println("atender(\"" + textoDelMonto + "\")");
    try {                                                       // ---- try EXTERNO
        int monto = interpretarMonto(textoDelMonto);            // parseInt puede explotar
        try {                                                   // ---- try INTERNO
            extraer(monto);                                     // throw DENTRO del try
            System.out.println("   operación exitosa");
        } catch (SaldoInsuficienteException e) {
            // lo esperable del negocio se resuelve acá, cerca
            System.out.println("   no alcanza: " + e.getMessage()
                      + " (faltan $" + e.faltante() + ")");
        }
        System.out.println("   fin del camino con monto numérico");
    } catch (NumberFormatException e) {
        // PRIMERO la específica (es hija de IllegalArgumentException)
        System.out.println("   eso no es un número (" + e.getMessage() + ")");
    } catch (IllegalArgumentException e) {
        // el try interno NO la capturaba: siguió viajando hasta acá
        System.out.println("   monto inválido: " + e.getMessage());
    } finally {
        System.out.println("   finally: devolver la tarjeta (SIEMPRE)");
    }
}

El main atiende cuatro operaciones —una por caso— y esta es la salida real, para leer con el dedo en el código:

  interpretarMonto: entendí 300

  operación exitosa
  fin del camino con monto numérico
  finally: devolver la tarjeta (SIEMPRE)

  interpretarMonto: entendí 5000
  extraer: piden $5000 (saldo $700)
  no alcanza: pediste $5000 pero el saldo es $700 (faltan $4300)

  interpretarMonto: leyendo "-50"

Releé el tercer caso, que es el fino: extraer lanza IllegalArgumentException dentro del try interno, pero ese try sólo sabe capturar SaldoInsuficienteException — así que la excepción sale del try interno (salteando "operación exitosa" y "fin del camino...") y recién la atrapa el catch del externo. Dos redes: la de adentro para lo esperable del negocio, la de afuera para el resto. Y el finally imprimió las cuatro veces: con éxito, con captura interna, con captura externa y con explosión temprana.

Error común

Errores clásicos con excepciones:

  • El catch vacío (catch (Exception e) { }): la excepción desaparece sin dejar rastro y el bug se vuelve invisible. Como mínimo, mostrala.
  • Capturar Exception “por las dudas”: atrapa también lo que no sabés manejar y esconde errores de programación. Capturá los tipos que sí sabés resolver.
  • Usar excepciones para el flujo normal: si el caso pasa siempre (fin de un ciclo, opción del menú), es un if, no un throw — las excepciones son para lo excepcional.
  • Olvidar el orden específico → general en los catch (no compila).
  • Poner return adentro de un finally: pisa silenciosamente el resultado (o la excepción) del try. No lo hagas nunca.

1B.20Archivos

Hasta acá, todos los datos de tus programas viven en la memoria y desaparecen al terminar. Para que sobrevivan hay que llevarlos al disco: eso es trabajar con archivos. El ciclo completo es simple: tu programa nombra el archivo con un Path, escribe con Files.writeString, y más tarde (incluso en otra ejecución) lee con Files.readString o readAllLines:

Para leer y escribir archivos de texto, la forma más simple es la clase utilitaria Files:

Path archivo = Path.of("datos.txt");

}   // el Scanner se cierra solo al salir del try

1B.21Validaciones

Programar “a la defensiva” significa verificar las precondiciones antes de operar y rechazar los datos inválidos con un error claro. Dos herramientas básicas: Objects.requireNonNull (falla si algo es null) y lanzar IllegalArgumentException ante un argumento inválido.

static double promedio(int[] notas) {
    Objects.requireNonNull(notas, "el arreglo no puede ser null");
    if (notas.length == 0) {
        throw new IllegalArgumentException("no hay notas para promediar");
    }
    int suma = 0;
    for (int n : notas) {
        if (n < 0 || n > 10) {
            throw new IllegalArgumentException("nota fuera de rango [0..10]: " + n);
        }
        suma += n;
    }
    return (double) suma / notas.length;
}
Idea clave

Validar temprano y fallar con un mensaje claro es una de las mejores costumbres que podés tomar: convierte errores difíciles de rastrear en mensajes que dicen exactamente qué pasó y dónde.

1Explicá con tus palabras qué es el bytecode y por qué permite “Write Once, Run Anywhere”.

El bytecode es el resultado de compilar un archivo .java con javac: un archivo .class con instrucciones que no son para ningún procesador real, sino para una computadora “imaginaria” llamada JVM.

Permite Write Once, Run Anywhere porque introduce una capa intermedia: en vez de compilar tu programa una vez para Windows, otra para Linux y otra para Mac (como en C), lo compilás una sola vez a bytecode. Lo que cambia de sistema a sistema es la implementación de la JVM, no tu .class. Cada sistema operativo tiene su propia JVM, y todas entienden el mismo bytecode.

2¿Qué diferencia hay entre el JDK, el JRE y la JVM?

Son tres cosas anidadas, de la más grande a la más chica:

  • JDK (Java Development Kit): todo lo necesario para desarrollar. Incluye el compilador javac, herramientas (jar, javadoc, jshell…) y, adentro, el JRE.
  • JRE (Java Runtime Environment): todo lo necesario para ejecutar un programa ya compilado. Incluye las bibliotecas estándar y, adentro, la JVM.
  • JVM (Java Virtual Machine): la máquina virtual propiamente dicha. Carga el bytecode, lo interpreta y lo compila a código nativo con el JIT.

En una frase: JDK ⊃ JRE ⊃ JVM. Para programar necesitás el JDK; para sólo correr un programa alcanzaría el JRE.

3¿Qué hace el compilador JIT y en qué momento actúa?

El JIT (Just-In-Time) es un compilador que vive dentro de la JVM y traduce bytecode a código de máquina nativo de tu CPU.

Actúa en tiempo de ejecución, mientras el programa corre — no antes. La JVM arranca interpretando el bytecode; a medida que detecta que ciertos métodos o ciclos se ejecutan muchas veces (los llamados hot spots), los compila a nativo y los optimiza. Por eso un programa Java suele ser más lento en los primeros milisegundos y después “se calienta” y acelera.

4Diferenciá tipo primitivo y tipo por referencia. Dá un ejemplo de cada uno.

Un tipo primitivo guarda el valor directamente dentro de la variable. Son ocho: byte, short, int, long, float, double, boolean, char. Ejemplo: int edad = 25; — el 25 está literalmente en la variable.

Un tipo por referencia guarda una referencia (una “flecha”) a un objeto que vive en otro lado de la memoria. Es todo lo demás: String, arreglos, wrappers, tus propias clases. Ejemplo: String nombre = "Jero"; — la variable no contiene el texto, contiene una flecha al objeto que lo contiene.

Consecuencias prácticas: un primitivo nunca puede ser null, una referencia sí; == sobre primitivos compara valores, sobre referencias compara si son el mismo objeto.

5¿Por qué 7 / 2 da 3 en Java? ¿Cómo obtendrías 3.5?

Porque cuando los dos operandos son enteros, Java usa la división entera: descarta la parte decimal (trunca hacia cero) y devuelve un int. 7 / 2 = 3 con resto 1; el resto lo devuelve 7 % 2 = 1.

Para obtener 3.5 alcanza con que al menos uno sea double:

7.0 / 2          // 3.5   (literal double)
7 / 2.0          // 3.5
(double) 7 / 2   // 3.5   (cast antes de dividir)
7 / (double) 2   // 3.5

(double) (7 / 2) // 3.0  ← ¡mal! primero divide entero, después convierte

La última es el error típico: el cast llega tarde.

6¿Qué genera automáticamente un record? ¿Cuándo conviene usarlo?

Un record genera solo, a partir de sus componentes:

  • El constructor canónico con todos los componentes.
  • Un accesor por componente, con el nombre del componente (celsius(), no getCelsius()).
  • equals() — compara componente por componente (igualdad por valor).
  • hashCode() — consistente con ese equals.
  • toString() — legible, del estilo Temperatura[celsius=21.5].

Además, sus campos son private final: el objeto es inmutable.

Conviene cuando el objeto es un simple portador de datos que no cambia: un punto, una temperatura, una coordenada, un DTO, la clave de un mapa. No conviene si necesitás estado mutable, herencia o lógica pesada: ahí va una clase normal.

7¿Para qué sirve un enum? ¿Qué ventaja tiene sobre usar cadenas de texto?

Un enum define un tipo cuyo conjunto de valores posibles es fijo y conocido en tiempo de compilación: los días de la semana, los palos de una baraja, los estados de un pedido.

Ventajas sobre usar String o int “mágicos”:

  • Seguridad de tipos: DiaDeSemana.LUNES no se puede confundir con otra cosa; "lunes", "Lunes" y "LUNES" son tres cadenas distintas y el compilador no te avisa.
  • Sin typos: escribir LUNEZ es un error de compilación; "lunez" no.
  • Exhaustividad: en un switch expression sobre un enum, el compilador te obliga a cubrir todos los casos.
  • Comparación con ==: los valores son únicos (singletons), así que == es seguro y rápido.
  • Puede tener campos y métodos: esFinDeSemana(), un símbolo asociado, etc.
  • values() te da todos los valores para recorrerlos.
8¿En qué se diferencia una excepción propia que extiende RuntimeException de una que extiende Exception?

La diferencia es si es unchecked o checked:

¿Hay que declararla con throws?NoSí, en la firma del método

9¿Por qué el orden de los bloques catch importa?

Porque los catch se prueban en orden, de arriba hacia abajo, y el primero que sea compatible con la excepción lanzada es el que la atrapa. Como una excepción hija es un tipo de su padre, un catch del padre atrapa también a todas las hijas.

Si ponés el más general primero, los siguientes quedan inalcanzables y Java lo detecta: el código no compila (“exception X has already been caught”).

// MAL — no compila
try { ... }
catch (Exception e) { ... }              // atrapa TODO
catch (IllegalArgumentException e) { }   // inalcanzable

// BIEN — del más específico al más general
try { ... }
catch (DivisionPorCeroException e) { ... }
catch (IllegalArgumentException e) { ... }
catch (Exception e) { ... }

Regla: la hija siempre antes que el padre.

10¿Qué ventaja aporta escribir tests con JUnit en lugar de probar “a mano” con System.out.println?
  • Son automáticos y repetibles: ./gradlew test corre todo en segundos, siempre igual. Con println tenés que ejecutar, leer la salida y decidir vos si está bien — y eso se hace una vez y nunca más.
  • Verifican, no muestran: assertEquals(esperado, obtenido) falla si difieren. Un println imprime igual esté bien o mal.
  • Detectan regresiones: si mañana tocás el código y rompés algo que antes andaba, el test te avisa. Es la red de seguridad antes de cada commit.
  • Cubren los casos borde: podés testear el arreglo vacío, el null, el número negativo… casos que a mano nunca probás.
  • Verifican errores: con assertThrows comprobás que el código lanza la excepción correcta — algo casi imposible de chequear prolijamente con prints.
  • Documentan: un test con @DisplayName explica qué se espera del método mejor que un comentario.
  • No ensucian: los println de prueba terminan quedando en el código entregado.

package ar.uba.fi.cb100.guia.i01_intro.i03_medio.e08;

import java.util.Objects;

public class Buscador {

    /** Devuelve el índice de la PRIMERA aparición de buscado, o -1 si no está. */
    public static int indiceDe(int[] v, int buscado) {
        Objects.requireNonNull(v, "el arreglo no puede ser null");
        for (int i = 0; i < v.length; i++) {
            if (v[i] == buscado) {
                return i;                 // corta apenas lo encuentra
            }
        }
        return -1;                        // recorrió todo y no está
    }

    public static boolean contiene(int[] v, int buscado) {
        return indiceDe(v, buscado) >= 0;
    }

    public static void main(String[] args) {
        int[] v = {4, 8, 15, 16, 23, 42};
        System.out.println(indiceDe(v, 16));   // 3
        System.out.println(indiceDe(v, 99));   // -1
    }
}

import java.math.BigDecimal;
import java.util.Objects;

public class CuentaBancaria {

    private final String titular;
    private BigDecimal saldo;

    public CuentaBancaria(String titular) {
        this(titular, BigDecimal.ZERO);
    }

    public CuentaBancaria(String titular, BigDecimal saldoInicial) {
        this.titular = Objects.requireNonNull(titular, "el titular no puede ser null");
        Objects.requireNonNull(saldoInicial, "el saldo inicial no puede ser null");
        if (saldoInicial.signum() < 0) {
            throw new IllegalArgumentException("saldo inicial negativo: " + saldoInicial);
        }
        this.saldo = saldoInicial;
    }

    public String titular()  { return titular; }
    public BigDecimal saldo() { return saldo; }     // sólo lectura

    public void depositar(BigDecimal monto) {
        validarMonto(monto);
        saldo = saldo.add(monto);
    }

    public void extraer(BigDecimal monto) {
        validarMonto(monto);
        if (saldo.compareTo(monto) < 0) {           // compareTo, NO equals
            throw new SaldoInsuficienteException(saldo, monto);
        }
        saldo = saldo.subtract(monto);
    }

    private static void validarMonto(BigDecimal monto) {
        Objects.requireNonNull(monto, "el monto no puede ser null");
        if (monto.signum() <= 0) {
            throw new IllegalArgumentException("el monto debe ser positivo: " + monto);
        }
    }

    @Override
    public String toString() {
        return "CuentaBancaria[" + titular + ", saldo=" + saldo + "]";
    }
}

FizzBuzz

Del 1 al n: “Fizz” si es múltiplo de 3, “Buzz” si de 5, “FizzBuzz” si de ambos, y el número si no. Resolvelo con un switch expression sobre un boolean combinado.

PistaNo podés hacer switch sobre dos condiciones a la vez, pero sí sobre una sola cosa que las resuma. Armá un entero o una cadena que codifique los dos restos y prendé el switch sobre eso.
public static String fizzBuzz(int i) {
    boolean tres  = i % 3 == 0;
    boolean cinco = i % 5 == 0;

    // el truco: codificar las DOS condiciones en un solo valor
    int codigo = (tres ? 2 : 0) + (cinco ? 1 : 0);

    return switch (codigo) {
        case 3 -> "FizzBuzz";      // múltiplo de 3 y de 5
        case 2 -> "Fizz";          // sólo de 3
        case 1 -> "Buzz";          // sólo de 5
        default -> String.valueOf(i);
    };
}


public static void imprimirHasta(int n) {
    for (int i = 1; i <= n; i++) {
        System.out.println(fizzBuzz(i));
    }
}

La gracia del ejercicio no es FizzBuzz: es separar el cálculo de la impresión. Con fizzBuzz(int) devolviendo un String podés testearlo; si hubieras metido el println adentro, no.

Palíndromo

Método boolean esPalindromo(String s) que ignore mayúsculas y espacios. Testeá casos afirmativos y negativos.

PistaDos etapas bien separadas: primero normalizar (bajar a minúsculas y sacar lo que no sea letra), después comparar. Para lo segundo, dos índices que caminan desde los extremos hacia el centro.
public static boolean esPalindromo(String s) {
    if (s == null) {
        return false;
    }
    String limpio = s.toLowerCase().replaceAll("[^a-záéíóúñ0-9]", "");

    int i = 0, j = limpio.length() - 1;
    while (i < j) {
        if (limpio.charAt(i) != limpio.charAt(j)) {
            return false;                       // corta apenas encuentra diferencia
        }
        i++;
        j--;
    }
    return true;                                // vacío y de un carácter dan true
}

Por qué dos índices y no reverse(): comparar contra la cadena dada vuelta también funciona (new StringBuilder(limpio).reverse().toString().equals(limpio)) pero recorre todo siempre y arma un objeto extra. Con dos índices cortás en la primera diferencia y no reservás nada.

Estadísticas

Dado un int[], devolvé un record Estadisticas(int min, int max, double promedio) recorriéndolo una sola vez.

PistaLa restricción es la consigna: nada de tres recorridos. Llevá las tres cuentas en paralelo dentro del mismo for. Y pensá qué hacer con el arreglo vacío antes de empezar.
public record Estadisticas(int min, int max, double promedio) { }


public static Estadisticas calcular(int[] v) {
    if (v == null || v.length == 0) {
        throw new IllegalArgumentException("no hay estadísticas de un arreglo vacío");
    }

    int min = v[0], max = v[0];
    long suma = 0;                              // long: evita el desborde al sumar

    for (int x : v) {                           // UN solo recorrido
        if (x < min) { min = x; }
        if (x > max) { max = x; }
        suma += x;
    }
    return new Estadisticas(min, max, (double) suma / v.length);
}

Tres decisiones que valen más que el algoritmo:

  • Arrancar con v[0] y no con Integer.MAX_VALUE. Funcionan las dos, pero la primera es más difícil de romper y se lee mejor.
  • long para la suma. Con un arreglo grande de enteros grandes, un int desborda en silencio y el promedio sale mal sin ningún error.
  • El (double) antes de dividir. Si dividís dos enteros, Java hace división entera y el promedio de {1, 2} te da 1.

Ordenar tres números

Sin usar librerías, ordená tres enteros de menor a mayor y devolvelos en un arreglo.

PistaLa vía corta y sin bifurcaciones raras: tres comparaciones con intercambio, siempre las mismas. Es el bubble sort de tres elementos, desplegado a mano.
public static int[] ordenar(int a, int b, int c) {
    if (a > b) { int t = a; a = b; b = t; }     // a ≤ b
    if (b > c) { int t = b; b = c; c = t; }     // c es el mayor
    if (a > b) { int t = a; a = b; b = t; }     // reacomoda a y b
    return new int[]{a, b, c};
}

Por qué hacen falta las tres comparaciones y no dos. Después de las dos primeras, c ya es el mayor con seguridad — pero a y b pueden haber quedado cruzados por el segundo intercambio. Probá con (3, 5, 1): tras el primer if queda 3, 5, 1; tras el segundo, 3, 1, 5; y el tercero es el que arregla el 3, 1. Sin él devolverías {3, 1, 5}.

Serie de Fibonacci

Escribí long fibonacci(int n) iterativo (sin recursión) y testeá los primeros valores.

PistaNo necesitás guardar la serie entera: alcanza con recordar los dos últimos valores e irlos corriendo. Y prestá atención a por qué el enunciado insiste en “sin recursión”.
public static long fibonacci(int n) {
    if (n < 0) {
        throw new IllegalArgumentException("n debe ser ≥ 0 y es " + n);
    }
    if (n <= 1) {
        return n;                               // fib(0) = 0, fib(1) = 1
    }

    long anterior = 0, actual = 1;
    for (int i = 2; i <= n; i++) {
        long siguiente = anterior + actual;
        anterior = actual;                      // se corren de a uno
        actual = siguiente;
    }
    return actual;
}

Por qué iterativo y no recursivo. En la Unidad 4 vas a poder demostrar esa diferencia — una es exponencial y la otra lineal.

Matriz transpuesta

Dada una matriz int[][], devolvé su transpuesta.

PistaLa transpuesta de una matriz de f filas por c columnas tiene c filas y f columnas — ojo con crear el arreglo del tamaño correcto. Y acordate de que en Java una matriz es un arreglo de arreglos, así que cada fila podría tener largo distinto.
public static int[][] transponer(int[][] m) {
    if (m == null || m.length == 0) {
        return new int[0][0];
    }
    int filas = m.length;
    int columnas = m[0].length;

    for (int[] fila : m) {                      // en Java las filas pueden ser desparejas
        if (fila.length != columnas) {
            throw new IllegalArgumentException("la matriz no es rectangular");
        }
    }

    int[][] t = new int[columnas][filas];       // ¡invertidas!
    for (int i = 0; i < filas; i++) {
        for (int j = 0; j < columnas; j++) {
            t[j][i] = m[i][j];                  // el corazón del ejercicio
        }
    }
    return t;
}

Toda la transposición es esa línea: t[j][i] = m[i][j]. Lo que se equivoca la gente está alrededor — crear new int[filas][columnas] en vez de al revés, que explota con ArrayIndexOutOfBoundsException apenas la matriz no es cuadrada.

La validación de “rectangular” no es paranoia: en Java int[][] es un arreglo de arreglos, y nada impide que m[0] tenga 3 elementos y m[1] tenga 5. Eso se llama matriz dentada (jagged), y transponerla no está definido.

@Test void matrizNoCuadrada() {
    int[][] m = {{1, 2, 3},
                 {4, 5, 6}};                    // 2x3
    int[][] esperado = {{1, 4},
                        {2, 5},
                        {3, 6}};                // 3x2
    assertArrayEquals(esperado, transponer(m)); // assertArrayEquals compara en profundidad
}

@Test void transponerDosVecesEsLaOriginal() {
    int[][] m = {{1, 2, 3}, {4, 5, 6}};
    assertArrayEquals(m, transponer(transponer(m)));
}
El segundo test es el más elegante: en vez de escribir a mano el resultado esperado, verifica una propiedad que la función debe cumplir siempre. Transponer dos veces devuelve la original, sea cual sea la matriz.

Calculadora con excepciones

Método double operar(double a, double b, char op) que soporte + - * /, lanzando excepciones propias ante división por cero u operador inválido. Cubrí todo con tests.

PistaDos excepciones propias distintas, porque son dos problemas distintos. Y cuidado con una trampa: en double, dividir por cero no lanza nada — devuelve Infinity. Tenés que chequearlo vos.
public class DivisionPorCeroException extends RuntimeException {
    public DivisionPorCeroException(double dividendo) {
        super("intento de dividir " + dividendo + " por cero");
    }
}

public class OperadorInvalidoException extends RuntimeException {
    public OperadorInvalidoException(char op) {
        super("operador no soportado: '" + op + "' (válidos: + - * /)");
    }
}
public static double operar(double a, double b, char op) {
    return switch (op) {
        case '+' -> a + b;
        case '-' -> a - b;
        case '*' -> a * b;
        case '/' -> {
            if (b == 0) {                       // en double NO lanza solo: hay que chequear
                throw new DivisionPorCeroException(a);
            }
            yield a / b;
        }
        default -> throw new OperadorInvalidoException(op);
    };
}

La trampa del ejercicio es la división. Con enteros, 7 / 0 lanza ArithmeticException sola. Con double, 7.0 / 0 devuelve Infinity, -7.0 / 0 devuelve -Infinity y 0.0 / 0 devuelve NaN — sin ningún error. Es la norma IEEE 754, y es exactamente el tipo de cosa que pasa desapercibida hasta que un resultado absurdo aparece diez pantallas más adelante.

Dos detalles de sintaxis: en un switch expression, un caso con varias líneas usa llaves y yield para devolver el valor; y el default puede throw directamente, sin yield.

@Test void lasCuatroOperaciones() {
    assertEquals(7.0, operar(3, 4, '+'), 1e-9);
    assertEquals(-1.0, operar(3, 4, '-'), 1e-9);
    assertEquals(12.0, operar(3, 4, '*'), 1e-9);
    assertEquals(0.75, operar(3, 4, '/'), 1e-9);
}

@Test void divisionPorCero() {
    DivisionPorCeroException e = assertThrows(DivisionPorCeroException.class,
                                             () -> operar(7, 0, '/'));
    assertTrue(e.getMessage().contains("por cero"));
}

@Test void operadorInvalido() {
    assertThrows(OperadorInvalidoException.class, () -> operar(3, 4, '%'));
}
Fijate que assertThrows devuelve la excepción: eso te deja verificar también el mensaje. Un buen mensaje es parte del contrato del método, y si vale la pena escribirlo, vale la pena testearlo.

Histograma de caracteres

Dado un String, devolvé cuántas veces aparece cada letra (usá un int[26] para las letras a–z).

PistaEl truco está en convertir una letra en un índice: c - 'a' da 0 para la a, 1 para la b… Porque un char es, por debajo, un número.
public static int[] histograma(String s) {
    int[] conteo = new int[26];                 // arranca todo en 0
    if (s == null) {
        return conteo;
    }

    for (char c : s.toLowerCase().toCharArray()) {
        if (c >= 'a' && c <= 'z') {             // filtra dígitos, espacios y acentos
            conteo[c - 'a']++;                  // 'a'→0, 'b'→1, ... 'z'→25
        }
    }
    return conteo;
}


public static void imprimir(int[] conteo) {
    for (int i = 0; i < conteo.length; i++) {
        if (conteo[i] > 0) {
            System.out.println((char) ('a' + i) + ": " + "*".repeat(conteo[i]));
        }
    }
}

Por qué funciona c - 'a'. Un char es un entero de 16 bits con el código Unicode del carácter. Las letras minúsculas son consecutivas ('a' es 97, 'b' 98…), así que restar 'a' te da la posición dentro del alfabeto. Y para el camino inverso, (char) ('a' + i).

Por qué el if es imprescindible. Sin él, un espacio (código 32) daría 32 - 97 = -65 y el conteo[-65] te lanza ArrayIndexOutOfBoundsException. Cualquier texto real tiene espacios, así que el programa explota en el primero.

@Test void cuentaLetras() {
    int[] c = histograma("Hola Mundo");
    assertEquals(2, c['o' - 'a']);              // dos oes
    assertEquals(1, c['h' - 'a']);
    assertEquals(0, c['z' - 'a']);
}

@Test void ignoraLoQueNoEsLetraAZ() {
    int[] c = histograma("a1 b!  á");           // el espacio, el dígito y la á se ignoran
    assertEquals(1, c[0]);
    assertEquals(1, c[1]);
}
El int[26] es la versión de juguete de una idea que vas a ver en serio en la Unidad 6: usar el dato mismo como índice en vez de buscarlo. Cuando el universo de claves es chico y conocido, es imbatible — y cuando no lo es, aparecen las tablas de hash.

Validador de contraseña

Escribí un método que valide una contraseña (mínimo 8 caracteres, al menos un dígito y una mayúscula) y devuelva, mediante una excepción propia con mensaje claro, qué regla falló. Testeá cada regla.

PistaEl enunciado pide que se sepa qué regla falló: no alcanza con devolver false. Guardá en la excepción cuál fue — un enum de reglas es más útil que un texto suelto.
public enum ReglaDeContrasenia {
    LARGO_MINIMO("debe tener al menos 8 caracteres"),
    FALTA_DIGITO("debe tener al menos un dígito"),
    FALTA_MAYUSCULA("debe tener al menos una mayúscula");

    private final String descripcion;
    ReglaDeContrasenia(String descripcion) { this.descripcion = descripcion; }
    public String descripcion() { return descripcion; }
}


public class ContraseniaInvalidaException extends RuntimeException {
    private final ReglaDeContrasenia regla;

    public ContraseniaInvalidaException(ReglaDeContrasenia regla) {
        super("contraseña inválida: " + regla.descripcion());
        this.regla = regla;
    }

    public ReglaDeContrasenia regla() { return regla; }
}
public static void validar(String contrasenia) {
    Objects.requireNonNull(contrasenia, "la contraseña no puede ser null");

    if (contrasenia.length() < 8) {
        throw new ContraseniaInvalidaException(ReglaDeContrasenia.LARGO_MINIMO);
    }

    boolean tieneDigito = false, tieneMayuscula = false;
    for (char c : contrasenia.toCharArray()) {  // un solo recorrido para las dos reglas
        if (Character.isDigit(c))      { tieneDigito = true; }
        if (Character.isUpperCase(c))  { tieneMayuscula = true; }
    }

    if (!tieneDigito) {
        throw new ContraseniaInvalidaException(ReglaDeContrasenia.FALTA_DIGITO);
    }
    if (!tieneMayuscula) {
        throw new ContraseniaInvalidaException(ReglaDeContrasenia.FALTA_MAYUSCULA);
    }
}

Por qué un enum adentro de la excepción y no sólo un mensaje: el mensaje es para el humano, el enum es para el programa. Con él, quien captura puede decidir según la regla (resaltar un campo, contar cuál falla más) sin andar comparando cadenas — que es frágil y se rompe apenas cambiás una palabra.

Este ejercicio junta casi toda la unidad: enum con atributo y constructor, excepción propia que lleva datos, Character, recorrido de String y validación temprana. Es un buen cierre porque ninguna pieza es difícil sola — lo que se evalúa es hacerlas convivir.

@Test void contraseniaValida() {
    assertDoesNotThrow(() -> validar("Segura123"));
}

@Test void cadaReglaSeInformaPorSeparado() {
    ContraseniaInvalidaException corta = assertThrows(ContraseniaInvalidaException.class,
                                                      () -> validar("Ab1"));
    assertEquals(ReglaDeContrasenia.LARGO_MINIMO, corta.regla());

    ContraseniaInvalidaException sinDigito = assertThrows(ContraseniaInvalidaException.class,
                                                          () -> validar("SinNumeros"));
    assertEquals(ReglaDeContrasenia.FALTA_DIGITO, sinDigito.regla());

    ContraseniaInvalidaException sinMayus = assertThrows(ContraseniaInvalidaException.class,
                                                         () -> validar("minusculas1"));
    assertEquals(ReglaDeContrasenia.FALTA_MAYUSCULA, sinMayus.regla());
}
Una variante que vale la pena pensar: en vez de cortar en la primera regla que falla, juntar todas y reportarlas de una (una lista de reglas incumplidas). Es lo que hace cualquier formulario web decente — nadie quiere corregir de a un error por vez.
