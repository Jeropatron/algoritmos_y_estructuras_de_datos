🧩 Conceptos de la Parte A

¿Qué es un record? ¿Y por qué Prestamo es una clase sin decir class?

Un record es una clase — una forma especial y abreviada de declararla. La palabra record reemplaza a class para modelar un valor inmutable (un dato que no cambia una vez creado). En una línea, Java genera solo: el constructor, los accessors (retiro(), padron()…), y equals, hashCode y toString.

Palabra clave¿Es clase?Para qué
classSí (la general)Cualquier objeto
recordSí (especial)Modelar datos/valores → mi Prestamo
enumSí (especial)Conjunto cerrado de valores
interfaceNoUn contrato puro (viene en la Parte B)

📘 ENUNCIADO  Usar record lo pide la consigna: un préstamo es un valor (dos préstamos con los mismos datos son "el mismo"). Ref: clase_1_y_2 · 1B.15 Modelar con record.

Prestamo es una clase y un TDA

No compiten: son dos capas.

  • TDA (Tipo de Dato Abstracto) = el qué: un tipo definido por sus operaciones e invariantes, escondiendo el cómo. Es una idea de diseño.
  • Clase / record = el cómo: el mecanismo concreto de Java para implementar ese TDA.

Entonces Prestamo es un TDA implementado como un record class. Ref: clase_4 · 3.2 TDA, 3.1 Abstracción.

Invariantes y el constructor compacto

Una invariante es una condición que siempre tiene que ser verdadera para que el objeto sea válido. 📘 ENUNCIADO "Un Prestamo mal formado NO debe existir." El lugar para hacerlas cumplir es el constructor compacto: se escribe con el nombre del record y llaves, sin repetir los parámetros. Si un dato no cumple, corto la creación lanzando una excepción.

Refs: 1B.21 Validaciones (el porqué), 1B.17 Excepciones (la herramienta), clase_4 · 3.4.1 Encapsulamiento.

💡 Tipado estático: cómo Java "sabe" el tipo

Java no adivina el tipo de retorno: yo lo declaro en la firma (public int multa(...) = "prometo devolver un int"). Java es el policía que verifica esa promesa al compilar. Por eso, cuando devolví un long donde prometí int, no compiló hasta poner el cast. El único lugar donde Java infiere el tipo es var (variables locales). Ref: 1B.6 Tipos, 1B.7 Rangos y wrappers.

💻 El código, explicado

El encabezado del record

package ar.uba.fi.cb100.clases.a2026.c02.tps.tp1;

import java.time.LocalDate;

public record Prestamo(LocalDate retiro, int padron, String socio,
                       String isbn, String titulo, LocalDate devolucion) { }
  • package: la "dirección postal" del archivo; coincide con las carpetas. 📘
  • 6 componentes. retiro/devolucion son LocalDate (tipo fecha, hay que importarlo). padron es int. Los demás String.
  • ¿Por qué isbn es String y no número? Es un identificador, no una cantidad: nunca hago matemática con él y podría tener ceros a la izquierda. 🎨

El constructor compacto (las invariantes)

public Prestamo {
    if (padron <= 0) {
        throw new IllegalArgumentException("El padron no puede ser menor o igual a 0.");
    }
    if (socio == null || socio.isEmpty()) {
        throw new IllegalArgumentException("El nombre del socio no puede estar vacio ni ser nulo.");
    }
    if (isbn == null || isbn.isEmpty()) {
        throw new IllegalArgumentException("El identificador del libro no puede estar vacio ni ser nulo.");
    }
    if (titulo == null || titulo.isEmpty()) {
        throw new IllegalArgumentException("El titulo del libro no puede estar vacio ni ser nulo.");
    }
    if (devolucion != null && devolucion.isBefore(retiro)) {
        throw new IllegalArgumentException("La devolucion no puede ser previa al retiro.");
    }
}
  • Orden del ||: chequeo == null antes de llamar .isEmpty(). Por el short-circuit, si es null Java no evalúa la derecha → evito la NullPointerException.
  • padron <= 0: "positivo" excluye al 0. 📘
  • La devolución es distinta: puede ser null (préstamo pendiente). Uso != null && isBefore: solo valido el orden de fechas si hay devolución.

Los 4 métodos (el comportamiento)

public boolean estaPendiente() {
    return devolucion == null;              // pendiente = sin fecha de devolución
}

public LocalDate vencimiento() {
    return retiro.plusDays(14);             // 14 días corridos (regla de negocio)
}

public int diasDeAtraso(LocalDate corte) {
    LocalDate fechaHasta = estaPendiente() ? corte : devolucion;
    long entre = Math.max(0, ChronoUnit.DAYS.between(vencimiento(), fechaHasta));
    return (int) entre;                     // cast long → int
}

public int multa(LocalDate corte) {
    int diasTotales = diasDeAtraso(corte);  // reutiliza el método de arriba
    int multaBase = diasTotales * 150;      // $150 por día
    return Math.min(3000, multaBase);       // tope de $3000
}
  • vencimiento(): LocalDate es inmutable — plusDays devuelve una fecha nueva, no modifica retiro. El "14" viene de la regla #1. 📘
  • diasDeAtraso: el ternario elige hasta qué fecha contar (corte si pendiente, devolución si no). ChronoUnit.DAYS.between(desde, hasta) cuenta días; Math.max(0, …) evita negativos. 📘 (herramientas sugeridas)
  • multa: reutiliza diasDeAtraso (un TDA que se apoya en sí mismo). Math.min pone el techo — el hermano de Math.max. 🎨 (reutilizar en vez de recalcular)
  • Nombres de variables: fechaHasta, diasTotales, multaBase — en camelCase y describiendo el contenido. 🎨

Refs: 1B.12 Métodos, 1B.18 Fechas y horas, 1B.10 Math, clase_3 · 2.9 Inmutables.

⚠️ Errores que cometí y cómo los corregí

⚠️ 1 · Validar la devolución como si nunca pudiera ser null

Primero escribí devolucion == null || devolucion.isBefore(retiro). Eso rechazaba los préstamos pendientes (que legítimamente tienen devolucion == null).

Corrección: devolucion != null && devolucion.isBefore(retiro). La regla dice que null es válido (pendiente); solo si hay fecha valido que no sea anterior al retiro.

⚠️ 2 · return con una asignación de más

En vencimiento() puse return vencimiento = retiro.plusDays(14);. vencimiento es el nombre del método, no una variable — no se le puede asignar nada.

Corrección: return retiro.plusDays(14);. El return devuelve directo la expresión; no hace falta guardarla en nada.

⚠️ 3 · double vs int en la multa

Declaré public double multa(...). Pero la multa siempre es entera (múltiplos de 150, tope 3000) — con double daría 3600.0 y no coincidiría con la salida esperada.

Corrección: public int multa(...). Regla: double solo si el dato puede tener decimales.

⚠️ 4 · long donde prometí int

ChronoUnit.DAYS.between(...) devuelve long. Como el método promete int, no compilaba.

Corrección: un cast explícito return (int) entre; — le digo a Java "me hago cargo, convertilo a int" (es seguro: los días de atraso nunca son un número gigante).

⚠️ 5 · Typo Localdate y estructura suelta

Escribí Localdate (Java distingue mayúsculas → LocalDate). Y al principio puse los if sueltos en el cuerpo del record, sin el encabezado public Prestamo { … } que los envuelve — el código ejecutable tiene que vivir dentro de un método o constructor.

❓ Preguntas que hice

❓ ¿Qué es el ISBN?

El número único que identifica a un libro (como el DNI de un libro). En los datos es el número largo. El mismo ISBN se repite cuando varios socios piden el mismo título → me va a servir para el ranking de la Parte D. Va como String por ser identificador.

❓ ¿Por qué Prestamo es una clase si no dice class?

Porque record es una forma de declarar una clase (una "record class"). Java la expande por detrás a una clase final con los campos, el constructor y los métodos estándar.

❓ Entonces, ¿Prestamo es una clase y un TDA?

Sí, las dos cosas: el TDA es el concepto de diseño (operaciones + invariantes); la clase/record es el mecanismo de Java que lo implementa. Mismo objeto, dos "sombreros".

❓ ¿Cómo "sabía" Java que devolvía un int?

No lo adivinó: lo declaré yo en la firma. Java (tipado estático) solo verifica que cumpla la promesa al compilar. Ver el recuadro de tipado estático más arriba.

❓ "Method 'multa' is never used" — ¿qué es?

Una inspección de IntelliJ (no un warning del compilador): nadie llama a multa todavía porque construyo de abajo hacia arriba. Se resuelve solo cuando escriba su "cliente" (los tests o el Reporteador). No se suprime ni se borra el método.

❓ ¿El repo donde commiteo es mío? ¿El profe verá mis HTML y guías?

El repo local es mío (aunque su remoto sea de la cátedra). Los HTML de teoría NO se entregan (viven en mi repo personal externo). Las guías SÍ quedarían incluidas (están en el mismo repo del TP), pero son mi propio trabajo y no afectan la corrección.

❓ ¿Cómo toma su valor un parámetro? (ej. corte en diasDeAtraso)

Hay que separar dos ideas:

  • Parámetro = el hueco con nombre en la definición: diasDeAtraso(LocalDate corte). Es una variable local que todavía no tiene valor.
  • Argumento = el valor concreto que paso al llamar: prestamo.diasDeAtraso(LocalDate.parse("2026-03-26")).

Al ejecutar la llamada, Java copia el argumento dentro del parámetro (como si al entrar hiciera LocalDate corte = <el argumento>;). Desde ahí, adentro del método, corte vale eso; cuando el método termina, desaparece (es local). Por eso el mismo método con distintos argumentos hace que corte tome distintos valores en cada llamada — eso lo hace reutilizable. En mi multa yo hago diasDeAtraso(corte): le paso mi corte como argumento del corte del otro método (se encadena).

Matiz: Java pasa siempre por valor (el parámetro recibe una copia); para objetos como LocalDate se copia la referencia, pero al ser inmutable no hay sorpresas. Ref: 1B.12 Métodos, clase_3 · 2.8 Paso de parámetros.

🧪 JUnit y aserciones

📘 ENUNCIADO  Los tests son obligatorios (sección 7, 15 puntos). Van en un árbol paralelo: src/test/java/… (no en src/main), con el mismo package. Se corren con ./gradlew test.

PiezaQué es
@TestAnotación que marca un método como test para que Gradle lo ejecute
@DisplayName("...")Nombre legible que se ve al correr la suite
assertEquals(esperado, obtenido)Falla si difieren. Compara por valor (.equals()), no por referencia (==) → por eso comparar dos LocalDate distintos con el mismo día da OK
assertThrows(Exc.class, () -> ...)Verifica que el código de la lambda lance la excepción. Si no lanza, el test falla

La () -> ... es una lambda: en vez de ejecutar el código ya, se lo doy a assertThrows para que lo corra él y vea si explota. Ref: 1B.22 JUnit 5, 1B.16 Lambdas, clase_3 · 2.6 == vs equals.

Ejemplos de lo que escribí

@Test
@DisplayName("Vencimiento es 14 dias despues del retiro")
void vencimientoEsCatorceDiasDespuesDelRetiro() {
    LocalDate retiro = LocalDate.parse("2026-03-02");
    LocalDate vencimiento = LocalDate.parse("2026-03-16");   // esperado, escrito a mano
    Prestamo p = new Prestamo(retiro, 115324, "Patron", "B335D", "Rebelion en la granja", null);
    assertEquals(vencimiento, p.vencimiento());
}

@Test

}

🎯 Lecciones de testing (lo que más me costó)

💡 El valor esperado tiene que ser independiente

Al principio calculé el esperado con retiro.plusDays(14) — la misma fórmula que usa el método que estoy probando. Si el "14" estuviera mal en los dos lados, el test pasaría igual. Corrección: escribir la fecha esperada a mano (2026-03-16), de una fuente distinta a la lógica bajo prueba.

⚠️ El "verde engañoso" #1: dos campos inválidos a la vez

En los tests de validación puse a veces dos campos rotos (ej. socio="" y isbn=""). Como el constructor valida en orden (padron → socio → isbn → titulo → devolucion) y corta en el primero, saltaba por socio y el isbn nunca se probaba. El test pasaba por el motivo equivocado.

Regla: un test de assertThrows debe tener un solo campo inválido y el resto válido, para saber con certeza qué validación disparó.

⚠️ El "verde engañoso" #2: probar el objeto equivocado

Creé devueltoAntes pero la aserción seguía preguntándole a prestamo (el de antes). La variable nueva quedaba sin usar (IntelliJ la pinta en gris) y el caso no se probaba. Pista visual: si creo una variable y queda en gris, algo del test no la está usando.

🎨 null vs vacío son dos ramas distintas

En socio == null || socio.isEmpty(), probar null NO cubre el caso "" (por el short-circuit, isEmpty() ni se evalúa). Para cubrir ambas ramas: dos construcciones (una con null, otra con ""), que pueden vivir en el mismo método @Test con dos assertThrows.

RegistroSobreArreglouna class que la implementa (implements) con un arreglo que crece. El "cómo".

implements = la clase se compromete a cumplir el contrato; Java la obliga a implementar los 6 métodos (por eso IntelliJ los generó con @Override). @Override = "este método viene del contrato" (chequeo de seguridad). Ref: clase_4 · 3.6 Interfaces, 3.4.3 Polimorfismo.

💡 Estado interno: capacidad vs. usados

La clase tiene dos campos privados: private Prestamo[] prestamos = new Prestamo[8] (el contenedor, capacidad 8) y private int usados = 0 (cuántos cargué de verdad). No alcanza con prestamos.length: eso da la capacidad (casillas que existen), no cuántas llené. La capacidad crece (8→16→32...) pero usados cuenta lo real. Este dúo "contenedor + contador" se repite en varios métodos. Ref: 1B.13, clase_4 · 3.4.1 Encapsulamiento.

💻 Los métodos, explicados

registrar — el crecimiento manual (el corazón, 15 puntos)

public void registrar(Prestamo p) {
    if (usados == prestamos.length) {                               // ¿lleno?
        prestamos = Arrays.copyOf(prestamos, prestamos.length * 2); // duplico y copio
    }
    prestamos[usados] = p;   // guardo en la proxima casilla libre
    usados += 1;             // cuento uno mas
}
  • El if solo agranda cuando está lleno; guardar+contar va afuera del if, para que corra siempre. 📘 (capacidad 8, doble, Arrays.copyOf)
  • prestamos.length * 2 usa la capacidad actual → crece bien siempre. Copiar un arreglo: clase_3 · 2.10.

obtener — chequeo de índice contra usados (no length)

if (i < 0 || i > usados - 1) {
    throw new IndexOutOfBoundsException("El indice a obtener es invalido");
}
return prestamos[i];

Los índices válidos son 0 .. usados-1 (los cargados), no hasta length. Si usara length, devolvería casillas vacías (null). Otra vez capacidad vs. usados.

padrones — distintos en orden, con bandera

Sin HashSet (prohibido), los repetidos se filtran a mano: contenedor int[] de tamaño máximo (usados) + contador distintos. Por cada padrón, un for interno busca si ya está; una bandera boolean esNuevo (arranca en true, pasa a false si aparece) decide, después del for interno, si se agrega. Al final, Arrays.copyOf recorta al tamaño real.

prestamosDe — filtrar (origen vs. destino)

Recorre el origen (prestamos[i]) y copia al destino los que coinciden con el padrón. Sobre-reserva de tamaño usados y recorta con copyOf. Si no hay ninguno, el contador queda en 0 y copyOf(..., 0) da el arreglo vacío que pide el contrato — gratis.

titulosMasPedidos — lo más difícil del TP

Junta cuatro cosas, sin colecciones. Se resolvió en 3 sub-problemas:

  • 1. Contar: dos arreglos paralelos — titulos (String[]) y conteo (int[]) — donde posición k ↔ mismo título. Búsqueda interna con .equals() (¡no ==!) que recuerda el índice (arranca en −1). Si el título es nuevo: se guarda + conteo 1; si ya estaba: conteo[pos] += 1.
  • 2. Elegir el top n: selección repetida. Un for externo repite Math.min(n, distintos) veces; adentro, un for interno busca el de mayor conteo (con desempate). Se guarda el ganador y se tacha (conteo[indiceMejor] = -1) para no re-elegirlo.
  • 3. Resultado: tamaño Math.min(n, distintos) (no siempre hay n títulos).

El desempate alfabético usa String.compareTo: a.compareTo(b) < 0 significa que a va antes que b. Solo se mira cuando los conteos empatan. Ref: clase_4 · 3.8 / Comparable.

⚠️ Errores y lecciones de la Parte B

⚠️ Origen vs. destino

Varias veces leí del arreglo resultado (vacío) en vez del origen. Regla: se lee de prestamos (los cargados) y se escribe en el arreglo resultado. Nunca confundir de dónde sale el dato y a dónde va.

⚠️ Índice vs. valor

En "buscar el máximo" guardé el conteo en una variable llamada indiceMejor. Tenía que guardar el índice (posición), y comparar con conteo[indiceMejor]. El índice te da acceso a las dos cosas (título y conteo) de esa posición.

⚠️ Anidar bien los ciclos (selección)

El ciclo que repite (top n) va AFUERA; el que busca el mejor va ADENTRO. Guardar y tachar van después del for interno pero dentro del externo (recién ahí está definido indiceMejor). Tachar es una línea, no un for.

⚠️ Off-by-one y == true

Recorrer hasta usados-1 en un for se escribe i < usados (no i < usados-1, que saltea el último). Y if (esNuevo == true) se escribe directo if (esNuevo).

🎨 El patrón que se repite: sobre-reservar + recortar

Cuando no sé de antemano cuántos elementos voy a juntar: creo un arreglo del tamaño máximo posible (usados), lleno con un contador, y al final recorto con Arrays.copyOf(arr, contador). Lo usé en padrones, prestamosDe y (variado) en titulosMasPedidos.
