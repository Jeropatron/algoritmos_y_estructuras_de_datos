De la memoria a las referencias
Objetivos de la unidad

Al terminar esta unidad vas a poder: (1) explicar cómo se organiza la memoria de un programa Java (stack y heap); (2) distinguir valores de referencias y entender qué es (y qué no es) una referencia; (3) manejar null y Optional sin miedo; (4) diferenciar identidad (==) de igualdad (equals); (5) razonar sobre aliasing, paso de parámetros por valor y objetos mutables/inmutables; y (6) entender, en lo esencial, cómo la recolección de basura libera la memoria por vos.

En la Unidad 1B vimos que hay dos familias de tipos: primitivos y referencias. Esta unidad se mete de lleno en esa distinción, porque es la base para entender todo lo que viene: cuando armemos listas, árboles o grafos, vamos a estar conectando objetos con referencias. Entender bien cómo funcionan ahora te va a ahorrar muchísimos errores más adelante.

2.1El modelo de memoria: stack y heap

Cuando un programa Java se ejecuta, la JVM organiza la memoria en dos zonas que nos interesan. El stack (pila) guarda las variables locales y las llamadas a métodos; es rápido y se organiza solo (cada método, al terminar, libera su parte). El heap (montículo) guarda los objetos que creás con new; es la zona de memoria dinámica.

Idea clave

Regla mental simple: lo que hacés con new vive en el heap; las variables locales viven en el stack. Una variable de objeto no “contiene” el objeto: contiene una referencia que lleva hasta él.

2.2Valores y referencias

Un tipo primitivo guarda el valor directamente. Al asignarlo o pasarlo, se copia el valor. Un tipo por referencia guarda una referencia al objeto; al asignarlo, se copia la referencia, no el objeto: las dos variables quedan apuntando al mismo objeto.

Esta diferencia es tan importante que vale la pena verla en cámara lenta, con el mismo guion de tres pasos para cada familia:

int a = 5;
int b = a;             // copia el valor
b = 99;                // a sigue valiendo 5


int[] x = {1, 2, 3};
int[] y = x;           // copia la referencia: x e y son el MISMO arreglo
y[0] = 99;             // x[0] también es 99 ahora

Leé la columna izquierda: en el paso 2, b recibe una copia del 5; son dos cajas separadas, y por eso en el paso 3 cambiar b no toca a a. Ahora la derecha: en el paso 2, y = x no copia el arreglo —copia la flecha—, así que x e y llevan al mismo objeto del heap. En el paso 3, y[0] = 99 modifica ese único arreglo… y x[0] “cambió solo”. No hubo magia: siempre hubo un solo arreglo.

Idea clave

La asignación en Java copia lo que hay en la caja de la variable: si la caja tiene un valor, copia el valor; si tiene una referencia (una flecha), copia la flecha. Nunca copia el objeto apuntado.

2.3Crear objetos con new

¿Qué pasa exactamente cuando escribís esta línea?

var cuenta = new Cuenta(1000);    // new -> objeto en el heap, 'cuenta' guarda la referencia

Aunque es una sola línea, adentro suceden cuatro pasos, en orden:

  1. Se declara la variable cuenta en el stack. Todavía no lleva a ningún lado.
  2. new reserva memoria en el heap para un objeto Cuenta, con sus campos aún sin inicializar.
  3. Se ejecuta el constructor Cuenta(1000), que puebla los campos (saldo = 1000).
  4. new devuelve la referencia al objeto recién creado, y la asignación la guarda en cuenta. Recién ahora la variable “lleva” al objeto.

Si el heap se queda sin memoria en el paso 2, la JVM lanza un OutOfMemoryError (raro en la práctica de la materia).

2.4Referencias, no punteros

Si venís de C o C++, cuidado: Java no tiene punteros. Una referencia se parece a un puntero en que “lleva hasta” un objeto, pero con diferencias importantes: no podés ver ni manipular la dirección de memoria, no hay aritmética de punteros, y no podés convertir un número en una referencia. Una referencia sólo sirve para una cosa: acceder al objeto al que apunta (o ser null). Esto elimina de un plumazo toda una familia de errores clásicos de C.

Imprimir un objeto sin toString propio muestra algo como Cuenta@65ae6ba4: no es “la dirección de memoria”, es el nombre de la clase y un código de hash en hexadecimal. No lo uses como si fuera una dirección.

2.5null y la NullPointerException

🔁 Repaso rápido · null y Optional
  • null = "ninguna referencia" (una variable de objeto que no apunta a nada). Usar un método sobre null tira NullPointerException.
  • Guard defensivo: chequeá if (s == null) { ... } ANTES de usar el objeto, y devolvé un valor seguro (ej. "" o 0).
  • Optional<T> = una "cajita" que puede tener un valor o estar vacía (alternativa segura a null). Métodos clave:
o.orElse("N/A")            // devuelve el valor, o "N/A" si esta vacia
o.map(s -> s.length())     // TRANSFORMA el valor si esta presente (texto → su largo)
o.map(String::length).orElse(0)   // combinados: largo si hay, 0 si no

Nota: map sobre Optional se profundiza en la Unidad 12 (Streams); acá aparece como adelanto.

null es una referencia especial que no apunta a ningún objeto. Una variable de objeto puede valer null (los primitivos, nunca). Si intentás usar un método o campo sobre una referencia null, la JVM lanza la famosa NullPointerException (NPE).

String s = null;
s.length();           // ¡NullPointerException!

Podés chequear con if (s != null), pero para expresar “puede no haber valor” de forma más clara existe Optional, que te obliga a pensar el caso vacío:

Optional<String> nombre = buscarNombre(id);
String texto = nombre.orElse("desconocido");      // valor por defecto si está vacío
nombre.ifPresent(n -> System.out.println(n));     // hace algo sólo si hay valor
Idea clave

Recordá de la Unidad 1B: los wrappers (Integer, Boolean…) son objetos, así que pueden ser null; los primitivos (int, boolean…) no. Mezclar ambos sin cuidado es una fuente típica de NPE por unboxing de un null.

2.6Identidad vs igualdad: == y equals

Esta distinción es de las más importantes de la materia. El operador == compara identidad: ¿las dos referencias apuntan al mismo objeto? El método equals compara igualdad de contenido: ¿los dos objetos valen lo mismo?

String s1 = new String("java");
String s2 = new String("java");
s1 == s2;          // false: son dos objetos distintos
s1.equals(s2);     // true:   tienen el mismo contenido


Punto p1 = new Punto(1, 2);
Punto p2 = new Punto(1, 2);
p1 == p2;          // false
p1.equals(p2);     // true (un record compara por valor)
Error común

Para comparar el contenido de objetos (textos, puntos, etc.) usá siempre equals, no ==. El == entre objetos casi nunca es lo que querés (salvo para comparar contra null, donde sí se usa ==).

Cuando definas tus propias clases y quieras compararlas por contenido, vas a tener que escribir equals (y su compañero hashCode). Un record ya te los da gratis; lo veremos en detalle al llegar a Hashing.

2.7Aliasing: dos referencias, un objeto

Cuando dos variables apuntan al mismo objeto, decimos que hay aliasing (de alias: dos nombres para la misma cosa). Como comparten el objeto, un cambio hecho a través de una lo ve también la otra. Veámoslo en tres pasos con una Cuenta:

Cuenta c = new Cuenta(1000);    // 1) un objeto, una referencia
Cuenta alias = c;               // 2) segunda referencia AL MISMO objeto
alias.depositar(500);           // 3) muto por el alias...
c.saldo();                      //      ...y c "ve" 1500

El paso 2 es el que engaña: Cuenta alias = c; parece crear otra cuenta, pero no hay ningún new —sin new no hay objeto nuevo—. Sólo se copió la flecha. Por eso en el paso 3 el depósito hecho “por el alias” le cambia el saldo “a c”: son el mismo objeto con dos nombres. Esto es potente (podés compartir estructuras sin copiarlas), pero es una fuente clásica de errores si no te das cuenta de que estás compartiendo.

2.8Paso de parámetros: siempre por valor

En Java, los argumentos se pasan siempre por valor: el método recibe una copia de la variable. Para un primitivo, copia el valor. Para un objeto, copia la referencia (no el objeto). De esa única regla salen las dos consecuencias que más confunden, así que vamos a mirarlas por separado, con la pila de llamadas a la vista.

static void mutar(int[] arr)     { arr[0] = 99; }            // se ve afuera
static void reasignar(int[] arr) { arr = new int[]{9,9,9}; } // NO se ve afuera

Caso 1: mutar el objeto — SÍ se ve afuera. Cuando main llama a mutar(datos), se crea un frame nuevo en el stack con el parámetro arr, que recibe una copia de la referencia. Dos flechas, un solo arreglo. Entonces arr[0] = 99 modifica el único arreglo que existe, y cuando el frame de mutar desaparece, main sigue apuntando a ese arreglo… ya modificado.

Caso 2: reasignar el parámetro — NO se ve afuera. Ahora el método hace arr = new int[]{9,9,9}. Eso cambia la copia local de la referencia: la flecha de arr pasa a apuntar a un arreglo nuevo, pero la flecha de datos en main no se enteró de nada. Al volver, el frame de reasignar muere, el arreglo nuevo queda inalcanzable (lo recolectará el GC) y main sigue viendo {1,2,3}.

Idea clave

Si querés que un método le “cambie el objeto” al llamador, tenés dos opciones honestas: mutar el objeto recibido, o devolver el objeto nuevo con return para que el llamador lo asigne. Reasignar el parámetro adentro no hace nada visible afuera.

2.9Objetos mutables e inmutables

Un objeto es inmutable si su estado no cambia después de creado: String, los wrappers y los record lo son. Es mutable si su estado puede cambiar: los arreglos y las clases con setters lo son. “Modificar” un inmutable en realidad significa crear uno nuevo.

String s = "abc";
s.toUpperCase();        // devuelve "ABC" pero NO cambia s; s sigue siendo "abc"
s = s.toUpperCase();    // así sí: guardo la referencia al String NUEVO

Fijate lo que pasa en la primera línea: toUpperCase() crea un String nuevo en el heap con el contenido "ABC" y devuelve su referencia… que nadie guarda. El original "abc" no se tocó (es inmutable), así que s sigue viendo "abc". La solución es la segunda forma: reasignar s para que apunte al nuevo. Este es uno de los errores más comunes al empezar con Java.

2.10Copias: superficial y profunda

🔁 Repaso rápido · Arreglos (la base de casi todos estos ejercicios)
int[] v = {1, 2, 3};        // crear con valores ya puestos
int[] w = new int[5];       // crear vacío de tamaño 5 (todo en 0)

v[0]                        // acceder: leer la posición 0 (arranca en 0)
v[0] = 9;                   // escribir en la posición 0
v.length                   // cuántos elementos tiene (¡sin paréntesis!)

for (int i = 0; i < v.length; i++) {   // recorrer por índice
    ... v[i] ...
}
for (int x : v) { ... x ... }           // recorrer sin índice (for-each)
  • Copiar un arreglo (objeto nuevo e independiente): v.clone() o Arrays.copyOf(v, v.length).
  • Alias vs copia: int[] a = v; NO copia — a y v son el mismo arreglo (tocar uno toca al otro). Para una copia de verdad, usá clone().
  • Los índices van de 0 a v.length - 1. Pasarte de ahí tira ArrayIndexOutOfBounds.

A veces querés una copia independiente de un objeto para que los cambios no se “contagien”. El problema aparece con estructuras anidadas: objetos que contienen referencias a otros objetos, como una matriz (un arreglo de arreglos). Ahí hay dos niveles de copia. Una copia superficial (shallow) copia la estructura de más afuera, pero comparte los objetos internos. Una copia profunda (deep) copia también los internos, quedando totalmente independiente.

int[][] matriz = {{1, 2}, {3, 4}};
int[][] superficial = matriz.clone();      // comparte las filas internas
superficial[0][0] = 99;                    // ¡también cambia matriz[0][0]!


int[][] profunda = new int[matriz.length][];
for (int i = 0; i < matriz.length; i++)
    profunda[i] = Arrays.copyOf(matriz[i], matriz[i].length);   // independiente

Seguí las flechas de la izquierda: matriz y copia tienen arreglos exteriores distintos (eso copió clone()), pero las flechas de adentro de ambos llevan a las mismas filas. Por eso copia[0][0] = 99 “le cambió” la matriz al original: la fila [99, 2] es compartida. A la derecha, la copia profunda duplicó también las filas: dos árboles completamente separados, y la mutación queda contenida.

Error común

clone() sobre arreglos y la mayoría de las copias “de un nivel” (Arrays.copyOf, el constructor new ArrayList<>(otra)) son superficiales. Si la estructura tiene objetos mutables adentro y necesitás independencia real, tenés que copiar cada nivel vos.

2.11La recolección de basura

En C o C++ el programador reserva y libera la memoria a mano, lo que provoca errores difíciles (fugas de memoria, liberar dos veces, usar memoria liberada). En Java eso lo hace la JVM automáticamente: el recolector de basura (garbage collector, GC).

La idea es simple: un objeto se puede alcanzar si existe alguna cadena de referencias que llega hasta él desde una variable “viva”. Cuando un objeto ya no es alcanzable por ninguna referencia, el GC lo detecta y libera su memoria, sin que vos hagas nada.

var c = new Cuenta(1000);
c = new Cuenta(2000);     // la primera cuenta ya no es alcanzable -> el GC la recolectará

Seguí la secuencia: al ejecutar la segunda línea, la flecha de c pasa a apuntar a la cuenta de saldo 2000. La cuenta de saldo 1000 sigue existiendo en el heap un rato más, pero ya nadie llega hasta ella: ninguna variable viva la apunta. Ése es exactamente el criterio del GC: en algún momento la detecta inalcanzable y recicla su memoria. Notá que vos no hiciste nada para “borrarla” —soltar la última referencia es soltarla—.

No necesitás (ni podés) liberar memoria a mano: no hay delete. Las JVM modernas usan por defecto un recolector llamado G1, y para aplicaciones de muy baja latencia existe ZGC; como programador casi nunca tenés que elegir ni configurar nada.

Al pie (del apunte)

G1 (Garbage First) es el recolector por defecto desde Java 9; ZGC es una opción para pausas muy bajas. Detalles como generaciones o algoritmos internos exceden esta materia.

Error común

El GC libera lo inalcanzable, no lo “inútil”. Si dejás una referencia apuntando a algo que ya no usás (por ejemplo, en una estructura que crece y nunca limpiás), ese objeto sigue siendo alcanzable y no se libera: es una fuga de memoria lógica. La solución es soltar la referencia (por ejemplo, ponerla en null o quitarla de la estructura).

2.12Ejemplo integrador

Este programa junta varias ideas: un objeto mutable compartido por dos referencias (aliasing), la diferencia entre identidad y hacer una copia, y por qué a veces conviene copiar explícitamente.

2.13Errores comunes

Error común — el resumen de la unidad
  • Comparar objetos con == esperando comparar contenido: usá equals.
  • Olvidar chequear null antes de usar una referencia que puede no tener valor.
  • Creer que pasar un objeto a un método lo “protege”: si lo mutás adentro, cambia afuera.
  • Hacer clone() de una estructura anidada creyendo que es una copia profunda: es superficial.
  • Pensar que poner una variable en null “borra” el objeto: sólo suelta esa referencia; el GC actúa si nadie más lo alcanza.

3B.1Cómo leer los diagramas

Cada figura es una foto de la memoria en un instante, con el formato del pizarrón:

  • La línea punteada vertical separa el STACK (izquierda) del HEAP (derecha).
  • Cada frame del stack es una caja con el nombre del método y sus variables; los frames se apilan (main arriba, la llamada más profunda abajo).
  • Cada objeto del heap es una caja con su dirección inventada (@A, @B… — en la máquina real es un número) y sus atributos.
  • Las referencias se muestran como → @A: nacen en una variable y cruzan hacia su bloque. En Java sólo las seguís; no las ves como números ni las podés operar.
  • Colores: verde = lo recién creado; rojo = lo que cambió en este paso; gris punteado = lo inalcanzable (huérfano).

3B.2El debugger: el stack en vivo

Todo lo que dibuja el microscopio, IntelliJ lo muestra en tiempo real — es la herramienta central del cuestionario del TP1:

  • Breakpoint: clic en el margen junto al número de línea (círculo rojo). El programa frena antes de esa línea.
  • Debug: ejecutá con el bicho verde (Shift+F9) en vez del play.
  • Panel Frames: es el stack, dibujado. Cada fila es un frame; el de arriba es donde está frenado.
  • Panel Variables: las variables del frame. Un primitivo muestra su valor (a = 5). Una referencia muestra Rectangulo@519 — ¡ese @519 es la flecha!
  • Los tres pasos: Step Over (F8) ejecuta la línea y frena en la siguiente; Step Into (F7) se mete en el método llamado (ves apilarse el frame); Step Out (Shift+F8) termina el método y vuelve (ves desapilarse el frame).
La comprobación reina

Dos variables apuntan al mismo objeto si y sólo si muestran el mismo @ en el panel Variables. Cuando dudes de un diagrama, ponele un breakpoint y comparalo contra Frames + Variables: el debugger es el árbitro.

1¿Qué se guarda en el stack y qué en el heap? Dá un ejemplo de cada uno.



El stack (pila) guarda las variables locales y las llamadas a métodos. Cada llamada apila un frame con sus parámetros y variables locales; al terminar el método, ese frame se libera solo. Es rápido y se ordena automáticamente.


El heap (montículo) guarda los objetos, o sea todo lo que se crea con new. Es memoria dinámica y la libera el recolector de basura cuando el objeto deja de ser alcanzable.


void metodo() {
    int edad = 25;                      // el 25 vive en el STACK (primitivo local)
    Cuenta c = new Cuenta(1000);        // el objeto Cuenta vive en el HEAP
                                        // la variable c vive en el stack y guarda la referencia
}


Detalle importante: la variable c está en el stack, pero el objeto al que lleva está en el heap. Una variable de objeto nunca “contiene” el objeto.





2¿Qué copia una asignación entre variables primitivas? ¿Y entre variables de objeto?



La asignación copia siempre lo que hay en la caja de la variable, y eso cambia según la familia del tipo:


    
  
  • Primitivas: copia el valor. Quedan dos cajas independientes; cambiar una no toca la otra.
    • 
  
  • De objeto: copia la referencia (la flecha), nunca el objeto apuntado. Quedan dos variables llevando al mismo objeto, y mutarlo por una se ve desde la otra.
    • 



int a = 5;
int b = a;             // copia el VALOR
b = 99;                // a sigue valiendo 5

int[] x = {1, 2, 3};
int[] y = x;           // copia la REFERENCIA: un solo arreglo, dos nombres
y[0] = 99;             // x[0] también es 99


Cuidado con una trampa de redacción: y = new int[]{...} tampoco “copia el objeto” — crea uno nuevo y reasigna la flecha de y, dejando a x donde estaba.

Una referencia sirve para una sola cosa: acceder al objeto al que apunta. Esa restricción elimina de un plumazo toda una familia de errores clásicos de C (aritmética mal calculada, punteros colgantes, doble liberación).


Ojo con la confusión típica: cuando imprimís un objeto sin toString y ves Cuenta@65ae6ba4, eso no es una dirección de memoria — es el nombre de la clase y un código de hash en hexadecimal.





4¿Qué es null? ¿Cuándo se produce una NullPointerException y qué aporta Optional?



null es una referencia especial que no apunta a ningún objeto. Sólo las variables de tipo referencia pueden valer null; un primitivo nunca.


La NPE se produce cuando intentás usar algo sobre una referencia que vale null: llamar a un método, acceder a un campo, recorrerla, o hacer unboxing de un wrapper nulo.


String s = null;
s.length();              // NullPointerException

Integer i = null;
int n = i;               // NPE también: unboxing de null


Optional aporta que el “puede no haber valor” quede en el tipo, en vez de ser una sorpresa. El que recibe un Optional<String> ve en la firma que puede venir vacío, y la API lo obliga a decidir qué hacer en ese caso:

String texto = nombre.orElse("desconocido");      // valor por defecto
nombre.ifPresent(n -> System.out.println(n));     // sólo si hay valor


No es magia: optional.get() sobre un vacío también explota. Lo que aporta es que el caso vacío sea explícito y difícil de olvidar.





5Explicá la diferencia entre == y equals con un ejemplo donde den distinto.



== compara identidad: ¿las dos referencias llevan al mismo objeto del heap? equals compara igualdad de contenido: ¿los dos objetos valen lo mismo?


String s1 = new String("java");
String s2 = new String("java");
s1 == s2;          // false: son dos objetos distintos
s1.equals(s2);     // true:  el contenido es el mismo

Punto p1 = new Punto(1, 2);
Punto p2 = new Punto(1, 2);
p1 == p2;          // false
p1.equals(p2);     // true (un record compara por valor)


Sobre primitivos == sí compara valores y es lo correcto. Sobre objetos, == casi nunca es lo que querés — la única excepción habitual es comparar contra null, donde == es obligatorio (s == null, porque s.equals(null) explotaría).


Detalle: si tu clase no define equals, hereda el de Object, que compara por identidad — o sea, se comporta igual que ==. Por eso los record son cómodos: lo generan por valor solos.





6¿Qué es el aliasing y qué riesgo trae cuando el objeto es mutable?



Aliasing es que dos o más referencias apunten al mismo objeto: dos nombres para la misma cosa. Se produce con cualquier asignación entre variables de objeto, al pasar un objeto a un método, al guardarlo en una estructura o al devolverlo desde un getter.


Cuenta c = new Cuenta(1000);
Cuenta alias = c;               // sin new: no hay objeto nuevo
alias.depositar(500);
c.saldo();                      // 1500 — cambió "solo"


El riesgo aparece sólo si el objeto es mutable. Como todos los alias comparten el estado, una mutación hecha por cualquiera de ellos la ven todos, y el que no sabía que estaba compartiendo ve su objeto “cambiar solo”. Es difícil de rastrear porque el código que rompe las cosas puede estar muy lejos del que las lee.


Con objetos inmutables el aliasing es inofensivo: nadie puede cambiar el objeto, así que compartirlo no tiene consecuencias. Por eso String y los record se comparten sin miedo.


La defensa habitual es la copia defensiva: copiar el objeto al recibirlo en el constructor y al devolverlo en el getter, para no regalar referencias a tu estado interno.





7Si un método muta un objeto recibido por parámetro, ¿se ve afuera? ¿Y si reasigna el parámetro? ¿Por qué?



Mutar: sí se ve. Reasignar: no se ve. Y las dos cosas salen de una única regla: Java pasa siempre por valor. Lo que se copia es el contenido de la caja de la variable; para un objeto, esa caja tiene una referencia, así que se copia la flecha.


static void mutar(int[] arr)     { arr[0] = 99; }             // SÍ se ve
static void reasignar(int[] arr) { arr = new int[]{9,9,9}; }  // NO se ve


Caso mutar: el parámetro arr es una copia de la referencia, pero lleva al mismo arreglo. Dos flechas, un solo objeto. Al hacer arr[0] = 99 se modifica ese único arreglo, y cuando el frame del método muere, el llamador sigue apuntando al arreglo ya modificado.


Caso reasignar: arr = new int[]{9,9,9} cambia la copia local de la flecha. La variable del llamador no se entera de nada. Al volver, el frame muere, el arreglo nuevo queda inalcanzable (lo recolecta el GC) y afuera se sigue viendo el original.


Si querés que el método le cambie el objeto al llamador tenés dos opciones honestas: mutar el objeto recibido, o devolver el nuevo con return para que el llamador lo asigne. Por eso en Java no se puede escribir un swap(int a, int b) que funcione.





8¿Qué diferencia hay entre un objeto mutable y uno inmutable? ¿Qué ventaja tiene la inmutabilidad?



Un objeto es inmutable si su estado no cambia después de creado. Es mutable si puede cambiar. “Modificar” un inmutable en realidad significa crear uno nuevo.





  
InmutablesMutables

String s = "abc";
s.toUpperCase();        // devuelve "ABC" pero NO cambia s
s = s.toUpperCase();    // así sí: reasigno al String NUEVO


Ventajas de la inmutabilidad:


    
  
  • Se comparte sin miedo: el aliasing deja de ser peligroso, porque nadie puede cambiar el objeto. No hacen falta copias defensivas.
    • 
  
  • Es más fácil razonar: si sabés el valor con el que se creó, sabés su valor siempre. No hay que rastrear quién lo pudo haber tocado.
    • 
  
  • Sirve como clave: un objeto cuyo contenido no cambia mantiene su hashCode estable, así que se puede usar como clave de un mapa (lo vamos a necesitar en Hashing).
    • 
  
  • Es seguro entre hilos sin sincronización.
    • 



El costo es crear objetos nuevos en cada “modificación”, que es exactamente por qué existe StringBuilder para armar texto dentro de un ciclo.





9¿Qué diferencia hay entre una copia superficial y una profunda?



La diferencia sólo importa en estructuras anidadas: objetos que contienen referencias a otros objetos.


    
  
  • Copia superficial (shallow): duplica la estructura de más afuera, pero comparte los objetos internos. Los dos “contenedores” son distintos, pero apuntan a los mismos hijos.
    • 
  
  • Copia profunda (deep): duplica también los objetos internos, en todos los niveles. Queda totalmente independiente.
    • 



int[][] matriz = {{1, 2}, {3, 4}};

int[][] superficial = matriz.clone();      // comparte las filas
superficial[0][0] = 99;                    // ¡matriz[0][0] también es 99!

int[][] profunda = new int[matriz.length][];
for (int i = 0; i < matriz.length; i++)
    profunda[i] = Arrays.copyOf(matriz[i], matriz[i].length);
profunda[0][0] = 99;                       // matriz NO cambia


Trampa a tener presente: clone() sobre arreglos, Arrays.copyOf y el constructor new ArrayList<>(otra) son todos superficiales. Si adentro hay objetos mutables y necesitás independencia real, tenés que copiar cada nivel a mano.


Detalle que suele preguntarse: si los elementos internos son inmutables (por ejemplo un String[]), la copia superficial alcanza, porque nadie puede mutar los compartidos.





10¿Cuándo el recolector de basura libera un objeto? ¿Qué es una fuga de memoria lógica?



El GC libera un objeto cuando deja de ser alcanzable: cuando ya no existe ninguna cadena de referencias que llegue hasta él desde una raíz viva (una variable local en el stack, un campo estático, etc.).


var c = new Cuenta(1000);
c = new Cuenta(2000);     // la primera queda inalcanzable -> el GC la recolectará


Dos precisiones que se preguntan seguido: no hay delete ni forma de forzar la liberación, y que un objeto sea apuntado por otro objeto que también es basura no lo salva — la cadena tiene que arrancar en una raíz.


Una fuga de memoria lógica es lo contrario: un objeto que ya no usás pero que sigue siendo alcanzable, porque quedó una referencia apuntándolo. El GC no lo puede liberar, porque su criterio es la alcanzabilidad, no la utilidad. El caso típico es una estructura que crece y nunca se limpia (una caché, una lista de escuchas, una pila que al desapilar no borra la posición).


// pila con fuga: el objeto desapilado sigue referenciado por el arreglo
public Object desapilar() { return datos[--tope]; }

// sin fuga: se suelta la referencia
public Object desapilar() {
    Object o = datos[--tope];
    datos[tope] = null;        // ahora sí el GC lo puede recolectar
    return o;
}


La solución es siempre la misma: soltar la referencia, poniéndola en null o quitando el objeto de la estructura.

PistaEl swap de primitivos parece andar si imprimís adentro del método: intercambia las copias locales. El test tiene que mirar las variables de afuera. La versión que funciona muta el arreglo, porque ahí el objeto sí es compartido.

package ar.uba.fi.cb100.guia.i02_memoria.i03_medio.e01;

import java.util.Objects;

public class Swap {

    /** NO funciona: intercambia las copias locales y nada más. */
    public static void swapRoto(int a, int b) {
        int tmp = a;
        a = b;
        b = tmp;          // adentro quedaron intercambiados... y mueren acá
    }

    /** SÍ funciona: muta el arreglo, que es un objeto compartido. */
    public static void swap(int[] v, int i, int j) {
        Objects.requireNonNull(v, "el arreglo no puede ser null");
        if (i < 0 || i >= v.length || j < 0 || j >= v.length) {
            throw new IndexOutOfBoundsException("índices fuera de rango: " + i + ", " + j);
        }
        int tmp = v[i];
        v[i] = v[j];
        v[j] = tmp;
    }

    /** La otra opción honesta: devolver el par intercambiado. */
    public static int[] swapDevolviendo(int a, int b) {
        return new int[]{b, a};
    }
}

package ar.uba.fi.cb100.guia.i02_memoria.i03_medio.e02;

import java.util.Objects;

public class Duplicador {

    /** Duplica cada elemento IN PLACE: muta el arreglo recibido. */
    public static void duplicar(int[] v) {
        Objects.requireNonNull(v, "el arreglo no puede ser null");
        for (int i = 0; i < v.length; i++) {
            v[i] *= 2;
        }
    }

    /** NO funciona: x es una copia del valor de cada celda. */
    public static void duplicarRoto(int[] v) {
        for (int x : v) {
            x *= 2;          // modifica la copia local, no la celda
        }
    }

    /** Versión que no muta nada: devuelve un arreglo nuevo. */
    public static int[] duplicado(int[] v) {
        int[] r = new int[v.length];
        for (int i = 0; i < v.length; i++) r[i] = v[i] * 2;
        return r;
    }
}

    public String nombre() { return nombre; }

    public int total() {
        int s = 0;
        for (int p : puntajes) s += p;
        return s;
    }
}

package ar.uba.fi.cb100.guia.i02_memoria.i03_medio.e05;

import java.util.Arrays;
import java.util.Objects;

public class CopiaDeMatriz {

    /** Copia profunda: duplica el arreglo exterior Y cada fila. */
    public static int[][] copiaProfunda(int[][] m) {
        Objects.requireNonNull(m, "la matriz no puede ser null");
        int[][] r = new int[m.length][];
        for (int i = 0; i < m.length; i++) {
            r[i] = (m[i] == null) ? null : Arrays.copyOf(m[i], m[i].length);
        }
        return r;
    }

    /** Copia superficial: sólo el exterior. Las filas quedan compartidas. */
    public static int[][] copiaSuperficial(int[][] m) {
        return m.clone();
    }
}

import java.util.Objects;

public class ContarInalcanzables {

    /**
     * Cuántos objetos recolectaría el GC.
     * El criterio del GC es la ALCANZABILIDAD desde una raíz viva,
     * no si el objeto "sigue siendo útil" para el programa.
     */
    public static int recolectables(boolean[] alcanzable) {
        Objects.requireNonNull(alcanzable, "el arreglo no puede ser null");
        int cuenta = 0;
        for (boolean a : alcanzable) {
            if (!a) cuenta++;
        }
        return cuenta;
    }

    public static int sobrevivientes(boolean[] alcanzable) {
        return alcanzable.length - recolectables(alcanzable);
    }
}

public class ListaEnlazada {

    private Nodo primero;
    private Nodo ultimo;      // para que agregar sea O(1)
    private int tamanio;

    /** Agrega al final. O(1). */
    public void agregar(int valor) {
        Nodo nuevo = new Nodo(valor, null);
        if (primero == null) {
            primero = nuevo;
        } else {
            ultimo.siguiente(nuevo);
        }
        ultimo = nuevo;
        tamanio++;
    }

    public int tamanio()      { return tamanio; }
    public boolean estaVacia() { return tamanio == 0; }

    /** Vuelca la lista en un arreglo, recorriendo la cadena de referencias. */
    public int[] aArreglo() {
        int[] r = new int[tamanio];
        int i = 0;
        for (Nodo n = primero; n != null; n = n.siguiente()) {
            r[i++] = n.valor();
        }
        return r;
    }

    public boolean contiene(int valor) {
        for (Nodo n = primero; n != null; n = n.siguiente()) {
            if (n.valor() == valor) return true;
        }
        return false;
    }
}

package ar.uba.fi.cb100.guia.i02_memoria.i04_dificil.e02;

import ar.uba.fi.cb100.guia.i02_memoria.i04_dificil.e01.Nodo;

public class DetectorDeCiclo {

    /**
     * Liebre y tortuga (Floyd). O(n) en tiempo y O(1) en memoria.
     * Si hay ciclo, la liebre da la vuelta y alcanza a la tortuga.
     */
    public static boolean tieneCiclo(Nodo primero) {
        Nodo tortuga = primero;
        Nodo liebre = primero;

        while (liebre != null && liebre.siguiente() != null) {
            tortuga = tortuga.siguiente();               // 1 paso
            liebre = liebre.siguiente().siguiente();     // 2 pasos
            if (tortuga == liebre) return true;          // == : ¿el MISMO nodo?
        }
        return false;    // la liebre llegó al final: no había ciclo
    }

    /** Devuelve el nodo donde empieza el ciclo, o null si no hay. */
    public static Nodo inicioDelCiclo(Nodo primero) {
        Nodo tortuga = primero, liebre = primero;
        while (liebre != null && liebre.siguiente() != null) {
            tortuga = tortuga.siguiente();
            liebre = liebre.siguiente().siguiente();
            if (tortuga == liebre) {
                // segunda fase: uno vuelve al principio y avanzan a la par
                Nodo p = primero;
                while (p != tortuga) { p = p.siguiente(); tortuga = tortuga.siguiente(); }
                return p;
            }
        }
        return null;
    }
}

Alcanzabilidad (mini-GC)
Dado un grafo por matriz de adyacencia y un nodo raíz, marcá los alcanzables (recorrido) y devolvé cuáles quedarían sin marcar; test.

    

  

  
PistaEs un recorrido en profundidad (DFS) o en anchura (BFS) desde la raíz, marcando lo visitado. Lo que sobra —lo no marcado— es la basura. Dos trampas: el grafo puede tener ciclos, así que sin el arreglo de visitados entrás en recursión infinita; y un objeto apuntado sólo por basura también es basura.

  


guia/i02_memoria/i04_dificil/e05/MiniGC.java


package ar.uba.fi.cb100.guia.i02_memoria.i04_dificil.e05;

import java.util.ArrayDeque;
import java.util.Objects;

/**
 * Modelo del criterio del GC: marcar lo alcanzable desde las raíces
 * y considerar basura todo lo demás (algoritmo mark and sweep).
 */
public class MiniGC {

    /** ady[i][j] == true significa "el objeto i tiene una referencia al j". */
    public static boolean[] alcanzables(boolean[][] ady, int raiz) {
        Objects.requireNonNull(ady, "el grafo no puede ser null");
        int n = ady.length;
        if (raiz < 0 || raiz >= n) throw new IndexOutOfBoundsException("raíz inválida: " + raiz);

        boolean[] marcado = new boolean[n];
        var pendientes = new ArrayDeque<Integer>();
        marcado[raiz] = true;
        pendientes.push(raiz);

        while (!pendientes.isEmpty()) {          // recorrido iterativo: sin desbordar la pila
            int actual = pendientes.pop();
            for (int j = 0; j < n; j++) {
                if (ady[actual][j] && !marcado[j]) {   // el !marcado corta los ciclos
                    marcado[j] = true;
                    pendientes.push(j);
                }
            }
        }
        return marcado;
    }

    /** Los índices que el GC recolectaría. */
    public static int[] recolectables(boolean[][] ady, int raiz) {
        boolean[] vivo = alcanzables(ady, raiz);
        int cuenta = 0;
        for (boolean v : vivo) if (!v) cuenta++;

        int[] basura = new int[cuenta];
        int k = 0;
        for (int i = 0; i < vivo.length; i++) if (!vivo[i]) basura[k++] = i;
        return basura;
    }
}

package ar.uba.fi.cb100.guia.i02_memoria.i04_dificil.e06;

import java.util.Objects;

public class Libro {

    private final String titulo;     // puede ser null
    private final String isbn;
    private final int anio;
    private final double precio;

    public Libro(String titulo, String isbn, int anio, double precio) {
        this.titulo = titulo;

        this.anio = anio;

    }

    }

Evitar la fuga
Implementá una pila sobre arreglo donde desapilar ponga en null la posición liberada (para no retener el objeto); test que la posición quedó en null.

    

  

  
PistaEste es el ejemplo canónico de fuga lógica del Effective Java. Si desapilar hace sólo return datos[--tope];, el arreglo sigue apuntando al objeto desapilado: es alcanzable, así que el GC no lo libera, aunque el programa ya no lo use. Para poder testearlo desde afuera, exponé un método que permita ver la celda cruda.

package ar.uba.fi.cb100.guia.i02_memoria.i04_dificil.e10;

import java.util.Arrays;
import java.util.EmptyStackException;

public class PilaSinFuga<T> {

    private static final int CAPACIDAD_INICIAL = 8;

    private Object[] datos = new Object[CAPACIDAD_INICIAL];
    private int tope;

    public void apilar(T elemento) {
        if (tope == datos.length) {
            datos = Arrays.copyOf(datos, datos.length * 2);
        }
        datos[tope++] = elemento;
    }

    @SuppressWarnings("unchecked")
    public T desapilar() {
        if (tope == 0) throw new EmptyStackException();
        T elemento = (T) datos[--tope];
        datos[tope] = null;      // ← SUELTA la referencia: sin esto hay fuga lógica
        return elemento;
    }

    public int tamanio()        { return tope; }
    public boolean estaVacia()  { return tope == 0; }

    /** Sólo para los tests: mira la celda cruda del arreglo interno. */
    Object celdaCruda(int i) { return datos[i]; }
}

package ar.uba.fi.cb100.guia.i02_memoria.i04_dificil.e10;

import java.util.EmptyStackException;

/** La versión con el bug, para poder contrastarla en el test. */
public class PilaConFuga<T> {

    private final Object[] datos = new Object[8];
    private int tope;

    public void apilar(T e) { datos[tope++] = e; }

    @SuppressWarnings("unchecked")
    public T desapilar() {
        if (tope == 0) throw new EmptyStackException();
        return (T) datos[--tope];     // el arreglo SIGUE apuntando al objeto
    }

    Object celdaCruda(int i) { return datos[i]; }
}
