Objetivos de la unidad

Esta unidad te da una herramienta que vas a usar en toda la materia: medir cuánto cuesta un algoritmo. Al terminarla vas a poder: (1) contar el costo en función del tamaño de la entrada; (2) usar las cotas O, Ω y Θ; (3) calcular la complejidad de cualquier algoritmo iterativo; (4) plantear la ecuación de recurrencia de un algoritmo recursivo y resolverla con el método de expansión; (5) aplicar el Teorema Maestro completo —por sustracción y por división—, entendiendo cada caso en su árbol de recursión; (6) analizar la complejidad amortizada del vector dinámico y el efecto del criterio de redimensión; y (7) conocer la complejidad de algoritmos estándar como Quicksort.

Hasta ahora nos preguntamos si un programa anda. Desde acá nos preguntamos algo más profundo: ¿cuánto cuesta? Dos algoritmos pueden resolver el mismo problema y ser abismalmente distintos: uno tarda un segundo y el otro, siglos. Saber estimar ese costo —sin siquiera ejecutar el código— es lo que distingue a quien programa de quien diseña algoritmos.

4.1Un poco de historia

La idea de analizar algoritmos es tan vieja como los algoritmos mismos: ya en 1843 Ada Lovelace escribió el primero pensado para una máquina. La notación que usamos hoy, la “O grande”, la introdujo el matemático Paul Bachmann en 1894 y la popularizó Edmund Landau (por eso se la llama notación de Landau). Recién en 1965, Juris Hartmanis y Richard Stearns fundaron formalmente la teoría de la complejidad computacional (les valió el premio Turing). Y fue Donald Knuth, alrededor de 1976, quien estandarizó el uso de O, Ω y Θ en la computación tal como los usamos hoy.

4.2¿Por qué no medir en segundos?

Lo intuitivo sería cronometrar. Pero el tiempo en segundos depende de la máquina, del lenguaje, de qué otra cosa esté corriendo… El mismo algoritmo tarda distinto en tu notebook que en un servidor. Necesitamos una medida independiente de la máquina.

La solución: contar cuántas operaciones elementales (una suma, una comparación, un acceso a memoria) hace el algoritmo, en función del tamaño de la entrada, que llamamos n. No nos interesa el número exacto, sino cómo crece ese número cuando n crece. Esa es la complejidad temporal.

4.3Órdenes de crecimiento

Para n grande, lo único que importa es el término que más crece; las constantes y los términos menores se vuelven irrelevantes. Por eso decimos que recorrer un arreglo de n elementos “es O(n)”, sin importar si hacemos una o tres operaciones por elemento. Estos son los órdenes más frecuentes, de mejor a peor:

O(1)constanteacceder a a[i]
O(log n)logarítmicobúsqueda binaria
O(n)linealrecorrer un arreglo
O(n log n)lineal-logarítmicoMergesort, Quicksort (promedio)
O(n²)cuadráticodos bucles anidados
O(2ⁿ)exponencialFibonacci recursivo ingenuo

La diferencia no es un detalle: mirá cómo se disparan las curvas al crecer n.

Idea clave

Para n = 1 000 000, un algoritmo O(n) hace un millón de pasos; uno O(n²) hace un billón (un millón de millones). El primero corre en un instante; el segundo puede tardar horas. Elegir el algoritmo correcto importa más que cualquier micro-optimización.

4.4Las tres cotas: O, Ω y Θ

Para hablar con precisión del crecimiento usamos tres cotas. Veamos cada una por separado, con su gráfico. En los tres, las curvas son las mismas —la f(n) azul es el costo real del algoritmo, con sus irregularidades— y en los tres aparece el mismo protagonista silencioso: el punto n0.

La O grande es la cota superior: dice que la función no crece más rápido que g(n) (salvo una constante), a partir de cierto punto. Formalmente:

f(n) = O(g(n))  ⟺  ∃ c > 0, n0 > 0 :   0 ≤ f(n) ≤ c·g(n)   ∀ n ≥ n0

Mirá el papel del n0 en el gráfico: antes de él, f(n) cruza la cota varias veces —a veces gana una, a veces la otra— y no importa. La definición sólo exige que a partir de n0 la desigualdad valga siempre. Por eso la notación captura el comportamiento asintótico (para n grande) e ignora el arranque, donde mandan las constantes.

La Ω (omega) es la cota inferior: la función crece al menos tan rápido como g(n), también a partir de un n0:

f(n) = Ω(g(n))  ⟺  ∃ c > 0, n0 > 0 :   0 ≤ c·g(n) ≤ f(n)   ∀ n ≥ n0

La Θ (theta) es la cota ajustada: crece exactamente como g(n), es decir, es O(g(n)) y Ω(g(n)) a la vez. Ahora hacen falta dos constantes, y el n0 es el mayor de los dos anteriores (desde ahí valen las dos desigualdades juntas):

f(n) = Θ(g(n))  ⟺  ∃ c1, c2 > 0, n0 > 0 :   0 ≤ c2·g(n) ≤ f(n) ≤ c1·g(n)   ∀ n ≥ n0

En la práctica, O suele referirse al peor caso (la garantía: “no tardará más que esto”), Ω al mejor caso, y Θ cuando ambos coinciden. Por ejemplo, la búsqueda lineal es O(n) en el peor caso (el elemento no está o está último) y Ω(1) en el mejor (está primero).

Error común

“Peor caso” y “O” no son sinónimos, aunque en la práctica vayan juntos. El caso (mejor, promedio, peor) dice qué entrada estás considerando; la cota (O, Ω, Θ) dice cómo acotás la función que resulta. Podés perfectamente dar una O del mejor caso: la búsqueda lineal en su mejor caso es O(1). Son dos ejes independientes.

4.5Calcular la complejidad de un algoritmo iterativo

Para los algoritmos con bucles, alcanza con seguir unas pocas reglas:

1.Operación simple (asignación, comparación, acceso): O(1).
2.Secuencia de instrucciones: se suma, y domina la mayor.
3.Bucle: (cantidad de iteraciones) × (costo del cuerpo).
4.Bucles anidados: se multiplican las iteraciones.
5.Bucle que divide el rango a la mitad (i *= 2 o i /= 2): hace log2 n vueltas, o sea O(log n).
6.Al final, descartá constantes y términos menores: 3n² + 5n + 8 es O(n²).

Tres ejemplos rápidos:

// (a) O(n): un bucle de n vueltas
for (int i = 0; i < n; i++) {
    suma += a[i];
}


// (b) O(n^2): dos bucles anidados, cada uno n vueltas
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) {
        contar++;
    }


// (c) O(log n): el rango se divide por 2 en cada vuelta
for (int i = 1; i < n; i *= 2) {
    paso++;
}

4.5.1El conteo línea por línea

Antes de usar las reglas “de memoria”, conviene hacer una vez el conteo completo, línea por línea, para ver de dónde salen. Tomemos la suma de un arreglo (el código está en el repo, SumaArreglo):

static long sumar(int[] a) {
    long suma = 0;                         // L1
    for (int i = 0; i < a.length; i++) {   // L2
        suma += a[i];                      // L3
    }
    return suma;                           // L4
}

Contemos cuántas veces se ejecuta cada línea con un arreglo de n elementos:

Línea¿Qué hace?¿Cuántas veces?Costo total
L1asignación1O(1)
L2inicialización, n+1 comparaciones, n incrementos2n + 2O(n)
L3acceso + suma + asignaciónnO(n)
L4return1O(1)
Total≈ 3n + 4O(n)

Fijate el detalle de L2: la condición i < a.length se evalúa n + 1 veces (las n que da verdadera más la última que da falsa y corta). ¿Importa? No: 3n + 4, 2n + 2 o 5n son todos O(n). Éste es justamente el punto de la notación: el conteo fino sirve para entender, pero al final sólo queda el término dominante. Con esa tranquilidad, de acá en adelante aplicamos las reglas directamente.

4.5.2Un ejemplo con truco: la exponenciación rápida

¿Siempre que hay un solo bucle es O(n)? No: hay que mirar cómo cambia la variable de control. En el repo, PotenciaRapida calcula baseexp así:

public static long potencia(long base, int exp) {
    long resultado = 1;
    while (exp > 0) {                     // el exponente se divide por 2 -> O(log n)
        if ((exp & 1) == 1) {
            resultado *= base;            // si exp es impar
        }
        base *= base;
        exp >>= 1;                        // exp = exp / 2
    }
    return resultado;
}

Antes de analizarlo, dos operadores nuevos que trabajan sobre los bits del número (su escritura en binario):

  • exp & 1 es el AND bit a bit con 1: compara el último bit de exp con el 1 y deja el resto en cero. El último bit de un número binario vale 1 si el número es impar y 0 si es par (igual que en decimal el último dígito te dice si es múltiplo de 10). O sea: (exp & 1) == 1 es simplemente una forma rapidísima de preguntar “¿exp es impar?”, equivalente a exp % 2 == 1.
  • exp >>= 1 es el desplazamiento a la derecha (shift): corre todos los bits un lugar hacia la derecha y el último se cae. Tirar el último dígito en binario es dividir por 2 descartando el resto (como tachar el último dígito decimal divide por 10): equivale a exp = exp / 2 con división entera.

4.6Calcular la de un algoritmo recursivo: la ecuación de recurrencia

Cuando un algoritmo se llama a sí mismo, su costo se describe con una ecuación de recurrencia: el costo T(n) se expresa en términos del costo sobre entradas más chicas, más el trabajo hecho fuera de la recursión.

T(n) = (llamadas recursivas) + (trabajo no recursivo)

4.6.1La ecuación se lee del algoritmo

La ecuación no es magia: es la foto de la recursividad, y se lee directamente del código, renglón por renglón. Hagámoslo con el factorial (n! = n · (n−1)!):

static long factorial(int n) {
    if (n <= 1) {                     // comparar: O(1)
        return 1;                     // caso base: costo fijo        ->   T(1) = O(1)
    }
    return n * factorial(n - 1);      // UNA llamada sobre n-1        ->   T(n-1)
                                      // más 1 multiplicación         ->   + O(1)
}

Ahora leamos la ecuación mirando el código:

  • ¿Cuántas llamadas recursivas hace factorial(n)? Una sola: factorial(n - 1). ¿Sobre qué tamaño? Sobre n − 1. Eso aporta el término T(n − 1): “lo que cueste resolver el problema de tamaño n − 1, sea lo que sea”.
  • ¿Qué trabajo propio hace, fuera de esa llamada? Una comparación y una multiplicación: costo constante, O(1).
  • ¿Y el caso base? Cuando n ≤ 1 no hay recursión: T(1) = O(1).
T(n) = T(n − 1) + O(1)      T(1) = O(1) ↑ de factorial(n-1)    ↑ del if y la multiplicación

Cada pedazo de la ecuación señala un pedazo del código. Ese es el método general: contá las llamadas recursivas (coeficiente), mirá sobre qué tamaño se hacen (el argumento de T), y sumá el costo de todo lo demás. Con la misma lectura:

  • Búsqueda binaria: una llamada sobre la mitad que queda, más comparar con el del medio, O(1):   T(n) = T(n/2) + O(1).
  • Mergesort: dos llamadas, cada una sobre una mitad, más la fusión que recorre todo, O(n):   T(n) = 2 T(n/2) + O(n).

4.7Resolver recurrencias: el método de expansión

El método de expansión (o sustitución iterativa) consiste en desarrollar la recurrencia reemplazándola en sí misma, varias veces, hasta ver el patrón y llegar al caso base. Tomemos T(n) = 2 T(n/2) + n (la de Mergesort) y hagamos la operatoria reemplazo por reemplazo, sin saltear pasos.

La clave del método: la ecuación es un molde que vale para cualquier tamaño, no sólo para n. Si en T(n) = 2 T(n/2) + n ponemos n/2 donde dice n (en los tres lugares), obtenemos cuánto vale T(n/2):

T(n/2) = 2 T(n/4) + n/2
Primer reemplazo Metemos esa expresión de T(n/2) dentro de la original, y distribuimos el 2 que la multiplica:
T(n) = 2 T(n/2) + n = 2( 2 T(n/4) + n/2 ) + n = 4 T(n/4) + 2n
Fijate la cuenta fina: el 2 de afuera multiplica a los dos términos del paréntesis. Con el primero forma 4 T(n/4); con el segundo, 2 · n/2 = n, que sumado al n que ya estaba da 2n.
Segundo reemplazo Usamos el molde otra vez, ahora con n/4: T(n/4) = 2 T(n/8) + n/4. Y lo metemos donde corresponde:
T(n) = 4 T(n/4) + 2n = 4( 2 T(n/8) + n/4 ) + 2n = 8 T(n/8) + 3n
Otra vez lo mismo: el coeficiente se duplica (4 → 8) y aparece un n más en la suma (2n → 3n).
El patrón Después de k reemplazos, el coeficiente se duplicó k veces y juntamos k enes:
ReemplazosExpresión
02 T(n/2) + n
14 T(n/4) + 2n
28 T(n/8) + 3n
k2k T(n/2k) + k n
El final La expansión termina al llegar al caso base: cuando n/2k = 1, o sea cuando 2k = n, o sea cuando k = log2 n. Sustituimos esos valores en la fila del patrón:
T(n) = 2k T(1) + k n = n · T(1) + n log2 n = Θ(n log n) 2k = n  ·  T(1) = O(1)  ·  k = log₂ n

Se ve muy claro con el árbol de recursión: en cada nivel el trabajo total suma n, y hay log2 n niveles, así que el total es n log2 n.

Con la misma técnica: T(n) = T(n − 1) + n da n + (n−1) + ⋯ + 1 = Θ(n²), y T(n) = T(n/2) + 1 da Θ(log n).

4.8El Teorema Maestro por sustracción

Expandir a mano funciona, pero es tedioso. Para las familias de recurrencias más comunes hay recetas listas: los Teoremas Maestros. Hay dos, según cómo se achica el problema en cada llamada: restando un poquito (T(n − b), como el factorial) o dividiendo en partes (T(n/b), como Mergesort). Empecemos por el de sustracción, que es el más fácil de los dos, y cubre las recursiones “más parecidas a un bucle”:

T(n) = a T(n − b) + O(nk)     a > 0, b > 0

Su resultado depende de a, la cantidad de llamadas recursivas:

a < 1

T(n) = O(nk)
manda el trabajo no recursivo

a = 1

T(n) = O(nk+1)
el trabajo se repite ~n/b veces: se suma un grado

a > 1

T(n) = O(nk an/b)
exponencial

Ejemplos: T(n) = T(n − 1) + O(1) (el factorial que acabamos de plantear): a = 1, k = 0, da O(n0+1) = O(n) — razonable: n llamadas de costo constante. T(n) = T(n − 1) + O(n) da O(n²). Y T(n) = 2 T(n − 1) + O(1) da O(2n).

¿Por qué a > 1 explota? Porque restar achica el problema muy de a poco: el árbol de llamadas tiene n niveles (no log n), y si además cada llamada abre a = 2 hijas, la cantidad de nodos se duplica en cada nivel:

Éste es exactamente el drama del Fibonacci recursivo ingenuo de la Unidad 6. Su recurrencia real es T(n) = T(n − 1) + T(n − 2) + O(1) —una rama baja un escalón y la otra, dos—, que no calza literalmente en el molde a T(n − b); pero como T(n − 2) ≤ T(n − 1), vale la cota T(n) ≤ 2 T(n − 1) + O(1) = O(2n). (El valor exacto crece como φn ≈ 1.618n: un poco menos que 2n, pero exponencial al fin — igual de impracticable.)

4.9El Teorema Maestro por división

El otro molde es el de las recurrencias “divide y vencerás”, donde cada llamada parte el problema en pedazos de tamaño n/b. Acá el árbol tiene logb n niveles (mucho más bajo que el de sustracción) y el análisis es más fino: el resultado depende de una comparación de fuerzas:

T(n) = a T(n/b) + f(n)     a ≥ 1, b > 1

donde a es la cantidad de subproblemas y b cuánto se achica cada uno. La clave es comparar f(n) (el trabajo de dividir y combinar) con nlogb a:

Caso 1 — gana la recursión

si f(n) = O(nlogba − ε) para algún ε > 0:
T(n) = Θ(nlogba)

Caso 2 — empatan

si f(n) = Θ(nlogba):
T(n) = Θ(nlogba log n)

Caso 3 — gana el trabajo

si f(n) = Ω(nlogba + ε) y se cumple la condición de regularidad:
T(n) = Θ(f(n))

Un ejemplo de cada caso:

CasoRecurrenciaLa comparaciónResultado
1T(n) = 8 T(n/2) + n²log28 = 3; n² crece menos que n³Θ(n³)
2T(n) = 2 T(n/2) + n (Mergesort)log22 = 1; n empata con n¹Θ(n log n)
3T(n) = 2 T(n/2) + n²log22 = 1; n² crece más que n¹Θ(n²)

4.9.1Ver los tres casos en el árbol de recursión

El teorema puede parecer una receta mágica, pero detrás hay una intuición muy concreta: en el árbol de recursión, ¿el trabajo por nivel crece, se mantiene o se achica al bajar? Dibujemos los tres ejemplos de arriba con sus números:

Seguí las cuentas del Caso 1: la raíz trabaja n²; sus 8 hijos trabajan 8 · (n/2)² = 2n² (¡el doble!); los 64 nietos, 4n²… Cada nivel duplica al anterior, así que la suma la dominan los últimos niveles: las hojas, que son 8log2n = n³. En el Caso 2, cada nivel suma exactamente n y hay log2 n niveles: total n log n (es el árbol de Mergesort que ya expandimos a mano). En el Caso 3, cada nivel trabaja la mitad que el anterior, así que la suma n²(1 + ½ + ¼ + …) ≤ 2n² la domina la raíz. El teorema no hace más que empaquetar estas tres situaciones.

Error común

Aplicar el Teorema Maestro por división a una recurrencia que resta. Si la ecuación dice T(n − 1), el molde que corresponde es el de sustracción (4.8); el de división pide T(n/b) con b > 1. Mirá siempre el argumento de T antes de elegir la receta: ¿resta o divide?

4.11Aplicar la complejidad a lo que ya hicimos

La complejidad no es un tema aparte: atraviesa toda la materia. Cada operación de un TDA tiene su costo, y elegir la implementación correcta es elegir la complejidad correcta. Un adelanto de lo que viene:

4.12Complejidad amortizada: el caso del vector dinámico

Hay operaciones cuyo costo es casi siempre barato, pero de vez en cuando carísimo. El ejemplo estrella —que vas a usar toda la materia— es agregar al final de un arreglo que se redimensiona (la técnica que viste en la Unidad 2; en la Unidad 5 la vas a ver empaquetada como el TDA VectorDinamico, y es exactamente lo que hace el ArrayList de Java por dentro). Mientras el arreglo interno tiene lugar, agregar cuesta O(1): escribir en la próxima celda libre. Pero cuando el arreglo se llena, hay que redimensionar: crear un arreglo más grande y copiar todos los elementos, lo que cuesta O(n).

¿Decimos entonces que agregar “es O(n)”? Sería técnicamente cierto como peor caso puntual, pero injusto: castiga a todas las operaciones por lo que hacen unas pocas. La medida correcta es la complejidad amortizada: el costo total de una secuencia de n operaciones, repartido entre las n operaciones.

costo amortizado = (costo total de n operaciones) / n

4.12.1El criterio de redimensión importa: duplicar

Supongamos que cuando el arreglo se llena lo duplicamos (capacidad 1, 2, 4, 8, 16…). Mirá el costo de cada agregar en una secuencia de 20 inserciones:

Los picos naranjas son las redimensiones: la operación 17, por ejemplo, paga la copia de los 16 elementos existentes. Pero fijate la línea verde: el promedio se mantiene siempre por debajo de 3. No es casualidad. Sumemos el costo total de n inserciones: cada una paga su escritura (n en total), y las copias suman

1 + 2 + 4 + 8 + ⋯ + n/2 + n < 2n una suma geométrica: cada término es el doble del anterior, y la suma entera es menos que el doble del último

Total: menos de 3n operaciones para n inserciones, o sea menos de 3 por operación. Por eso decimos que agregar al final es O(1) amortizado: picos aislados de O(n), pero promedio constante garantizado.

4.12.2¿Y si en vez de duplicar agrandamos de a 1?

El criterio de redimensión no es un detalle. Si al llenarse el arreglo lo agrandáramos de a una celda, cada inserción redimensionaría, y la inserción i copiaría i − 1 elementos. El total sería

1 + 2 + 3 + ⋯ + (n − 1) = n(n − 1)/2 = Θ(n²)

es decir Θ(n) amortizado por operación: mil veces más lento para n = 1000. Compará los dos criterios:

Criterio de redimensiónCosto total de n insercionesAmortizado
Duplicar la capacidad (×2)< 3nO(1)
Multiplicar por 1.5O(n)O(1)
Sumar una constante (+1, +10)Θ(n²)Θ(n)

Cualquier factor multiplicativo (×2, ×1.5…) da amortizado constante, porque genera una suma geométrica; cualquier incremento aditivo da amortizado lineal, porque genera una suma aritmética. (Dato para la Unidad 5: el ArrayList de Java usa ×1.5; el VectorDinamico que vas a construir ahí usa ×2.)

Idea clave

Amortizado no es “promedio con suerte”. Es una garantía sobre el total: cualquier secuencia de n inserciones cuesta O(n), terminen donde terminen los picos. Distinto del “caso promedio” de Quicksort, que depende de la distribución de los datos: acá no hay azar, sólo contabilidad bien hecha.

4.13Medición empírica vs. teórica

Además de razonar la complejidad, podés medirla con System.nanoTime. Es útil para confirmar la teoría, pero es engañosa: la afectan el compilador JIT (que acelera el código “en caliente”), el sistema operativo y la máquina. Por eso, para comparar algoritmos, la teoría es más confiable; la medición sirve para detectar sorpresas. En el repo, Benchmark mide la suma de un arreglo para n creciente.

4.14Ejemplo integrador

Analicemos un algoritmo completo. Este cuenta cuántos pares de elementos iguales hay en un arreglo:

static int paresIguales(int[] a) {
    int pares = 0;
    for (int i = 0; i < a.length; i++)           // n vueltas
        for (int j = i + 1; j < a.length; j++)   // ~n/2 vueltas en promedio
            if (a[i] == a[j]) {
                pares++;   // O(1)
            }
    return pares;
}

Dos bucles anidados sobre n dan Θ(n²). ¿Se puede mejor? Sí: usando una tabla de hash (Unidad de Hashing) se cuenta en Θ(n). Ese salto de n² a n —que parece magia— es exactamente lo que esta unidad te enseña a ver y a buscar.

Nota

Ojo con el segundo bucle: arranca en i + 1, así que da n−1, n−2, … vueltas. El total es n(n−1)/2, que es la mitad de n² — y sigue siendo Θ(n²), porque la constante ½ se descarta. Es el mismo razonamiento de la regla 6: la constante cambia el reloj, no el orden.

4.15Errores comunes

Error común
  • Confundir “mejor/peor caso” con “O/Ω”: son cosas distintas; podés dar O del mejor caso.
  • Dejar constantes o términos menores en la respuesta final (O(2n + 3) es O(n)).
  • Sumar cuando hay que multiplicar: dos bucles anidados son n², no 2n.
  • Plantear mal la recurrencia (olvidar el trabajo no recursivo, o la cantidad de llamadas).
  • Aplicar el Teorema Maestro por división a una recurrencia que resta (T(n − 1)).
  • Creer que la medición en segundos “refuta” la teoría: mide otra cosa (incluye JIT, SO, máquina).

4.17Preguntas teóricas

1¿Por qué medimos operaciones en función de n y no en segundos?

Porque los segundos miden la máquina, no el algoritmo. El mismo código tarda distinto según el procesador, el lenguaje, la versión de la JVM, qué más esté corriendo y hasta si el JIT ya “calentó” el método. Dos mediciones del mismo programa en la misma máquina pueden diferir.

Contar operaciones elementales en función del tamaño de la entrada da una medida independiente de todo eso: es una propiedad del algoritmo, no de dónde corre. Y además permite predecir sin ejecutar: si sé que algo es O(n²), sé que multiplicar la entrada por 10 multiplica el trabajo por 100, sin necesidad de probarlo.

Esto no significa que medir no sirva: sirve para detectar sorpresas (una constante enorme, un cuello de botella inesperado). Pero para comparar algoritmos, la teoría es más confiable.

2Definí O, Ω y Θ. ¿Cuál se asocia al peor caso?
CotaQué diceDefinición
O(g(n))cota superior: no crece más rápido∃ c, n0 : f(n) ≤ c·g(n) ∀ n ≥ n0
Ω(g(n))cota inferior: crece al menos así∃ c, n0 : f(n) ≥ c·g(n) ∀ n ≥ n0
Θ(g(n))cota ajustada: crece exactamente asílas dos a la vez, con c1 y c2

La que se asocia al peor caso es la O, porque es la que da una garantía: “no va a tardar más que esto”. Ω se asocia al mejor caso y Θ a cuando los dos coinciden.

Pero ojo con la trampa: caso y cota son ejes independientes. El “caso” dice qué entrada considerás; la “cota” dice cómo acotás la función resultante. Podés dar la O del mejor caso (la búsqueda lineal en su mejor caso es O(1)) o la Θ del peor. La asociación habitual es una costumbre, no una regla.

Los tres n0 pueden ser distintos, y nada de lo que pasa antes de n0 importa: por eso son cotas asintóticas.

3¿Cómo se calcula la complejidad de dos bucles anidados? ¿Y de uno que hace i *= 2?

Anidados: se multiplican. El interno corre entero por cada vuelta del externo.

for (int i = 0; i < n; i++)        // n vueltas
    for (int j = 0; j < n; j++)    // n vueltas CADA VEZ
        op();                      // n × n = O(n²)

Tres advertencias que cambian el resultado:

  • Si el interno va hasta i, el total es n(n−1)/2 — que sigue siendo O(n²), porque ½ es constante.
  • Si el interno tiene un largo fijo (100), es O(n): anidado no implica cuadrático.
  • Si están en secuencia y no anidados, se suman: O(n), no O(n²).

i *= 2: es O(log n). La variable no avanza de a uno sino que se multiplica: toma 1, 2, 4, 8, 16… El bucle corta cuando 2k ≥ n, o sea a las k = log2 n vueltas.

La intuición: “¿cuántas veces puedo duplicar 1 antes de pasar n?”. Para n = 1 000 000, unas 20 vueltas. Por eso los algoritmos logarítmicos son tan buenos: multiplicar la entrada por mil agrega apenas 10 pasos.

4Planteá la ecuación de recurrencia de la búsqueda binaria y de Mergesort.

La receta es siempre la misma: contá las llamadas (el coeficiente), mirá sobre qué tamaño se hacen (el argumento de T), y sumá el trabajo no recursivo.

Búsqueda binaria. Compara con el del medio (O(1)) y sigue en una mitad:

T(n) = T(n/2) + O(1)  →  Θ(log n)

Mergesort. Parte en dos mitades, se llama en cada una, y después fusiona recorriendo los n elementos:

T(n) = 2 T(n/2) + O(n)  →  Θ(n log n)

La diferencia está en los dos números: el coeficiente (1 vs 2 llamadas) y el trabajo propio (O(1) vs O(n)). Cambiar cualquiera de los dos cambia el resultado — compará con T(n) = 2T(n/2) + O(1), que da Θ(n).

Un error habitual: escribir T(n) = T(n/2) + O(n) para Mergesort “porque parte a la mitad”. No: se llama dos veces, y esa es la razón de que aparezca el n multiplicando al log.

5Resolvé T(n) = 2T(n/2) + n con el método de expansión.

La idea: tratar la ecuación como un molde y reemplazarla en sí misma hasta ver el patrón.

El molde con n/2:   T(n/2) = 2T(n/4) + n/2

Primer reemplazo:

T(n) = 2( 2T(n/4) + n/2 ) + n
     = 4T(n/4) + 2·(n/2) + n
     = 4T(n/4) + n + n  =  4T(n/4) + 2n

Segundo reemplazo (con T(n/4) = 2T(n/8) + n/4):

T(n) = 4( 2T(n/8) + n/4 ) + 2n
     = 8T(n/8) + 4·(n/4) + 2n  =  8T(n/8) + 3n

El patrón tras k reemplazos:   T(n) = 2k T(n/2k) + k·n

El final. La expansión termina en el caso base: n/2k = 1 ⟹ 2k = n ⟹ k = log2 n. Sustituyendo:

T(n) = n · T(1) + n log2 n = Θ(n log n)

Verificación por el otro camino: Teorema Maestro por división con a = 2, b = 2 ⟹ log22 = 1, y f(n) = n empata con n¹ ⟹ caso 2 ⟹ Θ(n log n). ✓ Cuando los dos métodos aplican, tienen que coincidir; si no, hay un error en algún lado.

6Enunciá los tres casos del Teorema Maestro y dá un ejemplo de cada uno.

Para T(n) = a T(n/b) + f(n) con a ≥ 1, b > 1, todo se decide comparando f(n) con nlogba — el costo que tendría la recursión sola:

CasoCondiciónResultadoEjemplo
1f(n) crece menosΘ(nlogba)8T(n/2) + n² → Θ(n³)
2empatanΘ(nlogba log n)2T(n/2) + n → Θ(n log n)
3f(n) crece más (+ regularidad)Θ(f(n))2T(n/2) + n² → Θ(n²)

Qué los distingue en el árbol, que es la intuición detrás de la receta: caso 1, el trabajo por nivel crece al bajar, así que mandan las hojas; caso 2, todos los niveles trabajan lo mismo y hay log n; caso 3, el trabajo por nivel se achica, así que manda la raíz.

Y el otro teorema. Para T(n) = a T(n − b) + O(nk) todo depende de a: si a = 1, O(nk+1) (se suma un grado, porque hay ~n/b llamadas encadenadas); si a > 1, O(nk an/b), exponencial — porque el árbol tiene n niveles y además se ramifica.

La pregunta que decide cuál usar: ¿el argumento de T resta o divide?

7¿Qué complejidad tiene Quicksort en promedio y en el peor caso? ¿Por qué?

Promedio O(n log n), peor caso O(n²), y la diferencia está toda en dónde cae el pivote.

Promedio: el pivote parte el arreglo en dos mitades parecidas. Cada llamada hace la partición recorriendo todo (O(n)) y se llama en las dos mitades:

T(n) = 2 T(n/2) + O(n) = O(n log n)

Peor caso: el pivote es siempre el menor o el mayor (pasa con un arreglo ya ordenado si tomás el último como pivote). La partición queda en 1 y n−1: en vez de dividir, resta.

T(n) = T(n − 1) + O(n) = O(n²)

Fijate que cambia el teorema aplicable: el caso bueno es por división y el malo por sustracción. Ese es el punto fino del ejercicio.

Y sin embargo, en la práctica suele ser el más rápido de los O(n log n), por sus constantes pequeñas: trabaja in situ (no reserva un arreglo auxiliar como Mergesort) y aprovecha bien la caché. Las implementaciones reales evitan el peor caso eligiendo el pivote con mediana de tres o al azar.

La moraleja: la notación asintótica dice cómo escala, no cuál es más rápido para tu n. Las constantes importan cuando los órdenes empatan.

8¿Por qué la medición empírica del tiempo puede ser engañosa?

Porque mide muchas cosas además del algoritmo. Los sospechosos habituales:

  • El compilador JIT. La JVM interpreta el código al principio y lo compila a nativo cuando detecta que se usa mucho. Las primeras corridas pueden ser diez veces más lentas que las siguientes. Si medís una sola vez, medís el arranque.
  • El recolector de basura. Si corre justo en el medio de tu medición, agrega tiempo que no es tuyo.
  • El sistema operativo. Tu proceso comparte el procesador; una actualización en segundo plano te arruina la medición.
  • La caché. Un algoritmo con peor complejidad puede ganar si sus accesos a memoria son contiguos.
  • n demasiado chico. Con n = 100, un O(n²) con constantes chicas puede ganarle a un O(n log n) con constantes grandes. El cruce recién aparece para n grande — que es de lo que habla la notación asintótica.

Cómo medir mejor, si hay que hacerlo: calentar con varias corridas previas, repetir muchas veces y tomar la mediana, probar con varios n y mirar la forma de la curva (no un número suelto).

La medición no refuta la teoría: mide otra cosa. Sirve para detectar sorpresas, no para decidir qué algoritmo escala mejor.

9¿Qué complejidad tiene el Fibonacci recursivo ingenuo y por qué? ¿Cómo mejorarla?

O(2n) — exponencial. El código es engañosamente simple:

static long fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);       // DOS llamadas, y apenas se achican
}

La recurrencia es T(n) = T(n−1) + T(n−2) + O(1). Como T(n−2) ≤ T(n−1), vale la cota T(n) ≤ 2T(n−1) + O(1), que por el Teorema Maestro por sustracción con a = 2 > 1 da O(2n).

Por qué explota: el problema se achica restando (árbol de n niveles, no log n) y encima cada llamada abre dos. La causa concreta es que recalcula lo mismo una y otra vez: fib(5) calcula fib(3) dos veces, fib(2) tres veces…

(El valor exacto crece como φn ≈ 1.618n: menos que 2n, pero exponencial igual.)

Las tres mejoras, de menor a mayor:

  1. Memoización — guardar los ya calculados en un arreglo: cada valor se calcula una vez. O(n).
  2. Iterativo — llevar sólo los dos últimos y correrlos. O(n) tiempo y O(1) espacio: la mejor relación costo/complejidad de código.
  3. Exponenciación de matrices o fast doubling — O(log n), aprovechando la misma idea de la potencia rápida (4.5.2). Es el ejercicio 9 del nivel difícil.

La diferencia práctica no es menor: fib(50) ingenuo hace ~25 mil millones de llamadas; el iterativo, 50 sumas.

O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2n)

Para verlo con números, n = 1 000 000 a mil millones de operaciones por segundo:

Suma O(n)

long sumar(int[] a); comentá que es O(n). Test.

PistaUn bucle de n vueltas con cuerpo constante. Usá long para el acumulador: sumar muchos int grandes desborda sin avisar.
/** O(n): un recorrido, cuerpo O(1). */
public static long sumar(int[] a) {
    long suma = 0;                      // O(1)
    for (int x : a) {                   // n vueltas
        suma += x;                      // O(1)
    }
    return suma;                        // O(1)
}
// Total: 1 + n·1 + 1 = O(n)

El análisis, con las reglas: una asignación O(1), un bucle de n vueltas con cuerpo O(1) (regla 3: n × 1), y un return O(1). La secuencia se suma y domina la mayor (regla 2): O(n).

Y no se puede mejor: hay que mirar los n elementos al menos una vez. Cuando la salida depende de toda la entrada, Ω(n) es el piso. Éste es en realidad Θ(n).

@Test void sumaCorrecta() {
    assertEquals(10, sumar(new int[]{1, 2, 3, 4}));
    assertEquals(0, sumar(new int[0]));         // el borde
    assertEquals(-5, sumar(new int[]{-5}));
}

@Test void noDesbordaConValoresGrandes() {
    int[] grandes = {Integer.MAX_VALUE, Integer.MAX_VALUE};
    assertEquals(4294967294L, sumar(grandes));  // con int daría -2
}
El segundo test es el que justifica el long. Con un acumulador int pasa el primer test y falla el segundo — en silencio, devolviendo un negativo.
2
Pares iguales O(n²)

int paresIguales(int[] a) con dos bucles anidados; test.

PistaEl bucle interno tiene que arrancar en i + 1, no en 0: si no, contás cada par dos veces y también comparás cada elemento consigo mismo.
/** Θ(n²): dos bucles anidados; el interno da n−i−1 vueltas. */
public static int paresIguales(int[] a) {
    int pares = 0;
    for (int i = 0; i < a.length; i++)           // n vueltas
        for (int j = i + 1; j < a.length; j++)   // n−i−1 vueltas
            if (a[i] == a[j]) {
                pares++;                         // O(1)
            }
    return pares;
}

El conteo exacto: el interno da n−1, n−2, …, 1, 0 vueltas. Total n(n−1)/2, que es la mitad de n²… y sigue siendo Θ(n²), porque la constante ½ se descarta (regla 6).

Por qué j = i + 1: con j = 0 compararías a[i] consigo mismo (siempre igual) y contarías el par (2,5) también como (5,2). El resultado saldría mal, no sólo más lento.

¿Se puede mejor? Sí, Θ(n) con una tabla de hash: contás cuántas veces aparece cada valor y por cada grupo de k repetidos sumás k(k−1)/2. Es el salto de n² a n que menciona 4.14.

@Test void cuentaPares() {
    assertEquals(0, paresIguales(new int[]{1, 2, 3}));
    assertEquals(1, paresIguales(new int[]{1, 2, 1}));
    assertEquals(3, paresIguales(new int[]{7, 7, 7}));   // (0,1) (0,2) (1,2)
    assertEquals(6, paresIguales(new int[]{5, 5, 5, 5})); // 4·3/2
}
3
Máximo O(n)

int maximo(int[] a); test (incluí el caso de un solo elemento).

PistaArrancá con a[0] y no con Integer.MIN_VALUE. Y decidí qué hacer con el arreglo vacío antes de escribir el bucle.
/** O(n): un solo recorrido, comparación O(1) por elemento. */
public static int maximo(int[] a) {
    if (a == null || a.length == 0) {
        throw new IllegalArgumentException("no hay máximo de un arreglo vacío");
    }
    int max = a[0];                     // arranca con un elemento REAL
    for (int i = 1; i < a.length; i++) {// n−1 vueltas
        if (a[i] > max) {
            max = a[i];
        }
    }
    return max;
}

n−1 comparaciones, cada una O(1): O(n). Y es Θ(n) porque no hay forma de encontrar el máximo sin mirar todos — si salteás uno, podría ser justo el más grande.

Por qué lanzar en vez de devolver Integer.MIN_VALUE: ese valor es ambiguo —podría ser un máximo legítimo— y el error aparecería mucho después, lejos de la causa.

/** O(log n): el número se divide por 10 en cada vuelta (log₁₀ n vueltas). */
public static int cantidadDigitos(int n) {
    if (n == 0) {
        return 1;                       // el 0 tiene un dígito
    }
    n = Math.abs(n);                    // el signo no es un dígito
    int digitos = 0;
    while (n > 0) {                     // log₁₀ n vueltas

        n /= 10;

    return digitos;

Por qué es logarítmico: cada vuelta divide por 10, así que la cantidad de vueltas es ⌊log10 n⌋ + 1. Para n = 1 000 000 son 7 vueltas, no un millón.

Invertir O(n)

PistaCon dos índices que caminan desde los extremos hacia el centro alcanza n/2 vueltas. Y decidí si devolvés uno nuevo o modificás el original — no es lo mismo.
/** O(n): n/2 intercambios, cada uno O(1). Devuelve un arreglo NUEVO. */
public static int[] invertir(int[] a) {
    int[] r = a.clone();                // O(n)
    int i = 0, j = r.length - 1;
    while (i < j) {                     // n/2 vueltas
        int tmp = r[i];
        r[i] = r[j];
        r[j] = tmp;
        i++;
        j--;
    }
    return r;
}

n/2 vueltas más el clone que es O(n): total O(n). La constante ½ no cambia el orden.

La decisión de diseño: devolver uno nuevo (como acá) o invertir in situ. La versión pura no sorprende a nadie —el llamador conserva su arreglo— pero usa O(n) de memoria extra; la in situ usa O(1) pero muta el argumento, que es justo el aliasing de la Unidad 2. Las dos son válidas; lo que no vale es no decidirlo y que el llamador se entere por las malas.

Potencia rápida O(log n)

PistaEs el algoritmo de 4.5.2. La idea: b13 = b8 · b4 · b1 — los bits en 1 de 13 te dicen qué cuadrados multiplicar.
/** O(log exp): el exponente se divide por 2 en cada vuelta. */
public static long potencia(long base, int exp) {
    if (exp < 0) throw new IllegalArgumentException("exponente negativo");
    long resultado = 1;
    while (exp > 0) {
        if ((exp & 1) == 1) {           // ¿el bit actual está en 1?
            resultado *= base;
        }
        base *= base;                   // el siguiente cuadrado
        exp >>= 1;                      // exp = exp / 2
    }
    return resultado;
}

Por qué funciona: escribí el exponente en binario. 13 = 11012 = 8 + 4 + 1, así que b13 = b8 · b4 · b1. El bucle va generando b, b², b⁴, b⁸… (elevando al cuadrado) y multiplica al resultado sólo los que corresponden a un bit en 1.

El costo: tantas vueltas como bits tiene exp, o sea ⌊log2 exp⌋ + 1: O(log n). Para exp = 1000, 10 vueltas contra las 1000 de la versión lenta.

La versión recursiva deja la recurrencia a la vista:

    if (exp == 0) return 1;
    long mitad = potenciaRec(base, exp / 2);
    return (exp % 2 == 0) ? mitad * mitad : mitad * mitad * base;
}

Ojo con el error clásico de la versión recursiva: escribir potenciaRec(base, exp/2) * potenciaRec(base, exp/2) llamando dos veces. Eso da T(n) = 2T(n/2) + O(1) = O(n) — perdés todo el beneficio. Guardá el resultado en una variable.

Bubble sort O(n²)

PistaAgregale una bandera que corte si en una pasada no hubo ningún intercambio. Eso cambia el mejor caso, no el peor.
/** Peor y promedio O(n²); mejor caso O(n) gracias a la bandera. */
public static void ordenar(int[] a) {
    for (int i = 0; i < a.length - 1; i++) {
        boolean hubo = false;
        for (int j = 0; j < a.length - 1 - i; j++) {   // los últimos i ya están
            if (a[j] > a[j + 1]) {
                int t = a[j]; a[j] = a[j + 1]; a[j + 1] = t;
                hubo = true;
            }
        }
        if (!hubo) return;              // ya estaba ordenado: corta
    }
}

El análisis. Sin la bandera, el interno da n−1, n−2, …, 1 vueltas: total n(n−1)/2 = Θ(n²) siempre. Con la bandera, si el arreglo ya viene ordenado la primera pasada no intercambia nada y corta: mejor caso O(n).

El - i del interno es la otra optimización: después de la pasada i, los i últimos ya están en su lugar definitivo (por eso “burbujean”). Ahorra la mitad de las comparaciones — y no cambia el orden.

Es Θ(n²) en el peor caso (arreglo al revés) y no hay forma de mejorarlo con este esquema: sólo compara vecinos, así que mover un elemento k posiciones requiere k intercambios.

Insertion sort O(n²)

Test que ordena; comentá el mejor caso O(n).

PistaEs como ordenar cartas en la mano: tomás la siguiente y la corrés hacia atrás hasta que quede en su lugar.
/** Peor y promedio O(n²); mejor caso O(n) si ya viene ordenado. */
public static void ordenar(int[] a) {
    for (int i = 1; i < a.length; i++) {
        int actual = a[i];
        int j = i - 1;
        while (j >= 0 && a[j] > actual) {   // corre los mayores a la derecha
            a[j + 1] = a[j];
            j--;
        }
        a[j + 1] = actual;                  // lo deja en su lugar
    }
}

El mejor caso es genuinamente O(n), y no por un truco: si el arreglo ya está ordenado, la condición a[j] > actual falla de entrada en cada vuelta, el while no se ejecuta nunca y queda un solo recorrido. En el peor (al revés), el while recorre todo lo anterior: 1 + 2 + … + (n−1) = Θ(n²).

Por qué importa este algoritmo a pesar de ser cuadrático:

  • Es adaptativo: con datos casi ordenados se acerca a lineal. Los otros O(n²) no.
  • Es estable: no reordena elementos iguales entre sí (el > estricto es la clave — con >= dejaría de serlo).
  • Sus constantes son chicas, así que gana para n chico. Por eso las implementaciones reales de Quicksort y Mergesort cambian a insertion sort cuando el subarreglo baja de ~10 elementos.

Mergesort O(n log n)

Con su recurrencia comentada; test.

PistaDos partes: partir (trivial) y fusionar (donde está el trabajo). La fusión recorre los dos mitades en paralelo con dos índices.
/** T(n) = 2T(n/2) + O(n)  ->  Θ(n log n) por Teorema Maestro (caso 2). */
public static void ordenar(int[] a) {
    if (a.length > 1) {
        mergesort(a, 0, a.length - 1);
    }
}

private static void mergesort(int[] a, int izq, int der) {
    if (izq >= der) return;                    // caso base: 0 o 1 elemento
    int medio = izq + (der - izq) / 2;
    mergesort(a, izq, medio);                  // T(n/2)
    mergesort(a, medio + 1, der);              // T(n/2)
    fusionar(a, izq, medio, der);              // O(n)
}

private static void fusionar(int[] a, int izq, int medio, int der) {
    int[] tmp = new int[der - izq + 1];
    int i = izq, j = medio + 1, k = 0;

    while (i <= medio && j <= der) {           // mientras queden en las dos
        tmp[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];   // <= mantiene la estabilidad
    }
    while (i <= medio) tmp[k++] = a[i++];      // lo que sobró de la izquierda
    while (j <= der)   tmp[k++] = a[j++];      // ...o de la derecha

    System.arraycopy(tmp, 0, a, izq, tmp.length);
}

La recurrencia, leída del código: dos llamadas (2T) sobre la mitad (n/2), más la fusión que recorre los n elementos (O(n)). Teorema Maestro: log22 = 1, f(n) = n empata ⟹ caso 2 ⟹ Θ(n log n). Es exactamente la recurrencia que expandimos a mano en 4.7. ✓

Las virtudes: Θ(n log n) garantizado —mejor, promedio y peor, sin sorpresas como Quicksort— y estable (por el <= de la fusión: ante empate toma el de la izquierda).

El costo: usa O(n) de memoria auxiliar. Quicksort ordena in situ, y por eso en la práctica suele ganar aunque tenga peor caso cuadrático.

@Test void ordenaBien() {

PistaAntes de resolverlo, adiviná el resultado: dos llamadas sobre la mitad con trabajo constante. ¿Da log n o n? La respuesta sorprende a mucha gente.
/** T(n) = 2T(n/2) + O(1)  ->  Θ(n). ¡NO es logarítmico! */
public static int maximo(int[] a) {
    if (a == null || a.length == 0) {
        throw new IllegalArgumentException("arreglo vacío");
    }
    return maximo(a, 0, a.length - 1);
}

private static int maximo(int[] a, int izq, int der) {
    if (izq == der) {
        return a[izq];                          // caso base: un elemento
    }
    int medio = izq + (der - izq) / 2;
    int maxIzq = maximo(a, izq, medio);         // T(n/2)
    int maxDer = maximo(a, medio + 1, der);     // T(n/2)
    return Math.max(maxIzq, maxDer);            // O(1)
}

El resultado es Θ(n), no Θ(log n), y ahí está toda la gracia del ejercicio. Teorema Maestro: a = 2, b = 2 ⟹ log22 = 1; f(n) = 1 = n0 crece menos que n¹ ⟹ caso 1 ⟹ Θ(n).

La intuición: el árbol tiene n hojas (una por elemento) y hay que visitarlas todas — no podés saber cuál es el máximo sin mirar cada elemento. Los niveles de arriba son despreciables; mandan las hojas. Eso es el caso 1.

Comparalo con la búsqueda binaria (T(n) = T(n/2) + O(1), que sí da log n): la diferencia es el coeficiente. La binaria descarta media entrada; ésta recorre las dos mitades. Descartar es lo que da el logaritmo, no dividir.

Conclusión práctica: acá divide y vencerás no mejora nada frente al bucle simple del nivel fácil —las dos son Θ(n)— y encima gasta O(log n) de stack. Sirve para entender el teorema, no para usarlo así.

En un arreglo ordenado, contar cuántas veces aparece x con dos búsquedas binarias (primera y última posición); test.

PistaLa binaria común devuelve cualquiera de las apariciones. Para la primera, cuando encontrás no cortes: seguí buscando hacia la izquierda.
/** O(log n): dos binarias, 2·log n = O(log n). */
public static int contar(int[] a, int x) {
    int primera = primeraPosicion(a, x);
    if (primera == -1) return 0;
    return ultimaPosicion(a, x) - primera + 1;
}

private static int primeraPosicion(int[] a, int x) {
    int izq = 0, der = a.length - 1, resultado = -1;
    while (izq <= der) {
        int medio = izq + (der - izq) / 2;
        if (a[medio] == x) {
            resultado = medio;          // lo anoto...
            der = medio - 1;            // ...pero sigo buscando MÁS a la izquierda
        } else if (a[medio] < x) izq = medio + 1;
        else                     der = medio - 1;
    }
    return resultado;
}

private static int ultimaPosicion(int[] a, int x) {
    int izq = 0, der = a.length - 1, resultado = -1;
    while (izq <= der) {
        int medio = izq + (der - izq) / 2;
        if (a[medio] == x) {
            resultado = medio;
            izq = medio + 1;            // sigo hacia la DERECHA
        } else if (a[medio] < x) izq = medio + 1;
        else                     der = medio - 1;
    }
    return resultado;
}

El truco está en no cortar al encontrar: anotás la posición y seguís buscando en la mitad que corresponde. Cada búsqueda sigue siendo O(log n) porque el rango se sigue partiendo al medio; dos búsquedas son 2 log n = O(log n).

Por qué importa: la solución ingenua —encontrar uno y expandirse hacia los costados— es O(n) en el peor caso, cuando todos los elementos son x. Este algoritmo es O(log n) siempre, sin importar cuántas repeticiones haya. Es el mismo salto que hay entre la búsqueda lineal y la binaria, aplicado dos veces.

PistaA diferencia de bubble e insertion, acá no hay atajo posible. Preguntate si podés saber cuál es el mínimo del resto sin recorrerlo entero.
/** Θ(n²) SIEMPRE: mejor, promedio y peor. No hay atajo. */
public static void ordenar(int[] a) {
    for (int i = 0; i < a.length - 1; i++) {
        int minimo = i;
        for (int j = i + 1; j < a.length; j++) {   // busca el mínimo del resto
            if (a[j] < a[minimo]) {
                minimo = j;

Con partición de Lomuto; comentá promedio O(n log n) y peor O(n²); test.

PistaLomuto: tomás el último como pivote y llevás un índice i con la frontera de “los menores”. Al final intercambiás el pivote a su lugar.
/** Promedio T(n) = 2T(n/2) + O(n) -> O(n log n).
 *  Peor    T(n) = T(n−1) + O(n)   -> O(n²).   ¡Cambia el teorema aplicable! */
public static void ordenar(int[] a) {
    quicksort(a, 0, a.length - 1);
}

private static void quicksort(int[] a, int izq, int der) {
    if (izq >= der) return;
    int p = particionar(a, izq, der);       // O(n)
    quicksort(a, izq, p - 1);
    quicksort(a, p + 1, der);
}

/** Partición de Lomuto: el pivote es el último. */
private static int particionar(int[] a, int izq, int der) {
    int pivote = a[der];
    int i = izq - 1;                        // frontera de "los menores"
    for (int j = izq; j < der; j++) {
        if (a[j] <= pivote) {
            i++;
            int t = a[i]; a[i] = a[j]; a[j] = t;
        }
    }
    int t = a[i + 1]; a[i + 1] = a[der]; a[der] = t;   // el pivote a su lugar
    return i + 1;
}

Las dos recurrencias. Si el pivote parte en mitades: T(n) = 2T(n/2) + O(n) ⟹ caso 2 del teorema por división ⟹ O(n log n). Si el pivote es siempre el extremo: T(n) = T(n−1) + O(n) ⟹ teorema por sustracción con a = 1, k = 1 ⟹ O(n2).

El detalle cruel: con Lomuto y pivote al final, el peor caso ocurre justamente con el arreglo ya ordenado — el caso que uno esperaría que fuera el fácil. Cada partición deja 0 elementos de un lado y n−1 del otro.

Cómo lo evitan las implementaciones reales: eligen el pivote con mediana de tres (primero, medio, último) o al azar. Con pivote aleatorio, el peor caso deja de depender de la entrada y pasa a ser improbable.

PistaEs Quicksort, pero recursando en un solo lado: el que contiene la posición que buscás. Ese cambio es el que baja de n log n a n.
/** Promedio T(n) = T(n/2) + O(n) -> O(n). Peor caso O(n²). */
public static int kesimoMenor(int[] a, int k) {
    if (a == null || k < 1 || k > a.length) {
        throw new IllegalArgumentException("k fuera de rango: " + k);
    }
    int[] copia = a.clone();            // no mutamos el argumento
    int izq = 0, der = copia.length - 1, buscado = k - 1;

    while (izq <= der) {
        int p = particionar(copia, izq, der);
        if (p == buscado)      return copia[p];
        else if (p < buscado)  izq = p + 1;     // sólo la derecha
        else                   der = p - 1;     // sólo la izquierda
    }
    throw new IllegalStateException("inalcanzable");
}

Mergesort iterativo (bottom-up)

Sin recursión; test que ordena.

PistaAl revés que el recursivo: en vez de partir hasta abajo, arrancá fusionando de a 1, después de a 2, de a 4… El ancho se duplica.
/** O(n log n): log n pasadas (el ancho se duplica) × O(n) cada una. */
public static void ordenar(int[] a) {
    int n = a.length;
    for (int ancho = 1; ancho < n; ancho *= 2) {        // log₂ n pasadas
        for (int izq = 0; izq < n - ancho; izq += 2 * ancho) {   // O(n) por pasada
            int medio = izq + ancho - 1;
            int der = Math.min(izq + 2 * ancho - 1, n - 1);
            fusionar(a, izq, medio, der);
        }
    }
}

El análisis es directo, sin recurrencia: el bucle externo duplica ancho, así que da log2 n vueltas (regla 5). El interno recorre el arreglo entero fusionando pares de bloques: O(n). Total O(n log n) — el mismo resultado que el recursivo, obtenido con las reglas de 4.5 en vez del Teorema Maestro. Es una buena verificación de que las dos herramientas son consistentes.

Las ventajas sobre el recursivo: usa O(1) de stack (no hay llamadas) y recorre la memoria de forma más predecible. La desventaja: el manejo de índices es mucho más delicado.

Los dos bordes que hay que cuidar, y que son donde falla: el Math.min del der (el último bloque puede estar incompleto si n no es potencia de 2) y la condición izq < n - ancho (si no queda un segundo bloque para fusionar, no hay nada que hacer).

Contar inversiones O(n log n)

Con una variante de Mergesort; test contra el conteo ingenuo.

PistaUna inversión es un par i < j con a[i] > a[j]. Durante la fusión, cuando tomás un elemento de la mitad derecha, ése es menor que todos los que quedan en la izquierda.
/** O(n log n): es Mergesort con un contador. Misma recurrencia. */
public static long contarInversiones(int[] a) {
    return contar(a.clone(), 0, a.length - 1);
}

private static long contar(int[] a, int izq, int der) {
    if (izq >= der) return 0;
    int medio = izq + (der - izq) / 2;
    long inv = contar(a, izq, medio)            // T(n/2)
             + contar(a, medio + 1, der);       // T(n/2)
    return inv + fusionarContando(a, izq, medio, der);   // O(n)
}

private static long fusionarContando(int[] a, int izq, int medio, int der) {
    int[] tmp = new int[der - izq + 1];
    int i = izq, j = medio + 1, k = 0;
    long inv = 0;

    while (i <= medio && j <= der) {
        if (a[i] <= a[j]) {
            tmp[k++] = a[i++];
        } else {
            // a[j] es menor que a[i] Y que TODOS los que siguen en la izquierda
            inv += (medio - i + 1);             // <- el corazón del algoritmo
            tmp[k++] = a[j++];
        }
    }
    while (i <= medio) tmp[k++] = a[i++];
    while (j <= der)   tmp[k++] = a[j++];
    System.arraycopy(tmp, 0, a, izq, tmp.length);
    return inv;
}

La idea clave está en esa línea: durante la fusión, las dos mitades ya están ordenadas. Si a[j] (derecha) es menor que a[i] (izquierda), entonces es menor que a[i] y que todos los que le siguen — o sea medio - i + 1 inversiones de un saque, en vez de contarlas de a una.

La complejidad no cambia respecto de Mergesort: la misma recurrencia T(n) = 2T(n/2) + O(n), porque el contador es O(1) por paso. El salto es frente al algoritmo ingenuo —comparar todos los pares, Θ(n²)— y es exactamente el tipo de mejora que esta unidad enseña a buscar.

Para qué sirve: mide “cuán desordenado” está algo. Se usa para comparar rankings (el coeficiente tau de Kendall) y en sistemas de recomendación.

Kadane O(n)

int maxSubarreglo(int[] a) (suma máxima de un subarreglo contiguo); test.

PistaEn cada posición hay una sola decisión: ¿extiendo el subarreglo que venía, o arranco uno nuevo acá? Conviene arrancar de nuevo cuando lo acumulado es negativo.
/** O(n): un recorrido, O(1) por elemento. El ingenuo es O(n³) y el mejorado O(n²). */
public static int maxSubarreglo(int[] a) {
    if (a == null || a.length == 0) {
        throw new IllegalArgumentException("arreglo vacío");
    }
    int mejorAca = a[0];        // mejor suma que TERMINA en la posición actual
    int mejorGlobal = a[0];     // mejor suma vista hasta ahora

    for (int i = 1; i < a.length; i++) {
        mejorAca = Math.max(a[i], mejorAca + a[i]);   // ¿arranco de nuevo o extiendo?
        mejorGlobal = Math.max(mejorGlobal, mejorAca);
    }
    return mejorGlobal;
}

Toda la magia está en esa línea. mejorAca responde: “¿cuál es la mejor suma de un subarreglo que termina justo acá?”. Sólo hay dos candidatos: el elemento solo, o lo que venía más el elemento. Si lo que venía era negativo, arrastrarlo sólo resta, así que conviene empezar de cero.

La progresión completa del problema, que es lo que lo hace un clásico:

Ingenuotodos los pares (i,j), sumar cada tramoO(n³)

Búsqueda en arreglo rotado O(log n)

Buscar x en un arreglo ordenado y rotado; test.

PistaAl partir al medio, siempre una de las dos mitades está bien ordenada. Identificá cuál, fijate si x cae en su rango, y descartá la otra.
/** O(log n): descarta media entrada por vuelta, igual que la binaria común.
 *  Ejemplo de rotado: {4,5,6,7,0,1,2} (ordenado y "cortado" en algún punto). */
public static int buscar(int[] a, int x) {
    int izq = 0, der = a.length - 1;
    while (izq <= der) {
        int medio = izq + (der - izq) / 2;
        if (a[medio] == x) return medio;

        if (a[izq] <= a[medio]) {               // la IZQUIERDA está ordenada
            if (a[izq] <= x && x < a[medio]) der = medio - 1;   // x cae ahí
            else                             izq = medio + 1;
        } else {                                // entonces la DERECHA lo está
            if (a[medio] < x && x <= a[der]) izq = medio + 1;
            else                             der = medio - 1;
        }
    }
    return -1;
}

La observación que hace posible el algoritmo: por más que el arreglo esté rotado, al cortarlo por el medio al menos una de las dos mitades es un tramo ordenado normal. El punto de rotación cae en una sola de las dos.

Y saber cuál está ordenada alcanza para decidir: comparás x contra sus extremos y, si cae adentro, seguís ahí; si no, el elemento tiene que estar en la otra. En cualquier caso descartás la mitad, que es lo que mantiene el O(log n): T(n) = T(n/2) + O(1).

El detalle fino: el <= de a[izq] <= a[medio]. Cuando el tramo tiene un solo elemento, izq == medio, y con < estricto caerías por la rama equivocada.

El caso que rompe todo: si hay duplicados ({2,2,2,0,2}), a[izq] == a[medio] no te dice qué mitad está ordenada y hay que avanzar de a uno — el peor caso degenera a O(n). Por eso el enunciado supone elementos distintos.

Exponenciación modular

long potModular(long base, long exp, long mod) en O(log exp); test.

PistaEs la potencia rápida con un % mod en cada paso. Ese módulo no es sólo el resultado pedido: es lo que evita que los números exploten.
/** O(log exp): potencia rápida aplicando el módulo en cada paso. */
public static long potModular(long base, long exp, long mod) {
    if (mod <= 0) throw new IllegalArgumentException("módulo inválido: " + mod);
    if (exp < 0)  throw new IllegalArgumentException("exponente negativo");
    if (mod == 1) return 0;

    long resultado = 1;
    base = base % mod;                  // por si viene más grande
    if (base < 0) base += mod;          // Java devuelve negativos con %

    while (exp > 0) {
        if ((exp & 1) == 1) {
            resultado = (resultado * base) % mod;
        }
        base = (base * base) % mod;     // <- el módulo ACÁ es lo que evita el desborde
        exp >>= 1;
    }
    return resultado;
}

Por qué el módulo en cada paso y no al final. Calcular 71000 y recién después tomar módulo es imposible: ese número tiene 846 dígitos y desborda cualquier entero. Aplicando % mod en cada multiplicación, los valores nunca superan mod. Es correcto porque (a·b) mod m = ((a mod m)·(b mod m)) mod m.

La advertencia que se cobra: aun con el módulo, el producto intermedio base * base puede desbordar el long si mod supera ~3·10⁹ (porque mod² se pasa del rango). Para módulos grandes hay que usar Math.multiplyHigh o BigInteger.

Y el % de Java: -7 % 3 da -1, no 2. Por eso la corrección del signo al principio — un detalle que rompe el algoritmo silenciosamente con bases negativas.

Dónde se usa de verdad: es el núcleo de RSA y Diffie-Hellman. Sin este algoritmo, la criptografía de clave pública sería impracticable: los exponentes reales tienen cientos de dígitos, y O(log exp) es lo que lo vuelve instantáneo.

Torres de Hanoi

long movimientos(int n) con T(n) = 2T(n−1) + 1 ⇒ 2n − 1; test.

PistaPara mover n discos: mové n−1 a la varilla auxiliar, mové el grande, y volvé a mover los n−1 encima. Ahí está el 2T(n−1) + 1.
/** T(n) = 2T(n−1) + 1  ->  2^n − 1.
 *  T. Maestro por SUSTRACCIÓN con a = 2 > 1: EXPONENCIAL. */
public static long movimientos(int n) {
    if (n < 0) throw new IllegalArgumentException("n negativo");
    if (n == 0) return 0;
    return 2 * movimientos(n - 1) + 1;
}

/** La versión que además muestra los movimientos. */
public static void resolver(int n, char origen, char destino, char auxiliar) {
    if (n == 0) return;
    resolver(n - 1, origen, auxiliar, destino);                    // T(n−1)
    System.out.println("mover disco " + n + ": " + origen + " -> " + destino);
    resolver(n - 1, auxiliar, destino, origen);                    // T(n−1)
}

La recurrencia sale sola del algoritmo: dos llamadas sobre n−1 (mover la torre de n−1 dos veces) más un movimiento (O(1)). Por el teorema de sustracción, a = 2 > 1 ⟹ O(2n/1) = O(2n). Y acá el valor exacto es conocido: 2n − 1, que podés verificar con el método de expansión (lab 4, opción r5).

Por qué esto es un límite real y no una ineficiencia: a diferencia del Fibonacci ingenuo —que es exponencial por recalcular y se arregla con memoización— acá la salida tiene 2n − 1 movimientos. No hay algoritmo mejor posible: el problema mismo es exponencial. La leyenda de los 64 discos son 264 − 1 ≈ 1.8 × 1019 movimientos: a uno por segundo, 585 mil millones de años.

Esa distinción —exponencial por mala implementación vs exponencial por naturaleza del problema— es una de las ideas más importantes de la unidad.

Fibonacci rápido O(log n)

Por exponenciación (de matriz 2×2 o fast doubling); test contra el iterativo.

PistaLa misma idea de la potencia rápida, con matrices: elevar [[1,1],[1,0]] a la n te da los Fibonacci. Como es una potencia, se hace por cuadrados en log n.
/** O(log n): potencia de matriz por cuadrados.
 *  [[1,1],[1,0]]^n = [[F(n+1), F(n)], [F(n), F(n−1)]] */
public static long fibonacci(int n) {
    if (n < 0) throw new IllegalArgumentException("n negativo");
    if (n == 0) return 0;

    long[][] base = {{1, 1}, {1, 0}};
    long[][] r = potenciaMatriz(base, n - 1);
    return r[0][0];                     // F(n)
}

private static long[][] potenciaMatriz(long[][] m, int exp) {
    long[][] resultado = {{1, 0}, {0, 1}};      // la identidad
    while (exp > 0) {                           // log₂ exp vueltas
        if ((exp & 1) == 1) {
            resultado = multiplicar(resultado, m);
        }
        m = multiplicar(m, m);                  // el siguiente cuadrado
        exp >>= 1;
    }
    return resultado;
}

private static long[][] multiplicar(long[][] a, long[][] b) {
    return new long[][]{
        {a[0][0]*b[0][0] + a[0][1]*b[1][0],  a[0][0]*b[0][1] + a[0][1]*b[1][1]},
        {a[1][0]*b[0][0] + a[1][1]*b[1][0],  a[1][0]*b[0][1] + a[1][1]*b[1][1]}
    };
}

Por qué funciona: la recurrencia de Fibonacci se puede escribir como una multiplicación de matrices, y aplicarla n veces equivale a elevar la matriz a la n. Como es una potencia, se calcula por cuadrados en O(log n) — exactamente el algoritmo de 4.5.2, con matrices 2×2 en vez de números. La multiplicación de matrices es O(1) porque el tamaño es fijo.

Merge de k arreglos ordenados

Fusionar un int[][] en un solo arreglo ordenado; test.

PistaLa versión obvia mira los k frentes y elige el menor: O(N·k). Para mejorarla, necesitás una estructura que te dé el mínimo más rápido que recorriendo.

Versión 1 — fusión de a pares (O(N log k), sin estructuras extra):

/** O(N log k) con N = total de elementos: log k rondas, cada una toca los N. */
public static int[] fusionar(int[][] arreglos) {
    if (arreglos == null || arreglos.length == 0) return new int[0];

    List<int[]> actual = new ArrayList<>(Arrays.asList(arreglos));
    while (actual.size() > 1) {                  // log₂ k rondas
        List<int[]> siguiente = new ArrayList<>();
        for (int i = 0; i < actual.size(); i += 2) {
            if (i + 1 < actual.size()) {
                siguiente.add(fusionarDos(actual.get(i), actual.get(i + 1)));
            } else {
                siguiente.add(actual.get(i));    // el impar pasa de largo
            }
        }
        actual = siguiente;
    }
    return actual.get(0);
}

private static int[] fusionarDos(int[] a, int[] b) {   // O(|a| + |b|)
    int[] r = new int[a.length + b.length];
    int i = 0, j = 0, k = 0;
    while (i < a.length && j < b.length) r[k++] = (a[i] <= b[j]) ? a[i++] : b[j++];
    while (i < a.length) r[k++] = a[i++];
    while (j < b.length) r[k++] = b[j++];
    return r;
}

El análisis: cada ronda fusiona de a pares y reduce a la mitad la cantidad de arreglos, así que hay log2 k rondas; en cada una, el trabajo total toca los N elementos. Total: O(N log k). Es la estructura de Mergesort aplicada a arreglos en vez de a elementos.

Por qué no fusionar de a uno contra el acumulado: ahí el acumulado crece y lo recorrés k veces, dando O(N·k). Con k = 1000 arreglos, la diferencia es entre 10 pasadas y 1000.

Versión 2 — con una cola de prioridad (O(N log k) también, pero en una sola pasada y con O(k) de memoria extra):

public static int[] fusionarConHeap(int[][] arreglos) {
    int total = Arrays.stream(arreglos).mapToInt(a -> a.length).sum();
    int[] r = new int[total];

    // cada entrada: {valor, cuál arreglo, qué posición}
    PriorityQueue<int[]> cola = new PriorityQueue<>((x, y) -> Integer.compare(x[0], y[0]));
    for (int i = 0; i < arreglos.length; i++) {
        if (arreglos[i].length > 0) cola.add(new int[]{arreglos[i][0], i, 0});
    }

    int k = 0;
    while (!cola.isEmpty()) {
        int[] menor = cola.poll();               // O(log k)
        r[k++] = menor[0];
        int siguiente = menor[2] + 1;
        if (siguiente < arreglos[menor[1]].length) {
            cola.add(new int[]{arreglos[menor[1]][siguiente], menor[1], siguiente});
        }
    }
    return r;
}

La cola mantiene los k frentes y da el mínimo en O(log k) en vez de O(k). Se extraen N elementos: O(N log k). Mismo orden que la versión 1, pero con una sola pasada y sin arreglos intermedios — esta es la que se usa en el mundo real para fusionar archivos ordenados que no entran en memoria.
