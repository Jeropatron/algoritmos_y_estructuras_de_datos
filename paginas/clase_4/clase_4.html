Unidad 3

Abstracción, TDA y Programación Orientada a Objetos
Objetivos de la unidad

Esta es una de las unidades más importantes del curso. Al terminarla vas a poder: (1) explicar qué es la abstracción y por qué es la idea central; (2) definir un Tipo de Dato Abstracto (TDA) separando el contrato de la implementación; (3) programar con los pilares de la POO —encapsulamiento, herencia y polimorfismo—; (4) usar interfaces, clases y métodos abstractos y genéricos; (5) implementar los métodos estándar (toString, equals, hashCode, compareTo, clone); (6) leer y escribir diagramas UML; y (7) reconocer las prácticas que hacen un código elegante, robusto y mantenible.

Hasta acá aprendiste el lenguaje (Unidad 1B) y cómo se comportan los objetos en memoria (Unidad 2). Ahora damos el salto conceptual del curso: diseñar. Vamos a dejar de pensar “qué instrucciones escribo” para empezar a pensar “qué piezas tiene mi sistema, qué hace cada una y cómo se relacionan”. Esa es la esencia de la Programación Orientada a Objetos.

3.1Abstracción: la gran idea

Abstraer es quedarse con lo esencial y ocultar el detalle. Cuando manejás un auto usás el volante, el acelerador y el freno: no te importa cómo funciona el motor por dentro. Esa separación entre qué hace algo (su interfaz) y cómo lo hace (su implementación) es la herramienta más poderosa que tenemos para domar la complejidad. Todo lo que sigue en esta unidad son formas concretas de aplicar abstracción.

3.2Tipos de Datos Abstractos (TDA)

Un Tipo de Dato Abstracto es la especificación de un tipo por sus operaciones y sus propiedades, sin comprometerse con una implementación. Un TDA se define con: un nombre, un conjunto de operaciones (con sus precondiciones y postcondiciones) y sus invariantes (lo que siempre debe cumplirse). Eso es el contrato.

La clave es que el contrato es independiente de la implementación. Una Pila (operaciones apilar, desapilar, tope, con la regla LIFO) es un TDA; podés implementarla con un arreglo o con una lista enlazada, y quien la usa no debería notar la diferencia. Vas a ver este principio en cada estructura de la materia.

Veamos el contrato en acción. Sin saber nada de cómo está implementada la pila, el contrato alcanza para predecir qué pasa:

Pila<String> p = /* cualquiera de las dos implementaciones */;
p.apilar("a");       // pila: a
p.apilar("b");       // pila: a b         (b quedó arriba)
p.apilar("c");       // pila: a b c       (c quedó arriba)
p.tope();            // "c"   — mira el de arriba, sin sacarlo
p.desapilar();       // "c"   — LIFO: sale el ÚLTIMO que entró
p.desapilar();       // "b"
p.tope();            // "a"   — quedó el primero de todos

Cada línea se dedujo del contrato (la regla LIFO), no del código interno. Ése es el poder del TDA: podés razonar, testear y hasta escribir programas enteros contra el contrato, y recién después decidir (o cambiar) la implementación.

Idea clave

Una aclaración importante: la POO es el paradigma; el TDA es una herramienta de diseño. Se trabajan juntos —usamos objetos para implementar TDAs— pero no son lo mismo. Hablar de “paradigma TDA” es un error frecuente que conviene evitar.

3.3Clases y objetos

🔁 Repaso rápido · Variables, tipos y this (base de toda clase)
  • Una variable se declara con su TIPO adelante la primera vez: int x = 5;, String nombre = "Ana";, double p = 3.5;. Si le ponés el valor equivocado de tipo, no compila.
  • return espera un VALOR (una cuenta, una variable, un texto…), no una declaración. Si querés usar una variable, la declarás en una línea y en el return ponés solo su nombre.
  • Un atributo es un dato que el objeto guarda (privado); un método es una acción. Se accede al atributo con this.x ("mi propio x").
  • El constructor recibe valores y los guarda en los atributos: this.x = x; (a la izquierda el atributo, a la derecha el parámetro).
public class Punto {
    private int x;              // atributo (dato privado)
    public Punto(int x) {       // constructor: recibe un valor…
        this.x = x;             // …y lo guarda en el atributo
    }
    public int getX() {         // método (acción)
        return x;               // return devuelve un VALOR
    }
}

En POO, una clase es un molde que define un estado (los datos, en campos) y un comportamiento (los métodos). Un objeto es una instancia concreta de esa clase, creada con new, con sus propios valores.

material/i03_poo/CuentaBancaria.java
public class CuentaBancaria {
    private double saldo;                         // estado (privado)

    public CuentaBancaria(double saldoInicial) {  // constructor: inicializa el objeto
        this.saldo = saldoInicial;
    }
    public double saldo() { return saldo; }       // comportamiento
}

La palabra this se refiere al objeto actual; el constructor es el método especial que prepara un objeto recién creado.

3.4Los pilares de la POO

🔁 Repaso rápido · Herencia: extends, super, @Override
public class Gerente extends Empleado {   // HEREDA de Empleado ("Gerente ES-UN Empleado")
    private final double bono;
    public Gerente(String n, double base, double bono) {
        super(n, base);          // llama al constructor de la clase madre
        this.bono = bono;
    }
    @Override                    // REDEFINE un metodo heredado (sobrescritura)
    public double sueldo() {
        return super.sueldo() + bono;   // reutiliza el de la madre y le suma algo
    }
}
  • extends = heredar (recibís atributos y métodos de la clase madre). Regla: usalo cuando "X es-un Y".
  • @Override = redefinís un método heredado. Va SIEMPRE en los métodos estándar (toString, equals, compareTo…) porque los heredás de Object o de una interfaz.
  • super(...) = el constructor de la madre; super.metodo() = la versión de la madre (para reutilizarla).
  • private = solo la propia clase lo ve; public = todos; protected = la clase y sus subclases. Los atributos casi siempre private.

Sobre la abstracción se apoyan tres pilares que vas a usar constantemente.

3.4.1Encapsulamiento

Encapsular es ocultar el estado detrás de una interfaz que lo protege. Los campos se declaran private y sólo se tocan mediante métodos que garantizan los invariantes. Así nadie puede dejar el objeto en un estado inválido.

public class CuentaBancaria {
    private double saldo;                         // nadie lo cambia directamente

    public void extraer(double monto) {
        if (monto <= 0)    throw new IllegalArgumentException("monto inválido");
        if (monto > saldo) throw new SaldoInsuficienteException(saldo, monto);
        saldo -= monto;                           // el saldo nunca queda negativo
    }
}

Seguí las dos flechas de la figura. La roja intenta el camino directo (cuenta.saldo = -999) y ni siquiera compila: el campo es private, la puerta no existe. La verde entra por el método: cuenta.extraer(200) con saldo 150 hace que el propio método detecte el problema (200 > 150), lance SaldoInsuficienteException y deje el saldo intacto. El invariante “el saldo nunca es negativo” está garantizado no porque todos los que usan la clase sean cuidadosos, sino porque es imposible violarlo desde afuera.

Error común

Exponer los campos como public (como hicimos a propósito en la clase mínima de la Unidad 1B) rompe el encapsulamiento: cualquiera podría poner un saldo negativo. La regla es campos privados, acceso controlado.

3.4.2Herencia

La herencia permite que una clase (hija) reutilice y especialice a otra (padre) con extends. Modela una relación “es un/una”: un Perro es un Animal. La hija hereda el comportamiento del padre y puede agregar o redefinir lo suyo; con super accede al padre.

public class Animal {
    private final String nombre;
    public Animal(String nombre) { this.nombre = nombre; }
    public String nombre()      { return nombre; }
    public String sonido()      { return "..."; }
    public String presentarse() { return nombre + " dice " + sonido(); }
}


public class Perro extends Animal {                    // Perro ES UN Animal
    public Perro(String nombre) { super(nombre); }     // llama al constructor del padre
    @Override public String sonido() { return "Guau"; }  // redefine SOLO lo suyo
}

Mirá lo que Perro no tiene que escribir: ni nombre(), ni presentarse() —los hereda—. Sólo llama al constructor del padre con super(nombre) y redefine sonido() con la anotación @Override (que le pide al compilador verificar que efectivamente estás redefiniendo algo del padre; si te equivocás en el nombre, te avisa).

3.4.3Polimorfismo

Polimorfismo significa “muchas formas”: una misma referencia del tipo padre puede apuntar a objetos de distintas subclases, y al llamar un método se ejecuta el del objeto real (despacho dinámico), no el del tipo de la variable.

Animal[] animales = { new Perro("Fido"), new Gato("Milo") };
for (Animal a : animales) {
    System.out.println(a.presentarse());   // "Fido dice Guau" / "Milo dice Miau"
}

Esto es lo que hace al código extensible: podés agregar una clase Vaca sin tocar el bucle que recorre los animales.

3.5Composición: la alternativa a heredar

La herencia es potente, pero se abusa de ella. Antes de escribir extends, hacete la pregunta clave: ¿“X es un Y”… o en realidad “X tiene un Y”? Cuando la respuesta es “tiene un”, la herramienta correcta es la composición: guardar el otro objeto como campo y delegarle trabajo.

public class Auto {
    private final Motor motor;                     // el Auto TIENE un Motor
    public Auto(Motor motor) { this.motor = motor; }
    public void arrancar() { motor.encender(); }   // delega en su motor
}

¿Por qué importa tanto? Un Auto extends Motor “funcionaría” (heredaría encender()), pero el diseño queda roto: el auto expondría operaciones que no le corresponden, no podría cambiar de motor, y quedaría atado para siempre a una jerarquía sin sentido. La composición es más flexible (podés cambiar el motor por otro, incluso en tiempo de ejecución) y más honesta (el auto muestra sólo sus propias operaciones). En UML, la composición se dibuja con un rombo lleno del lado del “todo” (mirá la leyenda de la sección de UML).

Idea clave

Regla práctica: herencia para “es un”, composición para “tiene un” — y ante la duda, empezá por composición: es más fácil pasar de composición a herencia que deshacer una jerarquía equivocada.

3.6Interfaces: el contrato puro

Una interfaz declara un conjunto de operaciones sin implementarlas: es el contrato de un TDA llevado a código. Una clase se compromete a cumplirlo con implements. Una interfaz puede tener muchas implementaciones distintas, y ese es su gran valor.

public interface Figura {              // el CONTRATO
    double area();
    double perimetro();
}


public class Circulo implements Figura {
    private final double radio;
    public Circulo(double radio) { this.radio = radio; }

    @Override public double area()      { return Math.PI * radio * radio; }
    @Override public double perimetro() { return 2 * Math.PI * radio; }
}

Notá que la interfaz no le impone a Circulo cómo calcular: sólo lo obliga a tener area() y perimetro(). Un Rectangulo cumple el mismo contrato con fórmulas totalmente distintas, y el código que trabaja con Figura los trata a todos por igual.

Las interfaces admiten métodos default (con implementación) para casos puntuales, pero su rol principal es especificar qué, dejando el cómo a cada implementación.

3.6.2Otro dominio, mismo poder: intercambiar implementaciones

Para que no quede pegado a la geometría, un contrato de la vida real: "algo que sabe avisar". Y una clase que lo usa dependiendo de la interfaz —nunca de una implementación concreta:

material/i03_poo/Notificador.java · RecordatorioDeEntrega.java
public interface Notificador {
    void notificar(String mensaje);
    default void notificarUrgente(String mensaje) {   // método default: cómo común
        notificar("¡URGENTE! " + mensaje);
    }
}

public class RecordatorioDeEntrega {
    private final Notificador notificador;   // depende del CONTRATO, no del cómo
    private final String materia;

    public RecordatorioDeEntrega(Notificador notificador, String materia) {
        this.notificador = notificador;
        this.materia = materia;
    }
    public void avisarEntrega(String tp, int diasQueFaltan) {
        if (diasQueFaltan == 0) {
            notificador.notificarUrgente(materia + ": ¡" + tp + " vence HOY!");
        } else {
            notificador.notificar(materia + ": " + tp + " vence en " + diasQueFaltan + " días");
        }
    }
}

En el repo hay dos implementaciones: NotificadorPorConsola (imprime) y NotificadorEnMemoria (no imprime nada: acumula los mensajes para inspeccionarlos). La misma RecordatorioDeEntrega funciona con ambas, sin tocarle una línea:

// con una implementación...
RecordatorioDeEntrega porConsola =
        new RecordatorioDeEntrega(new NotificadorPorConsola(), "CB100");
porConsola.avisarEntrega("TP individual", 3);   // [consola] CB100: TP individual vence en 3 días

// ...y con OTRA: RecordatorioDeEntrega ni se enteró del cambio
NotificadorEnMemoria memoria = new NotificadorEnMemoria();
RecordatorioDeEntrega paraTest = new RecordatorioDeEntrega(memoria, "CB100");
paraTest.avisarEntrega("TP grupal", 7);
paraTest.avisarEntrega("TP grupal", 0);
System.out.println(memoria.cantidadDeAvisos());   // 2

¿Y para qué querría alguien un notificador que no notifica? Para los tests: enchufás la implementación en memoria, ejercitás tu clase, y verificás qué avisos salieron —sin llenar la consola ni mandar nada de verdad. Este truco (una implementación "de mentira" que cumple el contrato) es moneda corriente en la industria, y funciona únicamente porque RecordatorioDeEntrega depende de la interfaz.

Idea clave

Programá contra el contrato, no contra la implementación. Atributos, parámetros y retornos declarados por la interfaz (Figura, Notificador); la implementación concreta aparece SOLO en el new. Beneficio doble: podés cambiar el cómo sin tocar a los usuarios, y podés testear con implementaciones falsas. Vas a ver esta idea a escala en la U5 (la interfaz Lista con dos implementaciones) y en cada TDA del curso.

3.7Clases y métodos abstractos

A veces querés una clase base que comparta código entre subclases pero que no tenga sentido instanciar por sí sola: eso es una clase abstracta (abstract class). Puede tener métodos concretos y métodos abstractos (sin cuerpo) que cada subclase debe completar.

public abstract class FiguraBase implements Figura, Comparable<Figura> {
    private final String nombre;
    protected FiguraBase(String nombre) { this.nombre = nombre; }

    // area() y perimetro() quedan ABSTRACTOS: los define cada figura concreta.

    @Override public int compareTo(Figura otra) { return Double.compare(area(), otra.area()); }
    @Override public String toString() { return String.format("%s(área=%.2f)", nombre, area()); }
}
Idea clave

¿Interfaz o clase abstracta? Usá una interfaz para declarar un contrato que muchas clases (aun sin relación entre sí) pueden cumplir; usá una clase abstracta cuando además querés compartir estado o código entre subclases emparentadas. Una clase implementa muchas interfaces, pero hereda de una sola clase.

3.8Los métodos estándar

🔁 Repaso rápido · Armar un texto con + (para el toString)

El toString arma un texto pegando pedazos con +. Hay dos tipos de pedazos:

  • Texto fijo → va entre comillas " ". Las comillas marcan "esto es literal" y no se imprimen.
  • Valores → son las variables, SIN comillas (así usan el valor real, no la palabra escrita).
  // código (con comillas en lo fijo, variables afuera):
  return "Persona{nombre=" + nombre + ", edad=" + edad + "}";

  // resultado al correr (con nombre="Ana", edad=30 — las comillas NO salen):
  Persona{nombre=Ana, edad=30}

Trampa típica: si ponés el nombre adentro de las comillas ("...Ana..."), queda fijo y toda persona diría "Ana". El valor real solo lo tomás usando la variable afuera de las comillas.

Casi toda clase de “valor” implementa algunos métodos que Java y sus bibliotecas esperan encontrar:

  • toString() — una representación legible del objeto (para imprimir y depurar).
  • equals(Object) — igualdad por contenido (Unidad 2), no por identidad.
  • hashCode() — un entero consistente con equals: si dos objetos son iguales, deben tener el mismo hashCode (esencial para Hashing, más adelante).
  • compareTo(...) (de Comparable) — define el orden natural, para poder ordenar.
  • clone() — una copia del objeto; en la práctica se prefiere un constructor copia, porque clone es delicado (copia superficial y diseño discutido).
🔁 Repaso rápido · La receta de equals y hashCode
@Override public boolean equals(Object o) {
    if (this == o) return true;                       // 1) mismo objeto → true
    if (o == null || getClass() != o.getClass())      // 2) null u otra clase → false
        return false;
    Punto otro = (Punto) o;                            // 3) convertir (cast) y…
    return x == otro.x && y == otro.y;                 //    …comparar los campos
}
@Override public int hashCode() {
    return Objects.hash(x, y);                         // los MISMOS campos que en equals
}
  • El contrato: si dos objetos son equals, deben tener el mismo hashCode. Por eso ambos usan los mismos campos (acá x e y).
  • compareTo (para ordenar): devolvé negativo/0/positivo. Te sirven Integer.compare(a, b) o Double.compare(a, b).
material/i03_poo/Fraccion.java
public final class Fraccion implements Comparable<Fraccion> {
    private final int numerador, denominador;

    public Fraccion(int numerador, int denominador) {
        if (denominador == 0) throw new IllegalArgumentException("denominador 0");
        int divisor = mcd(Math.abs(numerador), Math.abs(denominador));
        this.numerador   = numerador / divisor;     // guarda SIEMPRE simplificada:
        this.denominador = denominador / divisor;   // 2/4 se almacena como 1/2
    }
    private static int mcd(int a, int b) { return b == 0 ? a : mcd(b, a % b); }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Fraccion f)) return false;
        return numerador == f.numerador && denominador == f.denominador;
    }
    @Override public int hashCode() { return Objects.hash(numerador, denominador); }
    @Override public int compareTo(Fraccion o) {
        return Long.compare((long) numerador * o.denominador, (long) o.numerador * denominador);
    }
    @Override public String toString() { return numerador + "/" + denominador; }
}

Un detalle de diseño: el constructor simplifica al crear la fracción (dividiendo por el máximo común divisor), así el objeto guarda siempre la forma canónica. Eso hace que el equals de arriba sea correcto por comparación directa: new Fraccion(1, 2) y new Fraccion(2, 4) almacenan ambos 1/2, y por lo tanto son equals. Sin esa normalización, el equals campo a campo diría que 1/2 ≠ 2/4 — un bug silencioso.

Error común

equals y hashCode van siempre juntos: si redefinís uno, redefiní el otro de forma consistente. Romper esta regla causa errores muy difíciles de encontrar cuando uses tablas de hash.

¿Qué tan grave es romper esa regla? Veámoslo. Un HashSet guarda cada objeto en un “balde” elegido según su hashCode, y para buscar un objeto va directo al balde que indica el hashCode del buscado (por eso es tan rápido, como vas a ver en Hashing). Ahora imaginá una Fraccion con equals redefinido pero sin hashCode: cada objeto hereda el hashCode de Object, que es distinto para cada instancia.

El resultado del panel derecho es desconcertante en la práctica: agregás new Fraccion(1,2) al conjunto, preguntás si contiene new Fraccion(1,2)… y te dice que no. El objeto “está”, pero la búsqueda mira en el balde equivocado. Este bug no lanza excepciones ni avisa: simplemente el conjunto “pierde” cosas. Por eso la regla es innegociable: si dos objetos son equals, deben tener el mismo hashCode (lo más simple: generá ambos con el IDE, o usá un record, que te los da consistentes gratis).

3.9Genéricos

Los genéricos permiten escribir clases y métodos que funcionan con cualquier tipo, manteniendo la seguridad de tipos en tiempo de compilación. Se escriben con un parámetro de tipo entre < >.

public class Caja<T> {           // T es el tipo que se decide al usar la caja
    private T contenido;
    public Caja(T contenido) { this.contenido = contenido; }
    public T get() { return contenido; }
}


Caja<String> c = new Caja<>("hola");       // una caja de String

También podés acotar el tipo (<E extends Comparable<E>>) para exigir que soporte ciertas operaciones. Los genéricos son la base de las estructuras de datos reutilizables que vamos a construir en las próximas unidades.

3.11Diseño profesional: elegancia, robustez y mantenimiento

Programar bien no es sólo que “funcione”: es escribir código que otra persona (¡o vos en seis meses!) pueda entender y modificar sin miedo. Algunas prácticas que perseguimos en la materia:

  • Nombres claros: que digan qué hacen; el código se lee muchas más veces de las que se escribe.
  • Responsabilidad única: cada clase y cada método hacen una cosa bien.
  • Encapsulamiento: estado privado, invariantes protegidos.
  • Inmutabilidad cuando se pueda: menos errores por estado compartido (Unidad 2).
  • Validar y fallar claro: precondiciones explícitas y excepciones con buen mensaje (robustez).
  • Modularización: separar en piezas con contratos claros (interfaces/TDAs) permite cambiar una sin romper las otras.
  • Tests: cada pieza con sus pruebas, como red de seguridad ante cambios.
Idea clave

Un código elegante no es el más “corto” ni el más “ingenioso”: es el que se entiende de un vistazo, es difícil de usar mal y fácil de cambiar. Ese es el estándar profesional al que apuntamos.

3.11.1Validar con criterio

Validar está bien, pero no todo se valida. Una buena validación protege un invariante barato de chequear; una mala validación gasta tiempo comprobando algo que ya es parte del contrato de quien llama.

Validaciones que tienen sentido (baratas y evitan estados inválidos): un valor no nulo, o un número dentro de un rango.

public Persona(String nombre, int edad) {
    this.nombre = Objects.requireNonNull(nombre, "nombre no puede ser null");
    if (edad < 0 || edad > 150) throw new IllegalArgumentException("edad inválida: " + edad);
    this.edad = edad;
}

Validaciones que NO tienen sentido: si un método tiene como precondición que el arreglo venga ordenado (por ejemplo, la búsqueda binaria), no hay que verificar que lo esté: recorrerlo para chequearlo cuesta O(n) y destruiría la ventaja de la búsqueda binaria (O(log n), que veremos en la Unidad 4). Que el arreglo esté ordenado es responsabilidad de quien llama; se documenta en el contrato, no se comprueba.

/** PRECONDICIÓN: 'a' está ordenado de menor a mayor.
 *  NO se verifica acá: costaría O(n) y anularía la ventaja de la búsqueda binaria. */
static int busquedaBinaria(int[] a, int x) { /* ... O(log n) ... */ }

Unificar las validaciones en una clase utilitaria evita repetir código y mantiene los mensajes consistentes:

material/i03_poo/Preconditions.java
public final class Preconditions {
    private Preconditions() {}

    public static <T> T noNulo(T v, String nombre) {
        return Objects.requireNonNull(v, nombre + " no puede ser null");
    }
    public static int enRango(int v, int min, int max, String nombre) {
        if (v < min || v > max)
            throw new IllegalArgumentException(nombre + " fuera de rango [" + min + ".." + max + "]: " + v);
        return v;
    }
}


// uso:
this.edad = Preconditions.enRango(edad, 0, 150, "edad");

1¿Qué es la abstracción y por qué es la idea central de la POO?

Abstraer es quedarse con lo esencial y ocultar el detalle. Es separar qué hace algo (su interfaz) de cómo lo hace (su implementación).

La analogía del apunte: cuando manejás un auto usás el volante, el acelerador y el freno; no te importa cómo funciona el motor por dentro. El auto te ofrece una interfaz simple y te esconde una máquina complejísima.

Es la idea central porque es la herramienta más poderosa que tenemos para domar la complejidad: te permite razonar sobre una pieza sin tener toda la máquina en la cabeza. Todo lo demás de la unidad son formas concretas de aplicarla:

  • el TDA abstrae una estructura de datos en un contrato de operaciones;
  • el encapsulamiento abstrae el estado detrás de métodos;
  • las interfaces abstraen el contrato separándolo de sus implementaciones;
  • el polimorfismo abstrae el tipo concreto: tratás a muchos objetos distintos por igual;
  • los genéricos abstraen el tipo de los datos.
2¿Qué define un TDA y por qué su contrato es independiente de la implementación?

Un Tipo de Dato Abstracto es la especificación de un tipo por sus operaciones y sus propiedades, sin comprometerse con una implementación. Lo definen tres cosas:

  • un nombre;
  • un conjunto de operaciones, con sus precondiciones (qué debe cumplirse antes) y postcondiciones (qué garantiza después);
  • sus invariantes: lo que siempre debe cumplirse.

Todo eso junto es el contrato.

Es independiente de la implementación porque el contrato habla de comportamiento observable, no de estructura interna. El TDA Pila dice “apilar, desapilar, tope, y sale el último que entró (LIFO)”. Con eso alcanza para predecir el resultado de cualquier secuencia de operaciones, sin saber si por dentro hay un arreglo o una lista enlazada.

La consecuencia práctica es enorme: podés escribir y testear programas enteros contra el contrato y recién después elegir —o cambiar— la implementación. Si el contrato se respeta, nada del código que usa la pila se entera del cambio.

3¿Cuál es la diferencia entre una clase y un objeto?

Una clase es el molde: define qué estado (campos) y qué comportamiento (métodos) van a tener los objetos de ese tipo. Es una definición, existe una sola vez, y no guarda valores concretos.

Un objeto es una instancia concreta de esa clase, creada con new, con sus propios valores. De una misma clase podés crear tantos objetos como quieras, y cada uno tiene estado independiente.

// la CLASE: el molde, una sola vez
public class CuentaBancaria {
    private double saldo;
    public CuentaBancaria(double saldoInicial) { this.saldo = saldoInicial; }
}

// los OBJETOS: instancias con estado propio
CuentaBancaria a = new CuentaBancaria(1000);   // saldo = 1000
CuentaBancaria b = new CuentaBancaria(250);    // saldo = 250, independiente de a

Enganchando con la Unidad 2: la clase es una definición del programa; los objetos viven en el heap, y las variables que los nombran guardan referencias a ellos.

4Explicá los tres pilares: encapsulamiento, herencia y polimorfismo.

Encapsulamiento — ocultar el estado detrás de una interfaz que lo protege. Los campos van private y sólo se tocan por métodos que garantizan los invariantes. Así el objeto no puede quedar en un estado inválido, y no porque todos sean cuidadosos: porque es imposible desde afuera.

public void extraer(double monto) {
    if (monto > saldo) throw new SaldoInsuficienteException(saldo, monto);
    saldo -= monto;                  // el saldo nunca queda negativo
}

Herencia — una clase hija reutiliza y especializa a otra con extends. Modela la relación “es un/una”. La hija hereda todo el comportamiento del padre, puede agregar lo suyo y redefinir métodos con @Override; con super accede al padre.

public class Perro extends Animal {                  // un Perro ES UN Animal
    public Perro(String nombre) { super(nombre); }
    @Override public String sonido() { return "Guau"; }
}

Polimorfismo — “muchas formas”: una referencia del tipo padre puede llevar a objetos de distintas subclases, y al llamar un método se ejecuta el del objeto real, no el del tipo de la variable. Eso se llama despacho dinámico.

Animal[] animales = { new Perro("Fido"), new Gato("Milo") };
for (Animal a : animales) System.out.println(a.presentarse());
// "Fido dice Guau" / "Milo dice Miau"

Es lo que hace al código extensible: agregar una Vaca no obliga a tocar ese bucle. Los tres se apoyan sobre la abstracción.

5¿Cuándo usarías una interfaz y cuándo una clase abstracta?

Interfaz: cuando querés declarar un contrato que muchas clases —aun sin relación entre sí— pueden cumplir. No aporta estado ni (en general) código: sólo dice qué operaciones existen.

Clase abstracta: cuando además querés compartir estado o código entre subclases emparentadas, y no tiene sentido instanciar la base por sí sola.

Regla práctica: empezá por la interfaz. Si después descubrís que varias implementaciones repiten lo mismo, metés una clase abstracta en el medio.

6¿Por qué equals y hashCode deben ser consistentes?

Porque las estructuras basadas en hashing (HashSet, HashMap) usan el hashCode para decidir en qué “balde” guardar un objeto, y al buscar van directo al balde que indica el hashCode del buscado. Ahí, y sólo ahí, comparan con equals. Por eso son tan rápidas.

El contrato es: si a.equals(b) es true, entonces a.hashCode() == b.hashCode(). (La recíproca no hace falta: dos objetos distintos pueden compartir hashCode, eso es una colisión y está contemplado.)

Si lo rompés —redefinís equals pero no hashCode— cada instancia hereda el hashCode de Object, distinto para cada una. Entonces:

var set = new HashSet<Fraccion>();
set.add(new Fraccion(1, 2));
set.contains(new Fraccion(1, 2));   // false  ← ¡el objeto "está"!

Guardaste en el balde 1 y buscás en el balde 3, que está vacío. El bug no lanza excepciones ni avisa: el conjunto simplemente “pierde” cosas, y eso lo vuelve dificilísimo de encontrar.

La solución práctica: generá ambos con el IDE (Alt+Insert), usá Objects.hash(campo1, campo2) con los mismos campos que usa el equals, o directamente usá un record, que te los da consistentes gratis.

7¿Para qué sirven los genéricos? Dá un ejemplo.

Los genéricos permiten escribir clases y métodos que funcionan con cualquier tipo, manteniendo la seguridad de tipos en tiempo de compilación. Se declara un parámetro de tipo entre < > y se decide al usar la clase.

public class Caja<T> {           // T se decide al usar la caja
    private T contenido;
    public Caja(T contenido) { this.contenido = contenido; }
    public T get() { return contenido; }
}

Caja<String> c = new Caja<>("hola");
String s = c.get();              // sin cast, y el compilador lo garantiza

Sin genéricos habría que guardar Object y castear al sacar, con dos costos: el código queda sucio y un error de tipo recién se descubre al ejecutar, con un ClassCastException. Con genéricos ese error no compila.

También podés acotar el tipo para exigir que soporte ciertas operaciones:

static <T extends Comparable<T>> T maximo(T[] a) { … }   // exige que T se pueda comparar

Son la base de las estructuras de datos reutilizables que vamos a construir en las próximas unidades: una Pila<T> se escribe una sola vez y sirve para cualquier tipo.

9Nombrá tres prácticas que hacen un código más mantenible y explicá por qué.

El apunte lista siete; con tres bien explicadas alcanza. Estas son las que más rinden:

1. Responsabilidad única. Cada clase y cada método hacen una cosa bien. Importa porque cuando algo tiene una sola razón para cambiar, modificarlo es seguro: sabés exactamente qué puede romperse. Una clase que hace cinco cosas tiene cinco motivos para que la toquen, y cada cambio arriesga las otras cuatro.

2. Encapsulamiento. Estado privado, invariantes protegidos. Importa porque limita el radio del daño: si el estado sólo se toca desde adentro de la clase, cuando aparece un valor inválido sabés dónde buscar. Con campos públicos, el culpable puede estar en cualquier parte del programa.

3. Tests. Cada pieza con sus pruebas. Importa porque son la red de seguridad que te permite cambiar el código: sin tests, todo cambio da miedo y el código se congela. Con tests, refactorizás y en segundos sabés si rompiste algo.

Las otras cuatro del apunte: nombres claros (el código se lee muchas más veces de las que se escribe), inmutabilidad cuando se pueda (menos errores por estado compartido), validar y fallar claro (un mensaje bueno ahorra horas), y modularización (contratos claros permiten cambiar una pieza sin romper las otras).

10¿Qué es la integración continua y qué ingredientes de la materia la habilitan?

La Integración Continua (Continuous Integration, CI) es una práctica de la industria: cada vez que alguien sube cambios al repositorio, un servidor compila el proyecto y corre todos los tests automáticamente, y avisa si algo se rompió.

El valor está en el tiempo de detección: los errores aparecen en minutos, no en semanas. Y como corre todos los tests —no sólo los de lo que tocaste—, atrapa las regresiones: eso que andaba y dejó de andar por un cambio en otro lado.

Los ingredientes ya los tenés, y son exactamente los que la CI automatiza:

  • Git — el repositorio y el push que dispara todo el proceso.
  • Gradle — el build reproducible: ./gradlew build y ./gradlew test son literalmente lo que el servidor va a ejecutar.
  • JUnit — los tests automáticos, que son los que dan el veredicto.

La cátedra apunta a sumar CI (por ejemplo con GitHub Actions) para que los TP se integren y validen solos, más medición de cobertura y análisis de estilo. Correr ./gradlew test antes de cada commit ya es hacer CI a mano.

/**
 * TDA Pila: colección LIFO (last in, first out).
 * INVARIANTE: 0 <= tope <= datos.length
 */
public class PilaSobreArreglo<T> {

    private static final int CAPACIDAD_INICIAL = 8;

    private Object[] datos = new Object[CAPACIDAD_INICIAL];
    private int tope;                 // primera celda LIBRE

    /** POST: el elemento queda arriba de todo. */
    public void apilar(T elemento) {
        if (tope == datos.length) {
            datos = java.util.Arrays.copyOf(datos, datos.length * 2);
        }
        datos[tope++] = elemento;
    }

    /** PRE: la pila no está vacía.  POST: sale el ÚLTIMO que entró. */
    @SuppressWarnings("unchecked")
    public T desapilar() {
        if (estaVacia()) throw new PilaVaciaException("desapilar");
        T elemento = (T) datos[--tope];
        datos[tope] = null;           // suelta la referencia: evita la fuga lógica
        return elemento;
    }

    /** PRE: la pila no está vacía.  POST: la pila no cambia. */
    @SuppressWarnings("unchecked")
    public T tope() {
        if (estaVacia()) throw new PilaVaciaException("consultar el tope");
        return (T) datos[tope - 1];
    }

    public boolean estaVacia() { return tope == 0; }
    public int tamanio()       { return tope; }
}

Sobre arreglo: encolar, desencolar, frente; test FIFO.

PistaCon dos índices (frente y fin) que sólo avanzan, el arreglo se “consume” por la izquierda y desperdiciás lugar. La solución clásica es el arreglo circular: los índices dan la vuelta con % capacidad. Guardá el tamanio aparte para distinguir la cola vacía de la llena, porque en ambas frente == fin.
guia/i03_poo/i03_medio/e02/ColaSobreArreglo.java
package ar.uba.fi.cb100.guia.i03_poo.i03_medio.e02;

/**
 * TDA Cola: colección FIFO (first in, first out).
 * Implementada con un arreglo CIRCULAR para no desperdiciar lugar.
 */
public class ColaSobreArreglo<T> {

    private Object[] datos = new Object[8];
    private int frente;      // índice del primero
    private int fin;         // primera celda libre
    private int tamanio;     // necesario: con frente == fin no se distingue vacía de llena

    /** POST: el elemento queda al final. */
    public void encolar(T elemento) {
        if (tamanio == datos.length) redimensionar();
        datos[fin] = elemento;
        fin = (fin + 1) % datos.length;      // da la vuelta
        tamanio++;
    }

    /** PRE: la cola no está vacía.  POST: sale el PRIMERO que entró. */
    @SuppressWarnings("unchecked")
    public T desencolar() {
        if (estaVacia()) throw new ColaVaciaException("desencolar");
        T elemento = (T) datos[frente];
        datos[frente] = null;
        frente = (frente + 1) % datos.length;
        tamanio--;
        return elemento;
    }

    /** PRE: la cola no está vacía.  POST: la cola no cambia. */
    @SuppressWarnings("unchecked")
    public T frente() {
        if (estaVacia()) throw new ColaVaciaException("consultar el frente");
        return (T) datos[frente];
    }

    public boolean estaVacia() { return tamanio == 0; }
    public int tamanio()       { return tamanio; }

package ar.uba.fi.cb100.guia.i03_poo.i03_medio.e07;

import java.util.Comparator;
import java.util.Objects;

public final class Maximo {
    private Maximo() {}

    /** El mayor según el orden NATURAL. La cota exige que T se pueda comparar. */
    public static <T extends Comparable<T>> T maximo(T[] a) {
        Objects.requireNonNull(a, "el arreglo no puede ser null");
        if (a.length == 0) throw new IllegalArgumentException("no hay máximo en un arreglo vacío");

        T max = a[0];
        for (int i = 1; i < a.length; i++) {
            if (a[i].compareTo(max) > 0) max = a[i];   // habilitado por la cota
        }
        return max;
    }

    /** Versión con Comparator: sirve para tipos que no son Comparable. */
    public static <T> T maximo(T[] a, Comparator<? super T> cmp) {
        Objects.requireNonNull(cmp, "el comparador no puede ser null");
        if (a.length == 0) throw new IllegalArgumentException("arreglo vacío");
        T max = a[0];
        for (int i = 1; i < a.length; i++) if (cmp.compare(a[i], max) > 0) max = a[i];
        return max;
    }
}

package ar.uba.fi.cb100.guia.i03_poo.i04_dificil.e01;

import java.util.Arrays;
import java.util.NoSuchElementException;

/**
 * TDA Pila (LIFO) sobre arreglo con redimensión automática.
 * INVARIANTE: 0 <= tope <= datos.length
 */
public class Pila<T> {

    private static final int CAPACIDAD_INICIAL = 4;

    private Object[] datos = new Object[CAPACIDAD_INICIAL];
    private int tope;

    public void apilar(T elemento) {
        if (tope == datos.length) redimensionar(datos.length * 2);
        datos[tope++] = elemento;
    }

    @SuppressWarnings("unchecked")
    public T desapilar() {
        if (estaVacia()) throw new NoSuchElementException("pila vacía");
        T elemento = (T) datos[--tope];
        datos[tope] = null;                       // evita la fuga lógica

        // achica a la mitad cuando queda en un cuarto: histéresis, para no oscilar
        if (tope > 0 && tope == datos.length / 4 && datos.length > CAPACIDAD_INICIAL) {
            redimensionar(datos.length / 2);
        }
        return elemento;
    }

    @SuppressWarnings("unchecked")
    public T tope() {
        if (estaVacia()) throw new NoSuchElementException("pila vacía");
        return (T) datos[tope - 1];
    }

    public boolean estaVacia() { return tope == 0; }
    public int tamanio()       { return tope; }

    /** Sólo para los tests: la capacidad interna no es parte del contrato. */
    int capacidad() { return datos.length; }

    private void redimensionar(int nuevaCapacidad) {
        datos = Arrays.copyOf(datos, nuevaCapacidad);
    }
}

package ar.uba.fi.cb100.guia.i03_poo.i04_dificil.e02;

import java.util.Arrays;
import java.util.Objects;

/**
 * TDA Conjunto: colección SIN duplicados y sin orden garantizado.
 * INVARIANTE: no hay dos elementos e1, e2 con e1.equals(e2).
 * Búsqueda lineal: O(n). En la Unidad 9 lo haremos O(1) con hashing.
 */
public class Conjunto<T> {

    private Object[] datos = new Object[8];
    private int tamanio;

    /** @return true si se agregó; false si ya estaba. */
    public boolean agregar(T elemento) {
        if (contiene(elemento)) return false;      // el invariante se protege acá
        if (tamanio == datos.length) datos = Arrays.copyOf(datos, datos.length * 2);
        datos[tamanio++] = elemento;
        return true;
    }

    /** Usa EQUALS, no ==: dos objetos distintos de igual contenido son el mismo elemento. */
    public boolean contiene(T elemento) {
        for (int i = 0; i < tamanio; i++) {
            if (Objects.equals(datos[i], elemento)) return true;
        }
        return false;
    }

    public boolean quitar(T elemento) {
        for (int i = 0; i < tamanio; i++) {
            if (Objects.equals(datos[i], elemento)) {
                datos[i] = datos[--tamanio];       // trae el último al hueco
                datos[tamanio] = null;
                return true;
            }
        }
        return false;
    }

    public int tamanio()       { return tamanio; }
    public boolean estaVacio() { return tamanio == 0; }
}

PistaDos arreglos con el mismo índice: claves[i] corresponde a valores[i]. La decisión de diseño está en poner con una clave que ya existe: lo correcto es reemplazar el valor y devolver el anterior, no agregar otra entrada. Y obtener de una clave ausente devuelve null — mejor todavía, un Optional.
guia/i03_poo/i04_dificil/e03/Diccionario.java
package ar.uba.fi.cb100.guia.i03_poo.i04_dificil.e03;

import java.util.Arrays;
import java.util.Objects;
import java.util.Optional;

/**
 * TDA Diccionario: asocia claves únicas a valores.
 * Arreglos PARALELOS: claves[i] ↔ valores[i].
 * INVARIANTE: no hay dos claves ki, kj con ki.equals(kj).
 * Búsqueda lineal O(n); en la Unidad 9 será O(1) con hashing.
 */
public class Diccionario<K, V> {

    private Object[] claves  = new Object[8];
    private Object[] valores = new Object[8];
    private int tamanio;

    /** @return el valor anterior de esa clave, o null si no estaba. */
    @SuppressWarnings("unchecked")
    public V poner(K clave, V valor) {
        int i = indiceDe(clave);
        if (i >= 0) {                         // la clave ya estaba: REEMPLAZA
            V anterior = (V) valores[i];
            valores[i] = valor;
            return anterior;
        }
        if (tamanio == claves.length) {
            claves  = Arrays.copyOf(claves,  claves.length * 2);
            valores = Arrays.copyOf(valores, valores.length * 2);
        }
        claves[tamanio]  = clave;
        valores[tamanio] = valor;
        tamanio++;
        return null;
    }

    @SuppressWarnings("unchecked")
    public V obtener(K clave) {
        int i = indiceDe(clave);
        return (i >= 0) ? (V) valores[i] : null;
    }

    /** Versión honesta: el tipo avisa que puede no haber valor (Unidad 2). */
    public Optional<V> buscar(K clave) { return Optional.ofNullable(obtener(clave)); }

    public boolean contieneClave(K clave) { return indiceDe(clave) >= 0; }

    @SuppressWarnings("unchecked")
    public V quitar(K clave) {
        int i = indiceDe(clave);
        if (i < 0) return null;
        V anterior = (V) valores[i];
        claves[i]  = claves[--tamanio];       // trae el último al hueco
        valores[i] = valores[tamanio];
        claves[tamanio] = valores[tamanio] = null;
        return anterior;
    }

    public int tamanio() { return tamanio; }

    private int indiceDe(K clave) {
        for (int i = 0; i < tamanio; i++) {
            if (Objects.equals(claves[i], clave)) return i;   // equals, no ==
        }
        return -1;
    }
}

Lista enlazada genérica

Lista<T> con agregar, obtener(i), tamanio; test.

PistaUn Nodo<T> con valor y referencia al siguiente, como clase interna privada: nadie de afuera debe ver los nodos. Guardá una referencia al último para que agregar sea O(1). obtener(i) tiene que recorrer, así que es O(n) — a diferencia de un arreglo, que es O(1). Esa asimetría es lo que se estudia en la Unidad 5.
guia/i03_poo/i04_dificil/e06/Lista.java
package ar.uba.fi.cb100.guia.i03_poo.i04_dificil.e06;

import java.util.Objects;

/**
 * TDA Lista sobre nodos enlazados.
 * agregar al final: O(1) — obtener(i): O(n)
 */
public class Lista<T> implements Iterable<T> {

    /** Detalle de implementación: privado y estático, nadie de afuera lo ve. */
    private static final class Nodo<T> {
        final T valor;
        Nodo<T> siguiente;
        Nodo(T valor) { this.valor = valor; }
    }

    private Nodo<T> primero;
    private Nodo<T> ultimo;        // para que agregar sea O(1)
    private int tamanio;

    public void agregar(T elemento) {
        Nodo<T> nuevo = new Nodo<>(elemento);
        if (primero == null) primero = nuevo;
        else                 ultimo.siguiente = nuevo;
        ultimo = nuevo;
        tamanio++;
    }

    /** PRE: 0 <= i < tamanio. */
    public T obtener(int i) {
        if (i < 0 || i >= tamanio) {
            throw new IndexOutOfBoundsException("índice " + i + " fuera de [0.." + (tamanio - 1) + "]");
        }
        Nodo<T> n = primero;
        for (int k = 0; k < i; k++) n = n.siguiente;   // O(n): hay que recorrer
        return n.valor;
    }

    public boolean contiene(T elemento) {
        for (Nodo<T> n = primero; n != null; n = n.siguiente) {
            if (Objects.equals(n.valor, elemento)) return true;
        }
        return false;
    }

    public int tamanio()       { return tamanio; }
    public boolean estaVacia() { return tamanio == 0; }

    /** Permite usar el for-each sobre la lista. */
    @Override
    public java.util.Iterator<T> iterator() {
        return new java.util.Iterator<>() {
            private Nodo<T> actual = primero;
            @Override public boolean hasNext() { return actual != null; }
            @Override public T next() {
                if (actual == null) throw new java.util.NoSuchElementException();
                T v = actual.valor;
                actual = actual.siguiente;
                return v;
            }
        };
    }
}

Coherencia equals/compareTo

Clase de valor donde equals y compareTo sean consistentes (compareTo==0 ⟺ equals); test.

PistaLa regla del Javadoc de Comparable: x.compareTo(y) == 0 debería dar lo mismo que x.equals(y). Si no se cumple, un TreeSet (que usa compareTo) y un HashSet (que usa equals) se comportan distinto con los mismos datos. La forma de garantizarlo: que compareTo compare todos los campos que compara equals.
guia/i03_poo/i04_dificil/e08/Version.java
package ar.uba.fi.cb100.guia.i03_poo.i04_dificil.e08;

import java.util.Objects;

/**
 * Versión semántica (mayor.menor.parche).
 * COHERENCIA: compareTo(o) == 0  ⟺  equals(o)
 * Para lograrlo, compareTo compara EXACTAMENTE los mismos campos que equals.
 */
public final class Version implements Comparable<Version> {

    private final int mayor, menor, parche;

    public Version(int mayor, int menor, int parche) {
        this.mayor  = noNegativo(mayor,  "mayor");
        this.menor  = noNegativo(menor,  "menor");
        this.parche = noNegativo(parche, "parche");
    }

    private static int noNegativo(int v, String campo) {
        if (v < 0) throw new IllegalArgumentException(campo + " no puede ser negativo: " + v);
        return v;
    }

    @Override
    public int compareTo(Version o) {
        int c = Integer.compare(mayor, o.mayor);
        if (c != 0) return c;
        c = Integer.compare(menor, o.menor);
        if (c != 0) return c;
        return Integer.compare(parche, o.parche);   // los MISMOS tres campos que equals
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Version v = (Version) o;
        return mayor == v.mayor && menor == v.menor && parche == v.parche;
    }

    @Override public int hashCode()   { return Objects.hash(mayor, menor, parche); }
    @Override public String toString() { return mayor + "." + menor + "." + parche; }
}

import java.util.*;

/** Implementación sobre arreglo. El contrato no dice nada de arreglos: es un detalle. */
public class RepositorioEnMemoria<T extends Identificable<ID>, ID>
        implements Repositorio<T, ID> {

    private Object[] datos = new Object[8];
    private int cantidad;

    @Override
    public void guardar(T entidad) {
        Objects.requireNonNull(entidad, "la entidad no puede ser null");
        Objects.requireNonNull(entidad.id(), "el id no puede ser null");

        int i = indiceDe(entidad.id());
        if (i >= 0) { datos[i] = entidad; return; }        // reemplaza
        if (cantidad == datos.length) datos = Arrays.copyOf(datos, datos.length * 2);
        datos[cantidad++] = entidad;
    }

    @Override
    @SuppressWarnings("unchecked")
    public Optional<T> buscarPorId(ID id) {
        int i = indiceDe(id);
        return (i >= 0) ? Optional.of((T) datos[i]) : Optional.empty();
    }

    @Override
    public boolean eliminar(ID id) {
        int i = indiceDe(id);
        if (i < 0) return false;
        datos[i] = datos[--cantidad];
        datos[cantidad] = null;
        return true;
    }

    @Override
    @SuppressWarnings("unchecked")
    public List<T> todos() {
        List<T> r = new ArrayList<>(cantidad);
        for (int i = 0; i < cantidad; i++) r.add((T) datos[i]);
        return List.copyOf(r);                             // inmutable: no exponemos el estado
    }

    @Override public int cantidad() { return cantidad; }

    @SuppressWarnings("unchecked")
    private int indiceDe(ID id) {
        for (int i = 0; i < cantidad; i++) {
            if (Objects.equals(((T) datos[i]).id(), id)) return i;
        }
        return -1;
    }
}

import java.util.NoSuchElementException;

public class PilaSobreArreglo<T> implements Pila<T> {

    private Object[] datos = new Object[4];
    private int tope;

    @Override public void apilar(T e) {
        if (tope == datos.length) datos = Arrays.copyOf(datos, datos.length * 2);
        datos[tope++] = e;
    }

    @Override @SuppressWarnings("unchecked")
    public T desapilar() {

package ar.uba.fi.cb100.guia.i03_poo.i04_dificil.e10;

import java.util.NoSuchElementException;

public class PilaEnlazada<T> implements Pila<T> {

    private static final class Nodo<T> {
        final T valor;
        final Nodo<T> siguiente;
        Nodo(T valor, Nodo<T> siguiente) { this.valor = valor; this.siguiente = siguiente; }
    }

    private Nodo<T> cima;
    private int tamanio;

    @Override public void apilar(T e) {
        cima = new Nodo<>(e, cima);      // el nuevo nodo apunta al anterior: O(1)
        tamanio++;
    }

    @Override public T desapilar() {
        if (estaVacia()) throw new NoSuchElementException("pila vacía");
        T e = cima.valor;
        cima = cima.siguiente;           // el nodo viejo queda inalcanzable: lo limpia el GC
        tamanio--;
        return e;
    }

    @Override public T tope() {
        if (estaVacia()) throw new NoSuchElementException("pila vacía");
        return cima.valor;
    }

    @Override public boolean estaVacia() { return cima == null; }
    @Override public int tamanio()       { return tamanio; }
}
